Chapter 04

The Parser & the Manifest

Parsing is phase 4, and it's where Jinja runs for the first time. The parser reads every file in your project and its packages and produces one in-memory object, the Manifest. Every later phase reads from it, and so do outside tools such as Cosmos, data catalogs and CI pipelines (via manifest.json).

What a node is

Each thing dbt can build, test or describe becomes a node: a typed Python dataclass with a globally unique ID. The ID is resource_type.package.name, with an extra hash for generic tests so they don't collide.

The parse pipeline

ManifestLoader works in a fixed order, because each step relies on the ones before it:

  1. Read files. dbt walks every configured path (model-paths, macro-paths, test-paths and so on) in the root project, in every package under dbt_packages/, and in the internal packages (dbt, dbt_postgres). It records each file's checksum.dbt/parser/read_files.py
  2. Parse macros first. Every .sql file under macro-paths is scanned with Jinja's parser (not rendered) to find {% macro %}, {% test %} and {% materialization %} blocks. This has to come first, because models call macros while they are being parsed.dbt/parser/macros.py
  3. Parse SQL resources. Models, singular tests, analyses, snapshots and seeds become nodes. For models, dbt first tries the static parser and falls back to rendering Jinja in the parse context (below).dbt/parser/models.py · base.py
  4. Parse YAML properties. SchemaParser reads every .yml file. Its models: entries patch existing nodes (description, columns, config, tests), sources: become source nodes, and each entry under data_tests: becomes a generated test node.dbt/parser/schemas.py · generic_test_builders.py
  5. Resolve references. Each recorded ref and source is looked up and written into depends_on.nodes. A reference that can't be found is an error, unless the target is disabled, in which case it's a different error.ManifestLoader.process_refs / process_sources
  6. Validate and finish. dbt checks for duplicate names and resources with the same database location, resolves doc() blocks, validates the semantic layer, and writes target/manifest.json and target/partial_parse.msgpack.

Parsing a model, step by step

The static parser

Rendering Jinja for hundreds of models is slow, and most models only use simple ref, source and config calls. So dbt first runs dbt-extractor, a Rust/tree-sitter program that reads the Jinja syntax tree and pulls those calls out without executing anything. If the model contains anything the extractor doesn't understand (a {% set %}, an if, a custom macro call), dbt falls back to rendering Jinja for that model.

✓ Static parser handles it

select …
from {{ source('stg', 'employee') }} e
join {{ source('stg', 'person') }} p
  on …

↻ Needs full Jinja rendering

{{ config(…, post_hook=[…]) }}
…
{% if is_incremental() %}
  , tgt as (select … from {{ this }})
{% endif %}

Both paths should give the same node. dbt periodically checks this by sampling (comparing static and Jinja results) to catch differences.

The parse context

When Jinja rendering is needed, dbt renders the model with a ParseProvider behind the usual names:

CallWhat happens during parsing
ref('x')Appends x to node.refs and returns a placeholder relation that renders as something harmless
source('s','t')Appends ['s','t'] to node.sources
config(...)Merges the keyword arguments into the node's config
var, env_varResolved for real, and the names used are recorded (needed for partial parsing)
run_query, statementDon't touch the database; results are None
adapter.get_relation etc.Return nothing useful, because no queries run during parsing
calls to macrosThe macro really runs (with the same parse context) and is recorded in depends_on.macros

Refs inside conditionals

dbt only records a ref that actually executes during parsing. If you write {% if execute %}{{ ref('x') }}{% endif %}, the ref never runs at parse time, the dependency is never recorded, and at run time you get an error saying the model "depends on a node named 'x' which was not found", or else a silently wrong DAG order. If a ref can't be on every code path, add a "hint" comment that always runs, such as -- depends_on: {{ ref('x') }}, at the top of the file.

Config precedence

A model's final config is merged from three levels, from most to least specific:

  1. {{ config(...) }} in the model file
  2. config: under the model in a properties .yml
  3. dbt_project.yml, where the most specific path wins (e.g. models: dwlab: mart: beats models: dwlab:)

Most keys simply override. A few combine instead: tags are added together across levels, meta dictionaries are merged, and pre-hook/post-hook lists from all levels are appended. In your project, dbt_project.yml gives the mart folder +schema: mart, and dimemployee.sql adds materialized='incremental' and the hooks in its own config().

Generic tests become nodes

Every entry under data_tests: creates a test node during YAML parsing. Take this entry from your sources.yml:

- name: employee
  data_tests:
    - matches_source_metrics: {arguments: {key_column: businessentityid}, config: {tags: [reconcile]}}

From this entry dbt:

  1. finds the macro test_matches_source_metrics. A {% test matches_source_metrics %} block is stored as a macro with the test_ prefix.
  2. builds a test node named something like source_matches_source_metrics_stg_employee_businessentityid and gives it depends_on = the source, and tags = ['reconcile'].
  3. stores the keyword arguments (key_column, plus the implicit model) so the macro can be called with them at run time.

The test's SQL isn't rendered here. It's generated when the test runs (chapter 07).

Partial parsing

After each successful parse, dbt serialises the whole manifest to target/partial_parse.msgpack, along with the checksum of every file it read. On the next run it:

  1. checks the global inputs. If any of them changed, it throws the cache away and does a full parse.
  2. compares file checksums to find files that were added, changed or deleted.
  3. removes the affected nodes and re-parses those files, plus anything that depends on them in a way that affects parsing. For example, changing a macro re-parses the nodes that call it, and changing a YAML file re-applies its patches.
  4. re-parses nodes that use an environment variable whose value has changed.
Change since the last parseResult
Edited int_employee_sales.sqlPartial: that node is re-parsed
Edited record_dim_stats.sqlPartial: the macro is re-parsed, and so are the nodes that call it
Different --vars (a new run_id)Full re-parse
Changed profiles.yml, dbt_project.yml or the targetFull re-parse
New dbt version or new packagesFull re-parse
Edited an override of generate_schema_name/generate_alias_name/generate_database_nameFull re-parse (every node's schema could change)

To see the decision, run with --log-level debug. dbt logs whether partial parsing was enabled, and if not, which check failed. To skip the cache, use --no-partial-parse, which is also the first thing to try when parsing behaves strangely after switching git branches.

Applying this to your DAG

The nine dbt calls in one DAG run all pass the same run_id, so only the first call should do a full parse. If every call shows a full parse in the debug log, something else is changing between calls, for example a different target, or a target/ folder that isn't shared between workers. Chapter 08 covers a cleaner option: parse once at the start of the DAG run and reuse the manifest.

manifest.json

The manifest written to disk is the serialised form of the in-memory object. Its top-level keys are:

metadata        dbt_schema_version (…/manifest/v12.json), dbt_version, generated_at,
                invocation_id, project_name, adapter_type, env (DBT_ENV_CUSTOM_ENV_*)
nodes           models, tests, seeds, snapshots, analyses, operations   (by unique_id)
sources         source tables
macros          every macro incl. dbt's own and adapter macros
docs            {% docs %} blocks
exposures, metrics, groups, semantic_models, saved_queries, unit_tests
selectors       from selectors.yml
disabled        nodes that exist but have enabled: false
parent_map      unique_id → [parents]
child_map       unique_id → [children]
group_map
import json

m = json.load(open("target/manifest.json"))
node = m["nodes"]["model.dwlab.dimemployee"]

print(node["config"]["materialized"], node["config"]["unique_key"])
print("parents :", m["parent_map"]["model.dwlab.dimemployee"])
print("children:", m["child_map"]["model.dwlab.dimemployee"])
print("macros  :", node["depends_on"]["macros"])

Expect the children to be mostly tests (the unique, not_null and relationships tests and your singular assert_* tests), not models. Nothing in the project refs dimemployee except tests.

Key takeaways

  • The manifest is the full catalogue of nodes. Every later phase and every outside tool reads it.
  • dbt parses macros first, then SQL files, then YAML patches, and then resolves refs.
  • The static parser avoids Jinja for simple models. Anything more complex is rendered with the parse context, where refs are recorded and queries don't run.
  • A ref that doesn't execute during parsing isn't a dependency. Use a -- depends_on: hint.
  • Partial parsing uses file checksums, but global changes (vars, profile, project file, versions, name-generation macros) force a full re-parse.

Exercises

1 · Find the generated test

Using manifest.json, how would you list every test node tagged reconcile together with the source it tests?

Answer 
for uid, n in m["nodes"].items():
    if n["resource_type"] == "test" and "reconcile" in n["config"]["tags"]:
        print(uid, n["depends_on"]["nodes"])

Or, without Python: dbt ls --select tag:reconcile --resource-type test.

2 · The missing edge

A model contains {% if target.name == 'prod' %} … join {{ ref('dimsalesterritory') }} … {% endif %}. In dev everything works, but in prod the model sometimes runs before dimsalesterritory. Why?

Answer

Parsing happens with the current target. A manifest parsed in dev never runs that branch, so the edge doesn't exist in it. If prod reuses that manifest, or uses state that came from dev, the dependency is missing. Add -- depends_on: {{ ref('dimsalesterritory') }} outside the branch.

3 · Predict the parse

You run dbt run -s dimemployee --vars '{"run_id": 8}' twice in a row, then edit int_models.yml and run it again. Which runs do a full parse?

Answer

The first run does a full parse if the previous run used different vars. The second is partial, with no changes. The third is partial: it re-parses int_models.yml and re-applies its patches and tests.
