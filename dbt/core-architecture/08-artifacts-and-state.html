Chapter 08

Artifacts & State

A dbt process exits when it's done, but it leaves files behind. These artifacts are how dbt communicates with your orchestrator, your CI pipeline and the next dbt run. Once you can read them, you can do slim CI, retries, deferral and proper audit logging.

Each JSON artifact has a metadata.dbt_schema_version URL such as https://schemas.getdbt.com/dbt/manifest/v12.json. Tools that read artifacts should check this version. When dbt changes an artifact's structure, it releases a new schema version.

  • status uses the statuses from chapter 07. failures holds the failing-row count for tests.
  • adapter_response.rows_affected is the number of rows the main statement changed, here the number of merged rows. Hook statements aren't counted.
  • args records the full invocation, including vars, so you can always tell which run_id produced a file.

This is a good pattern, and the generated_at check is exactly right. A dbt call that crashes before it writes artifacts (exit code 2) would otherwise be credited with the previous step's results. Three improvements are worth considering:

  1. Check args.vars.run_id as well as the time. It's an exact match and doesn't depend on clocks: results["args"].get("vars", {}).get("run_id") == run_id.
  2. Record rows_affected per node from adapter_response. You get merge counts for free, without a separate query.
  3. Use a separate target-path per task (for example --target-path target/{{ ti.task_id }}), so two dbt tasks running at the same time can never overwrite each other's run_results.json. Your DAG runs them one after another today, but any parallel branch would break this.

State: comparing with a previous manifest

If you keep a copy of the artifacts from a known-good run (production's, say), dbt can compare the current project with it. You point to the folder with --state:

SelectorSelects nodes that…
state:newdon't exist in the saved manifest
state:modifiedare new or changed. Sub-selectors narrow it: .body, .configs, .relation, .persisted_descriptions, .macros, .contract
state:unmodified / state:oldthe opposites
result:error, result:fail, result:warn, result:successhad that status in the saved run_results.json
source_status:freshersources that received new data since the saved sources.json

How dbt decides a node was "modified":

  • body: the file checksum (raw code) changed.
  • configs: the unrendered config changed. Values that only differ after rendering (like target.name) don't count as changes.
  • macros: a macro the node uses, directly or indirectly, changed. Editing record_dim_stats marks both dimensions as modified.
  • relation: the database, schema or alias changed.

Deferral

With --defer --state prod_artifacts/, a ref() to a model that isn't selected and hasn't been built in the current target resolves to the production relation from the saved manifest instead. That's what lets CI build only what changed:

# build only changed models and their children; read unchanged parents from prod
$ dbt build --select state:modified+ --defer --state ./prod_artifacts --target ci

--favor-state goes further: even if a relation exists in the current target, refs prefer the state version. dbt clone creates copies of state relations in your target. On Postgres, which has no zero-copy clones, these are views pointing at the state relations.

Deferral and your generate_schema_name

Deferral only works when dev/CI and prod write to different schemas. Your generate_schema_name currently ignores the target and always writes to int/mart/rpt, so every target builds into the same place. Jinja chapter 11 shows an environment-aware version.

dbt retry

dbt retry reads target/run_results.json from the previous invocation and re-runs the nodes that errored or were skipped, using the same command and arguments. For an orchestrator this is the cheapest recovery: after fixing a transient problem, run dbt retry instead of the whole selection.

$ dbt build --select path:models --vars '{"run_id": 42}'   # 1 error, 3 skipped
$ dbt retry                                                 # re-runs those 4, same vars

Concurrency and the target folder

Two dbt processes that share one target/ directory race on manifest.json, run_results.json and partial_parse.msgpack. Prevent this with max_active_runs=1 on the DAG (overlapping DAG runs), avoid parallel dbt tasks over the same folder, or give each task its own --target-path/--log-path.

Artifacts as a data source

Because artifacts are JSON with versioned schemas, you can load them into the warehouse and report on them: model run times over time, test failure trends, lineage tables. Your lab already writes step-level counts into audit.etl_step. Loading run_results.json per node into an audit.dbt_node_result table would give you per-model timing and row counts, joined to audit.etl_run through run_id. An alternative that doesn't involve Airflow at all is an on-run-end hook that writes results directly. Jinja chapter 09 builds it.

Key takeaways

  • manifest.json describes the project, and run_results.json describes one execution. Both have versioned schemas.
  • Check that a run_results.json belongs to the step you think it does, using generated_at and args.vars.
  • --state lets dbt compare with saved artifacts: state:modified+, result:error, source_status:fresher.
  • --defer resolves unbuilt parents to production, which only works when environments use separate schemas.
  • dbt retry re-runs only what failed or was skipped. Use separate target folders when several dbt processes can run at once.

Exercises

1 · Merge counts in the audit table

Extend record_dbt_step so it also stores the total rows_affected of the step. Which field do you read, and what's the catch for the dimemployee step?

Answer

Sum r["adapter_response"].get("rows_affected") over the results, treating None as 0. The catch: for dimemployee it counts the rows touched by the MERGE only, not the parentemployeekey update in the post-hook, which is exactly why your record_dim_stats hook exists.

2 · Which models changed?

You keep a copy of the production target/ as prod_artifacts/. Someone edits record_dim_stats.sql. What does dbt ls --select state:modified --state prod_artifacts show?

Answer

Both dimsalesterritory and dimemployee, because they call the macro in their post-hooks, so state:modified.macros applies. The macro itself isn't a selectable node.

3 · Retry or re-run?

Stage 3 fails because the database was restarted while it ran. What's the fastest safe recovery, and why does it work with your run_id?

Answer

Run dbt retry in the same project folder (or clear the task in Airflow, which reruns the same command). Retry reuses the arguments recorded in run_results.json, including --vars, so the same run_id is used.
