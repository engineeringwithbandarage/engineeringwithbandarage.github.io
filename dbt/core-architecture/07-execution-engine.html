Chapter 07

The Execution Engine

Phase 7 is where your warehouse actually changes. A task organises the run, a pool of threads processes nodes, a runner handles each node, and a materialization macro decides which SQL to send. The adapter sends that SQL inside transactions. This chapter follows dimemployee through all of it.

~35 min read dbt Core 1.9+ Lab: the dimemployee incremental merge

BuildTask is a RunTask that uses a different runner for each node type (models, tests, seeds, snapshots, unit tests) and builds them in a single DAG pass. That's why dbt build can run a model's tests right after the model and skip its children if a test fails.

The life cycle of GraphRunnableTask.run()

  1. Initialise. Compile the graph, evaluate the selection, and create the GraphQueue (chapter 05).
  2. Fill the relation cache. For every schema the selected nodes will touch, dbt lists the relations that exist (on Postgres, with one query against the catalog per schema) and stores them in memory. From then on, adapter.get_relation() reads this cache instead of querying the database.adapter.set_relations_cache / populate_adapter_cache
  3. Create missing schemas. For each schema the selection needs (int, mart, rpt in your project), dbt runs create schema if not exists unless the cache already contains it.
  4. Run on-run-start hooks, for run, build, seed, snapshot and test.
  5. Execute nodes. A ThreadPool(threads) takes nodes from the queue. Each node goes to a runner, and each result goes back to the queue (mark_done) and into the results list.GraphRunnableTask.execute_nodes · call_runner
  6. Run on-run-end hooks, with results in the context.
  7. Write run_results.json, print the summary, and release the connections.

Finding the materialization follows the same idea as dispatch: materialization_incremental_postgres if it exists, otherwise materialization_incremental_default. Your root project is searched first, so a materialization you define there wins.

Connections and transactions

  • One connection per thread. Before a runner executes, the adapter opens or reuses a connection named after the node (adapter.connection_named(node.unique_id)). On Postgres this is a psycopg2 connection. It opens lazily, and dbt retries according to the retries setting in your profile.
  • Explicit transactions. SQLConnectionManager manages transactions itself. A {% call statement() %} block has auto_begin=True by default, which opens a transaction if none is open. run_query() passes auto_begin=False, so it doesn't open one itself, but it still runs inside any transaction already open on the node's connection. Nothing the materialization does is permanent until it calls adapter.commit().
  • Who commits? The materialization. Every built-in materialization runs its main statement and "inside" hooks, then calls adapter.commit(), then runs the "outside" hooks.
  • Cancelling. If the dbt process is interrupted (Ctrl-C), dbt cancels running queries on each open connection. On Postgres the adapter terminates the backend running the query.

Walking through the incremental materialization

Here is what materialization_incremental_default does for your dimemployee run. The control flow below is condensed from the dbt-adapters source. Read the real file next to it (see the lab box at the end).

{% materialization incremental, default -%}

  {%- set existing_relation = load_cached_relation(this) -%}
  {%- set target_relation   = this.incorporate(type='table') -%}
  {%- set temp_relation     = make_temp_relation(target_relation) -%}
  {%- set unique_key        = config.get('unique_key') -%}
  {%- set full_refresh_mode = should_full_refresh() -%}
  {%- set on_schema_change  = incremental_validate_on_schema_change(config.get('on_schema_change'), default='ignore') -%}

  {{ run_hooks(pre_hooks, inside_transaction=False) }}
  {{ run_hooks(pre_hooks, inside_transaction=True) }}       {#-- your: create sequence if not exists … --#}

  {% if existing_relation is none %}
      {%- set build_sql = get_create_table_as_sql(False, target_relation, sql) -%}       {#-- first run --#}
  {% elif full_refresh_mode %}
      {%- set build_sql = get_create_table_as_sql(False, intermediate_relation, sql) -%} {#-- then swap --#}
  {% else %}
      {% do run_query(get_create_table_as_sql(True, temp_relation, sql)) %}              {#-- tmp table --#}
      {% set dest_columns = process_schema_changes(on_schema_change, temp_relation, existing_relation) %}
      {% set strategy_sql_macro_func = adapter.get_incremental_strategy_macro(context, config.get('incremental_strategy')) %}
      {% set build_sql = strategy_sql_macro_func({'target_relation': target_relation,
                                                  'temp_relation': temp_relation,
                                                  'unique_key': unique_key,
                                                  'dest_columns': dest_columns, …}) %}
  {% endif %}

  {% call statement("main") %}
      {{ build_sql }}                                         {#-- the MERGE --#}
  {% endcall %}

  {{ run_hooks(post_hooks, inside_transaction=True) }}      {#-- your two post-hooks --#}
  {% do adapter.commit() %}
  {{ run_hooks(post_hooks, inside_transaction=False) }}

  {{ return({'relations': [target_relation]}) }}
{%- endmaterialization %}

Atomic by design

Your post-hooks run inside the same transaction as the merge, which is the default. If record_dim_stats fails (because audit.dim_load_stats is missing, say), the whole transaction rolls back and the dimension stays as it was. If a hook shouldn't keep the merge's transaction and locks open, such as a long analyze or a notification, wrap it as after_commit("analyze {{ this }}") so it runs after the commit. (vacuum is stricter: PostgreSQL refuses to run it inside any transaction block, so test it carefully on your dbt version, or run it outside dbt.)

Sequences are not transactional

In PostgreSQL, nextval() is never rolled back. If the merge fails after the temp table was built, the keys already drawn are lost, and the next run continues from a higher value. That's harmless for a surrogate key, but don't expect your employeekey values to have no gaps.

Tests at run time

For a test node, TestRunner renders the test macro (for example test_matches_source_metrics(model=…, key_column='businessentityid')) and wraps the returned query with get_test_sql:

select
    count(*)              as failures,
    count(*) != 0         as should_warn,
    count(*) != 0         as should_error
from (
    -- your test SQL: one row per failing record
) dbt_internal_test

The runner reads that single row and compares it with the test's severity, warn_if and error_if config, which default to "error if not 0". The status becomes pass, warn, fail or error, where error means the SQL itself failed. With store_failures, the failing rows are also saved to a table in an audit schema.

Your record_dbt_step callback groups these into passed (success, pass, warn), failed (fail, error, runtime error) and skipped (everything else), which matches the categories above.

Threads, the GIL and performance

dbt uses threads, not processes. Python's GIL isn't a bottleneck, because each thread spends nearly all its time waiting for the database. The real limits are:

  • The DAG's width. A chain can't run in parallel however many threads you have.
  • The warehouse. On your two-CPU lab server, two heavy queries at once mostly compete for the same CPUs.
  • Start-up cost: phases 1–6 (chapter 01), paid once per process.

Key takeaways

  • Tasks organise the run, runners handle one node each, and materializations decide the SQL.
  • A relation cache filled at start-up answers get_relation and load_cached_relation without extra queries.
  • There's one connection per thread, with explicit transactions. The materialization commits, and inside-transaction hooks are atomic with the main statement.
  • The incremental materialization is: temp table → schema check → strategy SQL (here MERGE) → hooks → commit.
  • Tests are wrapped in a count(*) query and compared with warn_if/error_if.

Exercises

1 · Where do keys get assigned?

At which moment in the materialization does nextval('mart.dimemployee_key_seq') run, and how many times per new row?

Answer

It runs while the compiled SELECT is being written into the temp relation, once per row that the SELECT returns with a null t.employeekey. The merge then only copies those values.

2 · Partial success?

The merge succeeds but the second post-hook (record_dim_stats) fails. What does mart.dimemployee look like afterwards?

Answer

Unchanged. Both post-hooks are inside the transaction, the commit never happens, and the connection rolls back. The node's status is error.

3 · Threads

Would changing threads: 1 to threads: 4 speed up stage 4 of your DAG?

Answer

No. Stage 4 runs each model in a separate dbt call with a single node selected, so there's never more than one node to run at a time. Threads only help when one invocation has several independent nodes ready at once, as in stage 3 or a combined dbt build.
