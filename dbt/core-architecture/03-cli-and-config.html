Chapter 03

CLI & Configuration Loading

Phases 1–3 of every invocation decide which project, profile, target, variables and flags the rest of the run will use. Errors here are cheap to fix but often confusing, because several sources (command line, environment, YAML files and defaults) can each set the same value.

~25 min read dbt Core 1.9+ Lab: profiles.yml, dbt_project.yml, DAG vars

The Click application

The dbt executable is a console script that calls dbt.cli.main:cli, a Click group. Each command (run, build, test, compile, parse, ls, run-operation and so on) is a Click command on that group. Its parameters are stacked on as decorators taken from dbt/cli/params.py. Simplified, dbt run looks like this:

@cli.command("run")
@click.pass_context
@global_flags
@p.exclude
@p.full_refresh
@p.profiles_dir
@p.project_dir
@p.select
@p.target
@p.threads
@p.vars
# … more params …
@requires.postflight
@requires.preflight
@requires.profile
@requires.project
@requires.runtime_config
@requires.manifest
def run(ctx, **kwargs):
    task = RunTask(ctx.obj["flags"], ctx.obj["runtime_config"], ctx.obj["manifest"])
    results = task.run()
    success = task.interpret_results(results)
    return results, success

The requires.* decorators are a pipeline. Each one adds something to Click's context object, and the next one uses it:

  1. preflight builds the Flags object, sets up logging and the event manager, starts the invocation (a new invocation_id), and records anonymous usage tracking if it's enabled.dbt/cli/requires.py · dbt/cli/flags.py
  2. profile finds and renders profiles.yml, then picks the target.dbt/config/profile.py
  3. project finds and renders dbt_project.yml, plus packages.yml/dependencies.yml and selectors.yml.dbt/config/project.py
  4. runtime_config combines project + profile + flags into a RuntimeConfig and registers the adapter.dbt/config/runtime.py
  5. manifest parses the project, or loads it from the partial-parse cache (chapter 04), and makes the manifest available.dbt/parser/manifest.py
  6. postflight runs after the command finishes. It fires the final events, decides the exit code, and turns exceptions into the "Encountered an error" output you see.

Not every command needs every step

dbt debug and dbt deps don't use requires.manifest, so they never parse your models. That's why dbt deps still works while a model has a syntax error, and why dbt debug is the right tool for checking connections even when parsing is broken.

Flags and their precedence

Every flag you can pass on the command line can also be set in two other places. dbt takes the first value it finds, in this order:

PrioritySourceExample
1 (highest)Command-line optiondbt --no-use-colors run
2Environment variable DBT_<FLAG>DBT_USE_COLORS=false, DBT_PARTIAL_PARSE=false
3flags: block in dbt_project.ymlflags: {use_colors: false, send_anonymous_usage_stats: false}
4 (lowest)Built-in defaultcolors on, partial parse on
 
flags:
  use_colors: false                 # Airflow logs are plain text anyway
  send_anonymous_usage_stats: false
  partial_parse: true

Old location

Before 1.8, these settings went in a config: block inside profiles.yml. That location is deprecated, so use flags: in dbt_project.yml instead. Behaviour change flags, the switches dbt Labs uses to roll out breaking changes gradually (for example require_explicit_package_overrides_for_builtin_materializations), also go in that flags: block.

Finding the project and the profile

Project directory

dbt uses --project-dir if given, otherwise the DBT_PROJECT_DIR environment variable, otherwise the current working directory. Your DAG passes cwd=DBT_DIR to every BashOperator, so the current-directory rule picks /opt/airflow/dbt/dwlab.

profiles.yml directory

  1. --profiles-dir
  2. DBT_PROFILES_DIR
  3. the current working directory, if it contains a profiles.yml
  4. ~/.dbt/

Your lab keeps profiles in dbt/profiles/, which isn't the project folder. So inside the container, either DBT_PROFILES_DIR points there or the file is mounted at one of the locations above. dbt debug prints which path it used, and that's the fastest way to check.

Choosing a profile and a target

dwlab:                     # ← matched by `profile: dwlab` in dbt_project.yml
  target: dev              # ← used unless --target is passed
  outputs:
    dev:
      type: postgres       # ← decides which adapter plugin is loaded
      host: postgres-15
      port: 5432
      user: "{{ env_var('DBT_PG_USER') }}"
      password: "{{ env_var('DBT_PG_PASSWORD') }}"
      dbname: dwlab
      schema: public       # ← target.schema
      threads: 1           # ← size of the worker thread pool

The profile name comes from profile: in dbt_project.yml (or --profile). The target comes from --target, or else the profile's target: key. The chosen output becomes the target object in Jinja: target.name is dev, target.schema is public, target.type is postgres, and target.threads is 1. Secrets such as the password aren't exposed there.

Rendering YAML: Jinja before parsing

profiles.yml and dbt_project.yml are Jinja templates first and YAML second. dbt reads the YAML into Python objects and then renders each string value through Jinja with a limited context. The full model context isn't available this early.

FileAvailable in JinjaNot available
profiles.ymlenv_var(), var() (CLI --vars only)target, ref, macros
dbt_project.ymlenv_var(), var(), targetref, source, your macros
packages.ymlenv_var() (e.g. for git tokens)almost everything else
model .yml propertiesa parse-time context (var, env_var, target, doc() in descriptions)runtime-only features (run_query results)

Under the hood: hooks are skipped on purpose

When dbt renders dbt_project.yml, it deliberately skips some keys, most importantly on-run-start, on-run-end, +pre-hook and +post-hook. Hooks need the runtime context (this, results, a database connection), so they're stored as raw strings and rendered later, when each one runs. That's also why the hooks inside your model's config() are written as quoted strings that contain {{ }}.

Variables: var() resolution

Your project relies on one variable, run_id, which Airflow passes in on every call. Here is how dbt resolves {{ var('run_id') }}:

  1. --vars on the command line, parsed as YAML: --vars '{"run_id": 42}' gives the integer 42.
  2. Project vars scoped to the package: vars: {dwlab: {run_id: …}}.
  3. Global project vars: vars: {run_id: 0}, which is what your dbt_project.yml sets.
  4. The default argument: var('run_id', 0).
  5. Otherwise, a compilation error: Required var 'run_id' not found in config.

The silent default

Because dbt_project.yml sets run_id: 0, running dbt run --select dimemployee by hand without --vars works. It then writes audit rows with run_id = 0, and record_dim_stats records statistics under run 0. Chapter 17 of the Jinja tutorial shows a two-line guard that refuses to run with the default in production.

Variables passed with --vars are parsed as YAML, so '{"flag": false}' gives a real boolean. env_var() always returns a string, so env_var('X') == 'false' is a string comparison and {% if env_var('X') %} is true for any non-empty value. Convert explicitly, for example with env_var('X', 'false') | as_bool in YAML or env_var('X') | lower == 'true' in SQL files.

Environment variables and secrets

  • env_var('NAME') raises an error at load time if NAME isn't set, and env_var('NAME', 'default') doesn't.
  • Variables whose name starts with DBT_ENV_SECRET_ are hidden in logs. They can only be used in profiles.yml, packages.yml and similar configuration files, not in model SQL, so a secret can't end up in compiled SQL or manifest.json.
  • Variables starting with DBT_ENV_CUSTOM_ENV_ are copied into the metadata.env section of every artifact. This is useful for stamping artifacts with an Airflow run id.
  • dbt records which environment variables each node used. Changing one later makes partial parsing re-parse the nodes that use it (chapter 04).
dbt_task = dict(
    cwd=DBT_DIR,
    env={"DBT_ENV_CUSTOM_ENV_AIRFLOW_RUN_ID": "{{ run_id }}",
         "DBT_ENV_CUSTOM_ENV_ETL_RUN_ID": "{{ ti.xcom_pull(task_ids='start_run') }}"},
    append_env=True,               # keep PATH, DBT_PG_USER, … from the worker
    on_success_callback=record_dbt_step,
    on_failure_callback=record_dbt_step,
)

RuntimeConfig: the merged result

Everything above ends up in one object. RuntimeConfig inherits from both Project and Profile and also holds the CLI args, so every later component (parser, compiler, runners) asks this single object for settings. Its important parts are:

  • project settings: name, paths (model-paths, macro-paths, target-path), the models: config tree, quoting, dispatch, flags
  • profile settings: credentials, threads, target name
  • vars: a VarProvider combining CLI vars with project vars
  • dependencies: the loaded packages, each with its own Project

dbtRunner: calling dbt from Python

The same CLI can be called in-process. Orchestrators use this to avoid starting a process for each command, and to get structured results instead of reading log text.

from dbt.cli.main import dbtRunner, dbtRunnerResult

runner = dbtRunner()
res: dbtRunnerResult = runner.invoke(
    ["run", "--select", "dimemployee", "--vars", '{"run_id": 42}'],
    project_dir="/opt/airflow/dbt/dwlab",
)

print(res.success)                  # bool
for r in res.result:                # RunExecutionResult → NodeResult objects
    print(r.node.unique_id, r.status, r.execution_time, r.adapter_response)
  • Reuse a manifest: dbtRunner(manifest=m) skips parsing for later invocations in the same process. The m comes from runner.invoke(["parse"]).result.
  • Listen to events: dbtRunner(callbacks=[fn]) calls fn(event) for every structured log event, which is useful for live progress.
  • Limits: dbt isn't designed to run several invocations at the same time in one process. Use one invocation at a time per process, and expect global state such as flags and adapters to be shared between invocations.

Exit codes

CodeMeaningTypical cause
0Success (warnings allowed)All nodes passed, or tests only warned
1Handled failureA model errored or a test failed
2Unhandled exceptionBad flags, broken YAML, missing profile, crash

Airflow's BashOperator fails the task for any non-zero code, so 1 and 2 look the same in the Airflow UI. Your record_dbt_step callback can tell them apart: an exit code of 2 usually leaves no fresh run_results.json, which your generated_at >= ti.start_date check correctly treats as "nothing to count".

Try it yourself

$ dbt debug                                    # shows profiles.yml path, target, connection test
$ dbt debug --config-dir                       # prints only the profiles directory in use
$ DBT_USE_COLORS=false dbt ls --select dimemployee
$ dbt ls --select dimemployee --vars '{"run_id": 7}' --output json --output-keys name config

Key takeaways

  • Every command passes through the decorator chain preflight → profile → project → runtime_config → manifest, and the result is one RuntimeConfig.
  • Flag precedence is CLI > DBT_ env var > flags: in dbt_project.yml > default.
  • YAML config files are rendered with a limited Jinja context, and hooks are kept as raw strings until run time.
  • --vars values keep their YAML types, while env_var() always returns a string.
  • dbtRunner is the in-process API, so you don't need to start a new process for every command.

Exercises

1 · Which value wins?

dbt_project.yml has flags: {use_colors: true}, the worker has DBT_USE_COLORS=false, and the DAG passes --no-use-colors. What is used, and what happens if you remove the CLI option?

Answer

Colors are off because of the CLI option. Without it, the environment variable still beats the project file, so colors stay off.

2 · Typed vars

A model contains {% if var('full_reload') %}. Airflow passes --vars '{"run_id": 5, "full_reload": "false"}'. What happens?

Answer

"false" is a quoted YAML string, so it's non-empty and therefore truthy, and the branch runs. Pass the unquoted boolean false, or compare explicitly.

3 · Secrets in models

Why does {{ env_var('DBT_ENV_SECRET_API_KEY') }} fail inside a model but work in profiles.yml?

Answer

dbt deliberately blocks secret variables outside configuration files, so they can't be written into compiled SQL, manifest.json or logs.
