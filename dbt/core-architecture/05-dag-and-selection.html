Chapter 05

The DAG & Node Selection

The manifest is a list of nodes, and the DAG is the set of relationships between them. This chapter covers how dbt builds the graph, how a --select string becomes a set of node IDs, why tests appear in runs you didn't expect them in, and how the queue decides what each thread does next.

~30 min read dbt Core 1.9+ Lab: the dwlab lineage and your DAG's selectors

From depends_on to a graph

After parsing, every node has a depends_on.nodes list. The Linker (in dbt/compilation.py) creates a networkx.DiGraph, adds every node, and adds an edge parent → child for each dependency. dbt then checks the graph with networkx.find_cycle, and a cycle stops the run with "Found a cycle: …".

Macro dependencies (depends_on.macros) are not edges in the DAG. Macros don't run as steps of their own. dbt tracks them separately so that state:modified can notice when a macro a model uses has changed.

What the figure tells you about your project

  • Inside one invocation, dimsalesterritory and dimemployee are independent. With threads: 2, a single dbt build could build them at the same time.
  • rpt_load_summary has to run last because it reads audit.dim_load_stats, which the dimensions' post-hooks write. dbt doesn't know this, because the dependency goes through a hook rather than a ref. Your Airflow DAG enforces the order between separate calls. If you ever move to a single dbt build, add -- depends_on: {{ ref('dimemployee') }} and -- depends_on: {{ ref('dimsalesterritory') }} to rpt_load_summary.sql.

The selector engine

A selection string is parsed into a spec (a tree of unions, intersections and differences) and then evaluated against the graph. The result is always a set of unique_ids.

Indirect selection: why tests come along

When you select a model or source, dbt can also pull in the tests attached to it, even though you didn't select those tests by name. This is called indirect selection. You control it with --indirect-selection (or DBT_INDIRECT_SELECTION):

ModeA test is included when…
eager (default)any of its parents is selected
buildableall its parents are selected, or are ancestors of the selection
cautiousall of its parents are selected
emptynever (only explicitly selected tests run)

Let's apply this to your stage 2 commands:

dbt test --select source:stg,tag:reconcile           # reconcile tests on stg sources
dbt test --select source:stg --exclude tag:reconcile # all other stg tests
  • source:stg directly selects the 21 source nodes. dbt test only executes tests, and those tests reach the selection through indirect selection, because their parent is a selected source.
  • tag:reconcile directly selects the reconcile tests, since the tag lives on the test config.
  • The comma intersects the two sets, each including its indirectly selected tests. That leaves exactly the reconcile tests whose parent is in stg.
  • The second command takes all tests on stg sources and removes the reconcile ones.

Relationship tests across layers

Under eager, dbt test --select dimsalesterritory also runs the relationships test defined on dimemployee.salesterritorykey, because one of that test's parents (dimsalesterritory) is selected. If dimemployee hasn't been rebuilt yet in this run, that test checks yesterday's data. Your stage 4 tests both models together, so you don't hit this, but it's a common surprise when a project uses dbt build with narrow selections.

YAML selectors

Long selection strings in DAG code are hard to review. A selectors.yml at the project root gives them names, keeps them in version control, and stores them in the manifest:

selectors:
  - name: stg_reconcile
    definition:
      intersection:
        - method: source
          value: stg
        - method: tag
          value: reconcile

  - name: stg_quality
    definition:
      union:
        - method: source
          value: stg
        - exclude:
            - method: tag
              value: reconcile

  - name: employee_dimension
    description: "dimemployee and everything upstream of it"
    definition:
      method: fqn
      value: dimemployee
      parents: true
      indirect_selection: cautious
dbt test  --selector stg_reconcile --vars '{"run_id": 42}'
dbt build --selector employee_dimension

The GraphQueue

Once the selection is known, dbt takes the matching sub-graph and wraps it in a GraphQueue (in dbt/graph/queue.py). The queue:

  1. keeps track of each selected node's unfinished selected parents. Unselected parents are assumed to exist already.
  2. offers nodes with no unfinished parents to the worker threads, ordered by a priority score based on their position in the graph, so that long chains start early.
  3. when a thread finishes a node, calls mark_done(node), which can make that node's children ready.
  4. when a node fails, has the task mark its selected descendants as skipped. In dbt build, a failing test also causes its downstream models to be skipped.

Your dwlab profile sets threads: 1, so this all runs one node at a time. The ordering logic is the same, but there's no parallelism. For a lab with two CPUs and small views that's a sensible choice. Raising it to 2 mostly helps when the database spends its time waiting on I/O rather than CPU.

Previewing a selection

The safest habit is to preview a selection with dbt ls. It uses the same selector engine as the real commands, but builds nothing.

$ dbt ls --select +dimemployee --resource-type model
$ dbt ls --select source:stg,tag:reconcile                   # what stage 2a will run
$ dbt ls --select dimsalesterritory --resource-type test     # see indirect selection at work
$ dbt ls --select dimsalesterritory --resource-type test --indirect-selection cautious
$ dbt ls --select config.materialized:incremental --output json --output-keys name config

Key takeaways

  • The DAG is a networkx.DiGraph built from depends_on.nodes. Macros aren't nodes in it.
  • Dependencies that go through hooks or direct table names are invisible to dbt. Make them visible with ref or -- depends_on:.
  • Space is union, comma is intersection, and --exclude removes nodes. Methods select by name, path, tag, config, state and more.
  • Tests are pulled in through indirect selection, eager by default.
  • GraphQueue releases a node only once all its selected parents are done. Failures skip the node's descendants.

Exercises

1 · One build instead of four stages?

Write a single dbt build selection that covers stages 3–5 of your DAG, and say what you would have to change in the project for the ordering to be correct.

Answer

dbt build --select path:models/int dimsalesterritory dimemployee rpt_load_summary, or path:models. For the ordering to be correct, add -- depends_on: refs to both dimensions in rpt_load_summary.sql. Otherwise dbt may build the report before the dimensions' post-hooks have written audit.dim_load_stats.

2 · Read a selector

What does dbt ls --select 1+dimemployee+1 return?

Answer

It returns dimemployee, its direct parent int_dimemployee_prepared, and its direct children. Its only children are tests: the unique/not_null/accepted_values/relationships tests and the singular assert_dimemployee_* tests, plus the relationships test on parentemployeekey, which points back at dimemployee itself.

3 · Skipped downstream

In stage 3, int_employee_hierarchy fails. Which of the other int_* models still build, and what's the status of int_dimemployee_prepared?

Answer

The other four int_* views build normally because they're independent. int_dimemployee_prepared is skipped because one of its selected parents failed. The command exits with code 1.
