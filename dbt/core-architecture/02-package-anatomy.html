Chapter 02

Package Anatomy

The single pip install dbt-postgres in your Dockerfile installs about a dozen Python distributions. Four of them hold most of dbt: dbt-core, dbt-common, dbt-adapters and dbt-postgres. This chapter shows what each one contains, how they fit together, and where to look when you want to read the source.

~20 min read dbt Core 1.9+ Lab: the Airflow worker image

From one package to four

Until version 1.7, an adapter such as dbt-postgres depended directly on a matching dbt-core, and Core contained the base adapter classes, the built-in macros and the Jinja helpers. Version 1.8 split this apart:

  • dbt-common holds code that both Core and adapters need, such as the Jinja client, event and logging types, exceptions and dataclass helpers.
  • dbt-adapters holds the adapter interface: base classes, the adapter factory and the global macro project (all built-in macros, including the materializations).
  • dbt-core keeps the CLI, config loading, parsing, the graph, compilation and the tasks.
  • dbt-postgres (the adapter) depends on dbt-adapters and dbt-common, not on a specific Core version.

The goal was to let adapters and Core be released on separate schedules. One side effect: installing an adapter no longer pins your Core version.

One dbt namespace, several distributions

If you look inside your virtualenv's site-packages you won't find a separate folder per distribution. dbt uses Python namespace packages (PEP 420): dbt-core, dbt-adapters and dbt-postgres all install files into the same dbt/ directory. Python merges them, so import dbt.adapters.postgres and import dbt.task.run look as if they come from one package, even though pip installed them separately.

├── config/           ← dbt-core

dbt_extractor/        ← dbt-extractor (compiled Rust extension)

Why mixed versions break in strange ways

Because all of these share one directory, mixing versions (for example an old adapter with a new Core, or two venvs on one PYTHONPATH) tends to fail at import time with an ImportError deep inside dbt, rather than with a clear "version mismatch" message. Your Dockerfile already does the right thing by putting dbt in its own venv, /home/airflow/dbt_venv, which keeps it away from Airflow's dependencies.

dbt-adapters: the interface and the built-in macros

This package defines what every adapter must be able to do, and supplies the macros that call it.

The class hierarchy

BaseAdapter                       dbt/adapters/base/impl.py
 └── SQLAdapter                   dbt/adapters/sql/impl.py
      └── PostgresAdapter         dbt/adapters/postgres/impl.py

BaseConnectionManager             dbt/adapters/base/connections.py
 └── SQLConnectionManager         dbt/adapters/sql/connections.py
      └── PostgresConnectionManager   dbt/adapters/postgres/connections.py  (psycopg2)

BaseRelation  → PostgresRelation   (database.schema.identifier + quoting rules)
Column        → PostgresColumn     (name, dtype, size helpers)

Two kinds of methods are worth telling apart:

  • Methods marked @available can be called from Jinja as adapter.<method>. Examples are adapter.get_relation(), adapter.get_columns_in_relation(), adapter.quote() and adapter.dispatch().
  • Python-only methods are used by tasks and runners and aren't visible from Jinja. Examples are connection management, cache population and cancelling queries.

The global project

The folder dbt/include/global_project/macros/ is loaded as an internal dbt package named dbt. It contains the macros you have been using without realising they are macros:

materializations/
  models/
    table.sql            ← materialization table, default
    view.sql             ← materialization view, default
    incremental/
      incremental.sql    ← materialization incremental, default
      merge.sql          ← get_merge_sql, get_delete_insert_merge_sql …
      is_incremental.sql ← is_incremental()
      on_schema_change.sql
  snapshots/  seeds/  tests/  hooks.sql
adapters/                ← create_table_as, drop_relation, rename_relation … (dispatched)
generic_test_sql/        ← SQL behind unique, not_null, accepted_values, relationships
get_custom_name/         ← generate_schema_name, generate_alias_name, generate_database_name
etc/                     ← statement, run_query, datetime helpers
utils/                   ← cross-database macros: dateadd, datediff, concat, hash …

Most of these are dispatched. For example, create_table_as calls adapter.dispatch('create_table_as', 'dbt'), which picks postgres__create_table_as if it exists and falls back to default__create_table_as if not. Your project's macros are searched first, which is how your generate_schema_name replaces the built-in one.

dbt-postgres: what an adapter really adds

An adapter is small compared with Core. dbt-postgres provides:

  • Credentials: a dataclass describing the profiles.yml fields it accepts (host, port, user, password, dbname, schema, keepalives_idle, sslmode, search_path, retries, …).
  • Connection manager: opens psycopg2 connections, translates database errors into dbt exceptions, and implements cancel() (on Postgres it terminates the backend of the running query).
  • Adapter methods: Postgres-specific behaviour such as the date function, how it lists relations, and the maximum identifier length (63 characters).
  • Macros: dbt/include/postgres/macros/ holds the postgres__* versions of dispatched macros (catalog queries, create_table_as with unlogged support, the Postgres incremental strategies append, delete+insert, merge and microbatch, and so on).

Under the hood: how dbt finds the plugin

When the profile says type: postgres, the adapter factory imports dbt.adapters.postgres and reads its Plugin object (an AdapterPlugin). That object names the adapter class, the credentials class and the include path holding its macros. It can also name dependencies: dbt-redshift, for instance, declares postgres as a dependency, so a Redshift project can use postgres__ macros as fallbacks. The same chain drives adapter.dispatch, which tries redshift__, then postgres__, then default__.

Reading the source productively

Before you start reading, decide which question you're trying to answer. Here are good starting points:

QuestionStart reading at
What SQL does an incremental merge produce?global_project/macros/materializations/models/incremental/ and include/postgres/macros/materializations/incremental_strategies.sql
What can I call on adapter in Jinja?Methods decorated @available in dbt/adapters/base/impl.py and dbt/adapters/postgres/impl.py
What does ref() do at parse time vs. run time?dbt/context/providers.py: look for ParseRefResolver and RuntimeRefResolver
How is a selector string interpreted?dbt/graph/selector_spec.py, cli.py and selector_methods.py
Why was the project fully re-parsed?dbt/parser/manifest.py: search for the partial-parsing checks

Try it yourself on the lab server

These commands only read installed files:

$ docker exec airflow_airflow-worker_1 /home/airflow/dbt_venv/bin/pip list --format=freeze
$ docker exec airflow_airflow-worker_1 /home/airflow/dbt_venv/bin/python -c "import dbt.adapters.postgres as p, dbt.task.run as r; print(p.__file__); print(r.__file__)"
$ docker exec airflow_airflow-worker_1 ls /home/airflow/dbt_venv/lib/python3.10/site-packages/dbt/include/global_project/macros/materializations/models/incremental/

In the first command's output, find dbt-core, dbt-adapters, dbt-common and dbt-postgres and note their versions. Then open is_incremental.sql from the third listing. It's about ten lines long, and it's the macro your dimemployee relies on.

Key takeaways

  • dbt is made of several distributions sharing one dbt namespace: core (CLI, parse, graph, tasks), adapters (interface + built-in macros), common (shared plumbing) and the adapter plugin.
  • The materializations and most built-in behaviour live in global_project as Jinja macros that you can read and override.
  • Adapters only implement what differs between databases: credentials, connections, a few methods and the postgres__ macros.
  • Since 1.8, installing an adapter doesn't pin Core, so pin both in your image.

Exercises

1 · Where does incremental live?

Which distribution contains the incremental materialization, and which one contains the SQL for the merge strategy on Postgres?

Answer

The materialization itself (materialization incremental, default) is in dbt-adapters, under global_project. The Postgres strategy macros (such as postgres__get_incremental_merge_sql, or the default merge SQL it calls) are in dbt-postgres and dbt-adapters respectively. Read incremental_strategies.sql in the Postgres include folder to see which one your version uses.

2 · Adapter method or macro?

You want to know whether mart.dimemployee exists from inside a macro. Is that a Python adapter method or a Jinja macro, and what's the call?

Answer

It's an @available Python method on the adapter: adapter.get_relation(database=this.database, schema='mart', identifier='dimemployee'). It returns a relation or none, and it reads dbt's relation cache, which is filled before the run starts.

3 · Diagnose the image

After an image rebuild, a model that used to compile now fails with a deprecation error about test arguments. Nobody changed the Dockerfile. What happened, and what is the fix?

Answer

The Dockerfile pins only dbt-postgres, so pip resolved a newer dbt-core during the rebuild, and its behaviour changed. The fix is to pin dbt-core==X.Y.Z next to the adapter, or use a constraints file, so rebuilds are reproducible.
