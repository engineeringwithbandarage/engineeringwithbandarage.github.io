Chapter 06

Compilation & the Jinja Engine

This is the link between the two tutorials. Here you'll see what kind of Jinja environment dbt creates, how the names you use in templates (ref, this, adapter, var) are put together in layers, how dbt chooses which macro a name refers to, and what "compiled SQL" actually means.

~35 min read dbt Core 1.9+ Lab: compiling dimemployee

dbt's Jinja environment

dbt doesn't use a plain jinja2.Environment. The template client in dbt_common/clients/jinja.py builds a customised one:

  • A sandboxed environment (jinja2.sandbox.SandboxedEnvironment). Templates can call methods on the objects they're given, but they can't reach Python internals such as attributes starting with _, __class__ or __globals__. That's why there's no import os in dbt and why only a few modules are exposed through modules.
  • Extensions: Jinja's built-in do extension (which provides {% do … %}), plus dbt's own block tags {% materialization %}, {% test %}, {% docs %} and {% snapshot %}.
  • A custom Undefined class. Using an unknown name produces a dbt Compilation Error that names the missing thing (for example 'record_dims_stats' is undefined) instead of Jinja's default behaviour.
  • A "native" variant for YAML configuration. When a value should keep its type (a list, a number, a boolean) rather than become a string, dbt renders it with Jinja's native-types environment. The filters as_bool, as_number, as_native and as_text control that conversion.
  • A template cache. Parsed templates (including macro files) are compiled once into Python code and reused, so calling a macro a thousand times doesn't re-parse it a thousand times.

Under the hood: Jinja compiles to Python

Jinja doesn't interpret templates directly. It lexes and parses the template into an AST, generates Python source code from it, compiles that code, and runs it. Every {% macro %} becomes a Python function. When you call {{ record_dim_stats(scd2=true) }}, you're calling a Python callable that dbt has wrapped in a MacroGenerator. The wrapper keeps the call stack for error messages, handles return(), and injects the right context.

The context, layer by layer

The set of names available while a template renders is called the context. dbt builds it from a series of classes, each adding names to the one below. In dbt/context/:

This is why the same expression can behave differently depending on where it appears. {{ this }} works in a model and in its hooks, but is undefined in on-run-end. {{ results }} exists only in on-run-end.

Macro resolution: which macro wins?

When a template calls {{ foo() }} without a package prefix, dbt looks the name up in a fixed order. Simplified:

  1. The root project (dwlab). Your macros override everything else, which is how your generate_schema_name replaces dbt's built-in one.
  2. The package the calling node belongs to, if it isn't the root project. This lets a package's own models call its own helpers without a prefix.
  3. dbt's internal packages: the adapter's macros (dbt_postgres), then the global project (dbt).

Macros from other installed packages are only reachable with their namespace, as in {{ dbt_utils.star(...) }}. Two packages can't silently override each other's macros.

Overriding built-in materializations

Defining a macro with the same name as a built-in one in your root project is a deliberate override. Packages are treated differently: for safety, newer versions don't let an installed package override built-in materializations unless you opt in, which is controlled by the behaviour flag require_explicit_package_overrides_for_builtin_materializations. Dispatch (Jinja chapter 10) is the supported way for packages to plug in adapter-specific implementations.

What "compile" means for a node

Compiler.compile_node() runs in phase 7 for each selected node, and also for dbt compile, dbt show and dbt docs generate:

  1. Build the runtime context for the node (RuntimeProvider). execute is now True.dbt/context/providers.py · generate_runtime_model_context
  2. Render raw_code with that context. Introspective macros now really query the database. is_incremental() checks whether the table exists, and run_query returns rows.
  3. Inject ephemeral CTEs. If the node refs an ephemeral model, dbt compiles that model too and adds it as a CTE named __dbt__cte__<name> at the top of the query, merged into an existing with clause if there is one.
  4. Store the result in node.compiled_code and write it to target/compiled/dwlab/models/…/dimemployee.sql.

Compilation produces only the SELECT. The DDL/DML wrapper (create table … as, merge into …) is added later by the materialization, and that full SQL is written to target/run/….

target/compiled/… (the SELECT)

with src as (
    select * from "dwlab"."int"."int_dimemployee_prepared"
    order by employeenationalidalternatekey, startdate
)
, tgt as (
    select employeekey, employeenationalidalternatekey, …
    from "dwlab"."mart"."dimemployee"
)
select
    coalesce(t.employeekey, nextval('mart.dimemployee_key_seq')) as employeekey,
    …
    coalesce(t.dw_first_run_id, 42) as dw_first_run_id,
    42                               as dw_last_run_id,
    …
from src s
left join tgt t on …
where t.employeekey is null
   or t.row_hash is distinct from s.row_hash

target/run/… (what was executed)

merge into "dwlab"."mart"."dimemployee" as DBT_INTERNAL_DEST
using "dimemployee__dbt_tmp…" as DBT_INTERNAL_SOURCE
on (
    DBT_INTERNAL_SOURCE.employeenationalidalternatekey
      = DBT_INTERNAL_DEST.employeenationalidalternatekey
  and DBT_INTERNAL_SOURCE.startdate
      = DBT_INTERNAL_DEST.startdate
)
when matched then update set
    "employeekey" = DBT_INTERNAL_SOURCE."employeekey", …
when not matched then insert
    ("employeekey", …)
values
    (DBT_INTERNAL_SOURCE."employeekey", …)

The merge on the right has been shortened, and the exact text depends on your dbt-postgres version. The structure is the point: the compiled SELECT is first loaded into a temporary relation, and the merge then reads from it. Hooks don't appear in either file. They are rendered and executed separately, and you'll see their SQL in logs/dbt.log when you run with --debug.

Compile is not read-only

Because compilation uses the runtime context, dbt compile connects to the database. It runs introspective queries (is_incremental(), adapter.get_relation, adapter.get_columns_in_relation), and any run_query in your models or macros really executes. Two consequences:

  • Compiled SQL depends on the database's current state. dimemployee compiles to the incremental branch only if mart.dimemployee already exists.
  • A run_query that changes data (an insert, say) runs during dbt compile and dbt docs generate too. Changes to data belong in hooks or materializations, never in a model's body.

For pure templating checks without the database there's dbt parse, which only does pass 1. For quick experiments there are the --inline options:

$ dbt compile --inline "select * from {{ ref('int_employee_sales') }} limit 5"
$ dbt show    --inline "select {{ var('run_id') }} as run_id, '{{ target.schema }}' as s" --vars '{"run_id": 7}'
$ dbt show    --select int_dimemployee_prepared --limit 10

Rendering is lazy and per node

  • Each node renders on its own thread, with its own context. A {% set %} in one model can never be seen by another.
  • Macros render only when called. A macro with a syntax error breaks parsing (the file is parsed up front), but a macro with a logic bug only fails when some node calls it.
  • Config strings that contain Jinja, such as hooks or a schema set from env_var, are rendered when they're used, in the context of the node they belong to.

Key takeaways

  • dbt runs Jinja in a sandbox with extra tags, a strict undefined type, and a native-types mode for YAML.
  • The context is built in layers. What exists depends on what is rendering: a YAML file, a model at parse time, a model at run time, a hook or an operation.
  • Macro lookup without a prefix checks the root project first, then the node's own package, then the internal dbt and adapter macros.
  • target/compiled holds the SELECT and target/run holds what the materialization executed.
  • dbt compile queries the database. dbt parse doesn't.

Exercises

1 · Why is this undefined?

A macro used in on-run-end contains {{ this.schema }} and fails with 'this' is undefined. Explain the error and suggest what to use instead.

Answer

on-run-end renders with the macro context, which has no current node, so this doesn't exist. Loop over results and use result.node.schema / result.node.alias, or use the schemas variable.

2 · Two different compiled files

A teammate compiles dimemployee on a fresh database and on the lab database, and gets different files. Is that a bug?

Answer

No, it's expected. is_incremental() is evaluated at compile time against the real database. On a fresh database the table doesn't exist, so the full-build branch is compiled.

3 · Override safely

You want to change how every Postgres table is created, for example adding unlogged for the int layer. Which macro would you override, and where does the override go?

Answer

Override postgres__create_table_as (or default__create_table_as) in your root project's macros/. Because the root project is searched first, dispatch finds your version. (dbt-postgres also supports an unlogged config, so check whether a config already does what you need before overriding anything.)
