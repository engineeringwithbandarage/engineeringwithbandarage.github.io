Custom Generic Tests

A generic test is a parameterised query that returns failing rows. You write it once and attach it to any model, source or column from YAML. Your matches_source_metrics is already a good one. This chapter explains how dbt turns such a block into test nodes, then generalises your two singular SCD2 tests into one reusable generic test.

Anatomy, using your test

{% test matches_source_metrics(model, key_column, modified_column='modifieddate') %}

with source_metrics as (
    select source_rows, source_min_key, source_max_key, source_max_modified
    from {{ source('audit', 'etl_table_load') }}
    where run_id = {{ var('run_id') }}
      and stg_table = '{{ model.identifier }}'
),
stg_metrics as (
    select count(*) as stg_rows, min({{ key_column }})::text as stg_min_key, …
    from {{ model }}
)
select '{{ model.identifier }}' as stg_table, s.*, t.*
from stg_metrics t
left join source_metrics s on true
where s.source_rows is null or s.source_rows <> t.stg_rows or …

{% endtest %}
  • {% test name(...) %} is stored as the macro test_name.
  • model is filled in by dbt with the relation being tested: a model, a source table (as here), a seed or a snapshot.
  • column_name is filled in when the test is listed under a column. Your test sits at table level and takes key_column as an ordinary argument instead.
  • The query returns failing rows. No rows means pass. Your design (one row when anything differs) reads well in a failure report.

Attaching tests in YAML

- name: employee
  data_tests:
    - matches_source_metrics:
        arguments:
          key_column: businessentityid
        config:
          tags: [reconcile]
          severity: error

Your project uses the newer form that separates arguments: from config:. Older projects put arguments directly under the test name (matches_source_metrics: {key_column: businessentityid}), and newer releases warn about that form. Use the separated form, as you already do.

Test configs

ConfigEffect
severity: warn | errorWhether failures make the command fail
error_if / warn_ifThresholds on the failure count, e.g. error_if: ">10", warn_if: ">0"
whereFilters the tested relation: dbt replaces {{ model }} with a filtered subquery
limitCaps the failing rows returned
fail_calcHow failures are counted (default count(*))
store_failures, store_failures_asSave failing rows to a table or view in an audit schema
tags, enabled, name, aliasSelection, switching off, readable names

A test can also set its own defaults with {{ config(severity='warn') }} inside the {% test %} block. YAML config still wins.

Under the hood: what where does

With config: {where: "status = 'Current'"}, dbt doesn't edit your SQL. It changes what {{ model }} renders to: instead of "dwlab"."mart"."dimemployee" you get (select * from "dwlab"."mart"."dimemployee" where status = 'Current') dbt_subquery. That's why a where config only works with tests that use {{ model }} in a FROM clause.

Generalising your SCD2 tests

Your two singular tests check the same rules that any SCD2 dimension needs. Combined into one generic test, they can be reused for every future dimension:

{#
  SCD2 rules for a dimension:
    1. exactly one current version per business key
    2. each version ends where the next one starts; only the last version is open
#}
{% test scd2_integrity(model, business_key, start_column='startdate', end_column='enddate',
                       status_column='status', current_value='Current') %}

with ordered as (
    select
        {{ business_key }}                              as bk,
        {{ start_column }}                              as start_at,
        {{ end_column }}                                as end_at,
        {{ status_column }} = '{{ current_value }}'     as is_current,
        lead({{ start_column }}) over (partition by {{ business_key }} order by {{ start_column }}) as next_start
    from {{ model }}
),

current_count as (
    select bk, count(*) filter (where is_current) as n_current
    from ordered
    group by bk
)

select 'not exactly one current version' as rule, bk, null::text as detail
from current_count
where n_current <> 1

union all

select 'gap or overlap between versions', bk, start_at::text || ' → ' || coalesce(end_at::text, 'open')
from ordered
where end_at is distinct from next_start
   or (end_at is null) <> coalesce(is_current, false)

{% endtest %}
  - name: dimemployee
    data_tests:
      - scd2_integrity:
          arguments:
            business_key: employeenationalidalternatekey
          config:
            severity: error
            store_failures: true

One generic test now replaces both singular files, gives each failure a rule label, and with store_failures leaves the offending rows in a table you can query after a failed run.

Overriding the wrapper

Every test query is wrapped by get_test_sql (internals ch. 07), which is dispatched. If you need to change how failures are counted across the project (counting distinct business keys rather than rows, say), use fail_calc for individual tests. Override default__get_test_sql only for a global rule.

Unit tests (1.8+): a different tool

Data tests check data that's already in the warehouse. Unit tests check model logic against fixed inputs, before anything is built. They're defined in YAML with given rows for each ref/source and an expect block. For tricky logic such as the Type 2 rules in int_employee_department_versions, a unit test with three or four input rows is the fastest safety net you can get.

unit_tests:
  - name: versions_start_at_hire_then_department_change
    model: int_employee_department_versions
    given:
      - input: source('stg', 'employee')
        rows:
          - {businessentityid: 1, hiredate: '2010-01-01'}
      - input: source('stg', 'employeedepartmenthistory')
        rows:
          - {businessentityid: 1, departmentid: 10, startdate: '2010-02-01'}
          - {businessentityid: 1, departmentid: 20, startdate: '2015-06-01'}
      - input: source('stg', 'department')
        rows:
          - {departmentid: 10, name: 'Engineering'}
          - {departmentid: 20, name: 'Sales'}
    expect:
      rows:
        - {businessentityid: 1, version_no: 1, departmentname: 'Engineering', startdate: '2010-01-01', enddate: '2015-06-01', is_current: false}
        - {businessentityid: 1, version_no: 2, departmentname: 'Sales',       startdate: '2015-06-01', enddate: null,         is_current: true}

Key takeaways

  • {% test x(model, …) %} becomes the macro test_x, and each YAML use becomes a test node.
  • Return failing rows. dbt counts them and compares the count with severity/warn_if/error_if.
  • where works by changing what {{ model }} renders to.
  • Turn repeated singular tests into generic ones, and use unit tests to check logic.
