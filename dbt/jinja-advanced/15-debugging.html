Debugging Jinja

Jinja bugs feel hard because the code that's wrong (the template) isn't the code that fails (the SQL), and the two run at different times. A systematic approach makes them routine: first find the phase, then look at the output, then narrow the input.

~25 min read

Step 2: look at the output

$ dbt compile -s dimemployee --vars '{"run_id": 42}'      # then open target/compiled/…/dimemployee.sql
$ dbt --debug run -s dimemployee --vars '{"run_id": 42}'   # every statement, incl. hooks, in logs/dbt.log
$ dbt --log-format json run -s dimemployee …              # machine-readable events (great in Airflow)
$ dbt compile --inline "{{ scd_hash_columns(graph.nodes['model.dwlab.int_dimemployee_prepared']) }}"
$ dbt parse --no-partial-parse                            # rule out stale caches

Step 3: log values

{{ log('is_incremental=' ~ is_incremental() ~ ' execute=' ~ execute, info=True) }}

{# dump a structure as readable JSON #}
{{ log(tojson(model.config, sort_keys=true), info=True) }}

{# log only while executing (avoids duplicated parse-time lines) #}
{% if execute %}{{ log('cols: ' ~ cols | join(', '), info=True) }}{% endif %}

{# inspect an agate table #}
{% if execute %}{% do run_query('select * from ' ~ this ~ ' limit 5').print_table() %}{% endif %}

Why you see the log line twice

A log() in a model runs in both renders (parse and execute), unless partial parsing skipped the parse. Wrap debug logs in {% if execute %}, or include execute in the message.

Step 4: make errors explicit

{% if unique_key is none %}
  {{ exceptions.raise_compiler_error(
       "scd2 (" ~ model.unique_id ~ "): config 'unique_key' is required. "
       ~ "Set it with config(unique_key='...').") }}
{% endif %}

{% if (cols | length) > 60 %}
  {{ exceptions.warn(model.name ~ ": hashing " ~ cols | length ~ " columns — is that intended?") }}
{% endif %}

A good error message says which node, what is wrong and how to fix it. It saves time for whoever reads the Airflow log at 3 a.m.

Step 5: interactive debugging

For hard cases, dbt's debug() context function opens a Python debugger in the middle of rendering. It only works when the environment variable DBT_MACRO_DEBUGGING is set and you're running in an interactive terminal (so not inside Airflow):

{% macro scd_hash_columns(node=none) %}
    {%- set node = node or model -%}
    {{ debug() }}          {# drops into ipdb/pdb with the macro's locals #}
    …
{% endmacro %}
$ DBT_MACRO_DEBUGGING=1 dbt compile -s int_dimemployee_prepared

Nested curlies

The most common beginner mistake survives into advanced code: {{ config(post_hook=record_dim_stats({{ var('run_id') }})) }}. Inside {{ … }} you're already writing Jinja expressions, so use var('run_id') directly. The only place nested curlies belong is inside a string that will be rendered later, such as a hook.

Debugging inside Airflow

  • Task logs contain dbt's console output. Add --log-level debug to a single task's bash_command temporarily to get every SQL statement in the Airflow log.
  • logs/dbt.log in the project folder on the worker keeps the debug-level log of the latest runs, even when the console was at info level.
  • To reproduce a failure, copy the exact command from the task log, including --vars, and run it inside the worker container with docker exec.

Key takeaways

  • Find the phase first: config/parse, runtime render or database execution.
  • Look at the generated SQL (target/compiled, target/run, --debug) before reading templates.
  • Log under execute, dump structures with tojson, and raise errors that explain the fix.
  • debug() with DBT_MACRO_DEBUGGING gives you a real debugger for the hard cases.

Exercises

1 · Diagnose

After adding a macro, dbt ls fails with 'None' has no attribute 'rows', but only for one model. What's your first action?

Answer

Because dbt ls only parses, this is a parse-time failure. Find the run_query(...).rows (or load_result) in that model or its macros and guard it with execute.

2 · The extra column

The compiled SQL of a model has None as dw_expired_run_id. Where does that come from?

Answer

A Jinja expression evaluated to none and was printed. For example, a variable was set only in one branch of an if. Render null explicitly, or make sure every path sets the variable.
