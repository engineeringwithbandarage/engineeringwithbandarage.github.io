How dbt Renders Jinja

The key idea for the whole tutorial is that Jinja is a text generator that runs before SQL exists. It doesn't know what SQL is. Its job is to produce a string, which dbt then sends to PostgreSQL. Advanced dbt Jinja is mostly a matter of controlling when that string is generated, with which context, and what it contains.

~25 min read Builds on: Internals ch. 01, 04, 06

Jinja produces text, SQL runs later

Look at this line from your dimemployee.sql:

coalesce(t.dw_first_run_id, {{ var('run_id') }}) as dw_first_run_id,

PostgreSQL never sees var('run_id'). Before any SQL runs, Jinja replaces {{ var('run_id') }} with the characters 42. As far as the database knows, the literal number 42 was always in the query. Two consequences follow:

  1. Jinja can't read your data as part of the query. It can only run a separate query first (with run_query) and paste the result in as text.
  2. Jinja errors and SQL errors happen at different times. A Jinja error stops dbt before the database is contacted. A SQL error comes back from PostgreSQL afterwards, about text that Jinja produced. When debugging, first work out which of the two you have.

The two passes, again, with consequences

As the internals tutorial explained, a model's Jinja is rendered first during parsing (execute = False) and again during execution (execute = True). Here is what that means for writing Jinja:

RuleWhy
Every ref and source must run during parsingThat's when dependencies are recorded. A ref inside {% if execute %} never becomes a DAG edge
Anything that queries the database must be behind {% if execute %}During parsing, query results are None
config() must be callable during parsingThe parser reads it to build the node. Configs computed from a query result won't work
Parse-time output is thrown awaySo it doesn't matter what SQL the parse pass produces, only that it doesn't crash

The last rule matters more than it looks. During parsing, a guarded block might produce invalid SQL, and that's fine. Nobody runs the parse output.

Output vs. return value

Jinja has two ways of getting something out of a piece of code, and mixing them up causes many subtle bugs:

  • Output: text written into the template. {{ expr }} writes text, and a macro's body writes text.
  • Return value: a Python object handed back to the caller. Plain Jinja macros always return their output as a string. dbt adds {{ return(x) }}, which returns the object x unchanged: a list, a dict, a number, a Relation.

Returns text

{% macro key_columns() %}
  employeenationalidalternatekey, startdate
{% endmacro %}

{% set cols = key_columns() %}
{# cols is a string with spaces/newlines #}
{{ cols | length }}  {# counts characters! #}

Returns an object

{% macro key_columns() %}
  {{ return(['employeenationalidalternatekey', 'startdate']) }}
{% endmacro %}

{% set cols = key_columns() %}
{# cols is a real list #}
{{ cols | length }}  {# 2 #}
{{ cols | join(', ') }}

Under the hood

return() works by raising a special exception (MacroReturn) that dbt's macro wrapper catches, taking the value out of it. That has two consequences. Code after return() in the same macro never runs, and any text the macro wrote before return() is discarded.

Compiled vs. run output

For every model there are two files to look at:

  • target/compiled/dwlab/models/…/x.sql: the model's Jinja rendered into a SELECT.
  • target/run/dwlab/models/…/x.sql: the DDL/DML the materialization wrapped around it (create table … as, merge).

Hooks aren't in either file. To see hook SQL, run with --debug and read logs/dbt.log.

Seeing what Jinja produced

# 1. Render one model (connects to the DB; runs introspection)
$ dbt compile --select dimemployee --vars '{"run_id": 42}'

# 2. Render an ad-hoc expression
$ dbt compile --inline "{{ record_dim_stats(scd2=true) }}" --vars '{"run_id": 42}'

# 3. Render and execute a SELECT, show rows
$ dbt show --inline "select '{{ target.name }}' as t, {{ var('run_id') }} as r" --vars '{"run_id": 7}'

# 4. Print from inside a template while it renders
{{ log("this = " ~ this ~ ", incremental = " ~ is_incremental(), info=True) }}

Inline compile of a macro that uses this

dbt compile --inline "{{ record_dim_stats() }}" renders the macro in the context of an inline SQL node, so this points at that temporary node rather than a dimension. That's fine for checking syntax, but compile a real model when the values matter.

A mental model to keep

Key takeaways

  • Jinja generates text before any SQL runs. It can't see data unless it runs its own query first.
  • Models render twice. Refs must run during parsing, and queries must be guarded by execute.
  • Macros return their output as a string unless you use return().
  • target/compiled holds the SELECT, target/run holds the wrapper, and hook SQL is in the debug log.

Exercises

1 · Jinja or SQL error?

Classify each: (a) column "dw_first_run_id" does not exist; (b) 'record_dims_stats' is undefined; (c) syntax error at or near ")"; (d) expected token 'end of statement block', got 'scd2'.

Answer

(a) SQL, reported by PostgreSQL. (b) Jinja, a misspelled macro. (c) SQL, very often caused by Jinja output such as a trailing comma from a loop. (d) Jinja, a malformed tag, for example a missing = or (.

2 · Fix the length

A macro hash_cols() writes a, b, c. A model does {% for c in hash_cols().split(',') %} and gets ' b' with a leading space. Give two fixes.

Answer

Make the macro return(['a','b','c']), which is best, or strip each item: {% for c in hash_cols().split(',') | map('trim') %}.
