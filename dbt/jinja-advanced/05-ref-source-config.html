ref, source & config Internals

These three functions are the core of every model. They look like simple substitutions, but each one has a parse-time behaviour, a run-time behaviour and a return type you can program against. This chapter ends by tracing is_incremental() through your dimemployee, line by line.

ref()

Signatures

{{ ref('int_dimemployee_prepared') }}               {# model in any package (root first) #}
{{ ref('dwlab', 'int_dimemployee_prepared') }}      {# explicit package #}
{{ ref('dim_customer', version=2) }}                {# model versions; also v=2 #}

Two behaviours

Parse timeRun time
Side effectAppends to node.refs, which later becomes a DAG edgeChecks that the target was declared during parsing
ReturnsA placeholder relationThe real Relation, built from the target node's database/schema/alias
Fails whenTarget doesn't exist or is disabledThe ref wasn't seen during parsing ("dbt was unable to infer all dependencies")

The run-time check catches the case from chapter 01: a ref that only executes inside {% if execute %}. dbt stops with an error suggesting a -- depends_on: comment, which is what you should add.

What the Relation knows

{% set r = ref('int_dimemployee_prepared') %}
{{ r }}                       "dwlab"."int"."int_dimemployee_prepared"
{{ r.schema }}                int
{{ r.identifier }}            int_dimemployee_prepared
{{ r.is_view }} / {{ r.is_table }}    (type known after resolution from the manifest)
{{ r.include(database=false, schema=false) }}   "int_dimemployee_prepared"
{{ r.incorporate(path={'schema': 'int_backup'}) }}   a copy pointing elsewhere

Relations, not strings

Pass relations to macros, not names. A macro that receives ref('x') can read its schema, quote it correctly and hand it to adapter.get_columns_in_relation. A macro that receives the string 'int.x' has to guess all of that.

source()

{{ source('stg', 'employee') }}        →  "dwlab"."stg"."employee"

Each source table becomes a node (source.dwlab.stg.employee) whose relation comes from the YAML (schema: stg, an optional identifier: and database:). Parse-time recording works exactly as it does for ref. Because sources are nodes, they can have tests (your reconcile tests), freshness checks and descriptions, and source:stg+ selects everything downstream of them.

Your sources.yml also declares the audit tables as a source. That's why rpt_load_summary and matches_source_metrics can use {{ source('audit', 'etl_table_load') }} instead of hard-coding audit.etl_table_load. Chapter 17 suggests doing the same in record_dim_stats.

config()

Inline config is read at parse time

{{ config(...) }} renders to nothing. Its job is the side effect during parsing. Keyword values must therefore be computable during parsing:

✓ Works

{{ config(
    materialized = 'table' if target.name == 'dev' else 'incremental',
    schema       = var('mart_schema', 'mart'),
    tags         = ['dimension', 'scd2'],
) }}

✗ Doesn't work

{% set n = run_query('select count(*) …') %}
{{ config(
    materialized = 'table' if n … else 'view'
) }}
{# n is None during parsing #}

Merging across levels

Reading config back

Elsewhere in the template, config.get('key') reads the final, merged value. During parsing the merge isn't finished yet, so don't make important parse-time decisions based on config.get inside model files.

is_incremental(), traced

This is the built-in macro (lightly formatted):

{% macro is_incremental() %}
    {#-- do not run introspective queries in parsing #}
    {% if not execute %}
        {{ return(False) }}
    {% else %}
        {% set relation = adapter.get_relation(this.database, this.schema, this.table) %}
        {{ return(relation is not none
                  and relation.type == 'table'
                  and model.config.materialized == 'incremental'
                  and not should_full_refresh()) }}
    {% endif %}
{% endmacro %}

Full refresh renumbers your surrogate keys

On --full-refresh, the non-incremental branch calls nextval() for every row, and the existing sequence keeps counting from where it was. Every employeekey changes, which breaks any fact table that already uses the old keys. If facts will reference this dimension, protect it with full_refresh=false in the model's config. dbt then ignores --full-refresh for that model.

{{ config(
    materialized='incremental',
    incremental_strategy='merge',
    unique_key=['employeenationalidalternatekey', 'startdate'],
    on_schema_change='fail',
    full_refresh=false,          {# ← --full-refresh is ignored for this model #}
    …
) }}

Key takeaways

  • ref/source record dependencies at parse time and return Relations at run time. Pass Relations around, not strings.
  • config() runs at parse time, so its values must not depend on queries.
  • Tags and hooks combine across levels, while most other keys override.
  • is_incremental() is false during parsing, on the first run and on full refresh. Think about what each branch means for your keys.

2 · Which branch?

Someone runs dbt compile -s dimemployee after dropping mart.dimemployee by hand. Which branch is in target/compiled, and what happens at the next scheduled run?

Answer

The compiled file has the full-build branch, because the relation doesn't exist. The next run also takes that branch: the table is recreated and every row gets a new key from the sequence, which keeps counting.
