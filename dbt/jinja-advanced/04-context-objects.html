Chapter 04 · The dbt Context

Built-in Context Objects

dbt puts several dozen names into every template. This chapter covers the ones you'll actually use in advanced work: what each one is, when it's available, and an example from the dwlab project for each.

~35 min read Reference: Appendix A

this: the current relation

this is a Relation object for the node being rendered. It's available in models, snapshots and their hooks, and in macros called from them.

{{ this }}                       →  "dwlab"."mart"."dimemployee"
{{ this.database }}              →  dwlab
{{ this.schema }}                →  mart
{{ this.identifier }}            →  dimemployee      (also: this.name, this.table)
{{ this.include(database=false) }}  →  "mart"."dimemployee"
{{ this.type }}                  →  table / view / none (none until known)

Your pre-hook create sequence if not exists {{ this.schema }}.dimemployee_key_seq uses this.schema, so the sequence always lives next to the table, whatever generate_schema_name decides.

model: the current node as a dictionary

model is the node from the manifest, as a dict. It's useful whenever a macro needs to know about the model that called it.

{{ model.unique_id }}                     model.dwlab.dimemployee
{{ model.name }}                          dimemployee
{{ model.resource_type }}                 model
{{ model.original_file_path }}            models/mart/dimemployee.sql
{{ model.fqn }}                           ['dwlab', 'mart', 'dimemployee']
{{ model.config.materialized }}           incremental
{{ model.config.unique_key }}             ['employeenationalidalternatekey', 'startdate']
{{ model.config.get('meta', {}) }}        {}
{{ model.columns.keys() | list }}         columns documented in YAML
{{ model.depends_on.nodes }}              ['model.dwlab.int_dimemployee_prepared']

model means something else inside a generic test

In a {% test %} block, model is the argument holding the relation under test (see your matches_source_metrics, which uses {{ model }} and {{ model.identifier }}). That argument shadows the context variable of the same name.

config: read config from a template

{{ config(materialized='incremental') }}          {# set (models) — parse-time #}
{{ config.get('unique_key') }}                    {# read, none if missing #}
{{ config.get('scd_hash_column', 'row_hash') }}   {# read with default #}
{{ config.require('unique_key') }}                {# read, compile error if missing #}

config.get and config.require are the standard way for materializations and macros to read custom settings. That's how you'll add new config keys in chapters 12 and 18.

Custom config keys

Newer dbt versions warn about unrecognised top-level config keys. Put your own settings under meta (config(meta={'scd': {...}})) and read them with config.get('meta'). That's the forward-compatible place for them.

var and env_var

{{ var('run_id') }}                       {# required; error if missing everywhere #}
{{ var('cutoff_days', 30) }}              {# with default #}
{{ env_var('DBT_PG_USER') }}              {# string; error if unset #}
{{ env_var('DWLAB_FLAG', 'false') }}      {# string default #}
{% if var('run_id') == 0 and target.name == 'prod' %}
  {{ exceptions.raise_compiler_error("run_id must be passed with --vars in prod") }}
{% endif %}

Adding '{{ invocation_id }}' as dw_dbt_invocation_id to your audit columns links each row to a specific run_results.json.

modules: the allowed Python

{{ modules.datetime.date.today() }}
{{ (modules.datetime.datetime.utcnow() - modules.datetime.timedelta(days=7)).isoformat() }}
{{ modules.re.sub('[^a-z0-9_]', '_', 'Sales & Marketing' | lower) }}   → sales___marketing
{{ modules.pytz.utc }}
{{ modules.itertools.product(['a','b'], [1,2]) | list }}

Only datetime, pytz, re and itertools are available (newer versions add a few more). os, subprocess and file access are deliberately missing.

Key takeaways

  • this and ref() return Relation objects, with parts you can read and methods you can call.
  • model is the node as a dict, but in tests model is the relation under test.
  • config.get/require read settings. Custom settings go under meta.
  • adapter and api are your interface to the database from Jinja.
  • Run metadata (invocation_id, run_started_at, flags) makes audit columns traceable.

Exercises

1 · Audit column

Add a column to dimemployee that records the dbt invocation and the date (in Sri Lanka time) when the row was last written.

Answer 
'{{ invocation_id }}'::uuid as dw_last_invocation_id,
'{{ run_started_at.astimezone(modules.pytz.timezone("Asia/Colombo")).date() }}'::date as dw_last_run_date,

Because on_schema_change='fail' is set, adding columns needs a --full-refresh, or a change to that config.

2 · Guard the default run_id

Write a guard at the top of dimemployee.sql that fails during execution (not parsing) if run_id is 0 and the target is not dev.

Answer 
{% if execute and var('run_id') == 0 and target.name != 'dev' %}
  {{ exceptions.raise_compiler_error("dimemployee: pass --vars '{run_id: N}' (got 0)") }}
{% endif %}
