Compile-time Queries

Sometimes the SQL you need depends on the data: one column per department, a list of tables to union, the last loaded run. Jinja can't see data, but it can run a query before generating the SQL and use the results as text. This chapter covers the tools for that and the rules that keep it safe.

~30 min read Lab: headcount pivot by department

run_query

{% macro run_query(sql) %}
  {% call statement("run_query_statement", fetch_result=true, auto_begin=false) %}
    {{ sql }}
  {% endcall %}
  {% do return(load_result("run_query_statement").table) %}
{% endmacro %}

It runs the SQL on the current node's connection and returns an agate.Table. During parsing, the statement doesn't execute and the return value is None, so every use needs an {% if execute %} guard.

Converting to plain structures

{% for r in t.rows %}
  {% do records.append(dict(zip(t.column_names, r))) %}
{% endfor %}

statement + load_result

run_query covers most needs. Use statement directly when you need the database's response (row counts, status) or more control over transactions:

{% call statement('expire_stale', fetch_result=false, auto_begin=true) %}
    update {{ this }} set status = null
    where status = 'Current' and enddate is not null
{% endcall %}

{% set res = load_result('expire_stale') %}
{{ log("expired: " ~ res['response'].rows_affected, info=True) }}   {# AdapterResponse #}
{# res['data'] → rows (when fetch_result=true), res['table'] → agate.Table #}

Name each statement uniquely within a node. load_result looks results up by name, and 'main' is reserved for the materialization's main query.

Worked example: a headcount pivot

The report should have one column per department with the current headcount, broken down by sales territory. Since the set of departments comes from the data, the columns have to be generated:

{{ config(materialized='table') }}

{%- set dept_sql -%}
    select distinct departmentname
    from {{ ref('dimemployee') }}
    where status = 'Current'
    order by 1
{%- endset -%}

{%- if execute -%}
    {%- set departments = run_query(dept_sql).columns[0].values() -%}
{%- else -%}
    {%- set departments = [] -%}
{%- endif %}

select
    e.salesterritorykey,
    t.salesterritoryregion,
{%- for d in departments %}
    count(*) filter (where e.departmentname = '{{ d | replace("'", "''") }}')
        as {{ adapter.quote(modules.re.sub('[^a-z0-9]+', '_', d | lower).strip('_')) }},
{%- endfor %}
    count(*) as total_headcount
from {{ ref('dimemployee') }} e
join {{ ref('dimsalesterritory') }} t using (salesterritorykey)
where e.status = 'Current'
group by 1, 2

Notice four details:

  • Refs outside the guard. ref('dimemployee') appears in the main SQL, which runs during parsing, so the dependency is recorded even though the query inside the guard doesn't run then.
  • An empty list during parsing. The parse-time render produces a valid query with no department columns. Nobody runs it, but it doesn't crash either.
  • Escaped values. Department names go inside SQL quotes, so single quotes are doubled.
  • Safe identifiers. "Research and Development" becomes "research_and_development".

The data is read at compile time, not at run time

The list of departments is read when this model compiles, not when the report runs. In one dbt build, dimemployee is built first (it's a parent), so the list is current. If you compile the report on its own, the list reflects whatever dimemployee contained at that moment.

Rules for compile-time queries

  1. Always guard with execute, or use a helper that does it for you.
  2. Only read. Model bodies are also rendered by dbt compile, dbt docs generate and dbt show. Writes belong in hooks, operations or materializations.
  3. Keep them small and few. Every query adds a round trip to every compile of that model, including the ones you didn't intend, like docs generate.
  4. Make the empty case valid. A first run on an empty database, a parse-time render, or a filter that matches nothing should all still give correct SQL.
  5. Escape values and quote identifiers every time data becomes SQL text.

Key takeaways

  • run_query returns an agate.Table. Use .columns[...], .rows and .column_names, and watch out for Decimal and None.
  • statement + load_result give access to the database response and transaction control.
  • Keep refs outside guards, give the parse pass an empty result, escape values and quote identifiers.
  • Compile-time queries see the data as it was at compile time.

Exercises

1 · High-water mark

In an incremental model, get the highest dw_last_run_id already in {{ this }} and use it in a filter. What should the value be on the first run?

Answer 
{% set hwm = 0 %}
{% if execute and is_incremental() %}
  {% set hwm = run_query("select coalesce(max(dw_last_run_id), 0) from " ~ this).columns[0].values()[0] | int %}
{% endif %}
… where source_run_id > {{ hwm }}

The value is 0 on the first run and during parsing. The | int converts the Decimal.

2 · Union all stg tables of a kind

Query information_schema.tables for every table in stg whose name starts with business, and generate a union all of their row counts.

Answer 
{% set q %}
  select table_name from information_schema.tables
  where table_schema = 'stg' and table_name like 'business%' order by 1
{% endset %}
{% set names = run_query(q).columns[0].values() if execute else [] %}
{% for n in names %}
select '{{ n }}' as tbl, count(*) as n from stg.{{ adapter.quote(n) }}
{% if not loop.last %}union all{% endif %}
{% else %}
select null::text as tbl, null::bigint as n where false
{% endfor %}

Tables found this way don't create DAG edges. For tables dbt manages, use dbt_utils.get_relations_by_pattern or declared sources instead.
