Packages

A dbt package is just another dbt project, with its own macros, tests and models, installed into yours. Reading good packages is one of the fastest ways to learn advanced Jinja, and moving your own macros into a package is how you reuse them across projects.

~30 min read Lab: a dwlab_macros package

Installing packages

packages:
  - package: dbt-labs/dbt_utils                 # dbt Hub
    version: [">=1.3.0", "<2.0.0"]
  - package: dbt-labs/codegen
    version: [">=0.13.0", "<1.0.0"]
  - git: "https://github.com/your-org/dwlab_macros.git"   # git
    revision: v0.3.1                            # tag, branch or full commit sha
  - local: ../dwlab_macros                      # a folder on disk (development)
$ dbt deps          # resolves versions, writes package-lock.yml, installs into dbt_packages/
  • package-lock.yml records the exact versions resolved. Commit it so every environment installs the same code.
  • Version ranges on Hub packages let dbt resolve shared dependencies. Git packages can only be pinned to a revision.
  • In your Docker setup, run dbt deps when building the image, or as an Airflow task before the first dbt step. Your Dockerfile already installs git for git-hosted packages.

Other packages worth knowing

  • dbt_expectations: a large library of data tests modelled on Great Expectations (distributions, regex matches, row-count comparisons). The original repository is archived, and the maintained fork is published by Metaplane, so check which one the Hub currently points to.
  • codegen: run-operations that write dbt code for you. For example, dbt run-operation generate_source --args '{schema_name: stg, generate_columns: true}' prints a complete sources.yml with column lists, and generate_model_yaml does the same for models.
  • dbt_project_evaluator: checks your project against best-practice rules (test coverage, naming, model fan-out), implemented with the graph techniques from chapter 14.
  • audit_helper: compares two relations row by row and column by column. It's ideal for validating a refactor like the row-hash change in chapter 08.

Reading package source

After dbt deps, the full source sits in dbt_packages/<name>/macros/. Reading dbt_utils teaches several patterns you've met in this tutorial, used in production code:

$ grep -rn "adapter.dispatch" dbt_packages/dbt_utils/macros | head         # ch. 10: every public macro dispatches
$ grep -rn "if not execute" dbt_packages/dbt_utils/macros | head          # ch. 07: execute guards
$ sed -n '1,60p' dbt_packages/dbt_utils/macros/sql/star.sql               # introspection + safe parse-time output
$ sed -n '1,40p' dbt_packages/dbt_utils/macros/sql/generate_surrogate_key.sql

Building your own package

The macros from this tutorial (row_hash, scd2_key_join, audit_columns, scd2_integrity, the scd2 materialization, the operations) make a natural package, dwlab_macros:

dwlab_macros/
├── dbt_project.yml
├── README.md                   what each macro does, configs it reads
├── macros/
│   ├── hashing/row_hash.sql            dispatched: default__ / postgres__
│   ├── scd2/scd2_key_join.sql
│   ├── scd2/audit_columns.sql
│   ├── materializations/scd2.sql
│   ├── tests/test_scd2_integrity.sql
│   ├── ops/purge_audit.sql
│   └── macros.yml                      documentation of every macro
└── integration_tests/          a small dbt project that installs the package via `local: ../`
    ├── dbt_project.yml               and has models + tests that exercise each macro
    ├── seeds/
    └── models/
name: dwlab_macros
version: "0.3.1"
config-version: 2
require-dbt-version: [">=1.8.0", "<2.0.0"]
macro-paths: ["macros"]

Rules for package macros

  1. Always dispatch with your namespace: adapter.dispatch('row_hash', 'dwlab_macros'), so users can override you (ch. 10).
  2. Use your own name for internal calls, as in dwlab_macros.scd2_key_join(...), so a user's macro with the same name doesn't silently replace yours.
  3. Read settings through var with defaults, scoped by the package name in the user's dbt_project.yml (vars: {dwlab_macros: {audit_schema: audit}}).
  4. Don't hard-code schemas like audit.. Take them from vars or source().
  5. Version with tags (v0.3.1) and pin them in consumers' packages.yml.
  6. Test with an integration project in CI on every change, against a real PostgreSQL.

Materializations from packages

Newer dbt versions only let a package provide new materializations. Packages can't silently replace built-in ones like table or incremental without the root project explicitly allowing it. A custom name such as scd2 is unaffected.

Key takeaways

  • Pin package versions and commit package-lock.yml. Run dbt deps as part of your build.
  • dbt_utils, codegen, audit_helper and dbt_project_evaluator cover a lot of what you'd otherwise write yourself.
  • Package source is excellent learning material: look for dispatch and execute guards.
  • A good internal package dispatches with its own namespace, calls its own macros by full name, reads vars, and has integration tests.

Exercises

1 · Replace the hash

Replace the md5(concat_ws(...)) in int_dimemployee_prepared with dbt_utils. What exactly changes in the data?

Answer

{{ dbt_utils.generate_surrogate_key([...columns...]) }} as row_hash. Every hash value changes (different separator and null handling), so the next run updates every row once, as chapter 08 explained. After that, null-position changes are detected correctly.

2 · Generate YAML

Which codegen operation would draft documentation for all of dimemployee's columns?

Answer

dbt run-operation generate_model_yaml --args '{model_names: [dimemployee]}'. It introspects the built table and prints YAML with every column, ready to paste and fill in descriptions.
