Data Types & Scope

Every Jinja value is a Python object, but Jinja's scoping rules aren't Python's. That's the cause of the classic "my counter is always zero" bug. This chapter covers how to build and change data structures, where variables are visible, and how to convert between strings, booleans, numbers and structures without surprises.

Changing lists and dicts: do

{{ }} prints its result, so {{ cols.append('x') }} would write None into your SQL. {% do %} evaluates an expression and discards the result, which makes it the tool for side effects:

{% set cols = [] %}
{% do cols.append('firstname') %}
{% do cols.extend(['lastname', 'title']) %}

{% set meta = {'scd2': true} %}
{% do meta.update({'business_key': 'employeenationalidalternatekey'}) %}

{% set unique = cols | unique | list %}
{% set sorted_cols = cols | sort %}

Scope rules

Rule 1: for loops have their own scope

A {% set %} inside a loop creates a new variable that only exists for that iteration. The variable outside the loop is never changed:

✗ Always prints 0

{% set total = 0 %}
{% for c in cols %}
  {% set total = total + 1 %}
{% endfor %}
{{ total }}   {# 0 #}

✓ namespace() survives the loop

{% set ns = namespace(total=0, names=[]) %}
{% for c in cols %}
  {% set ns.total = ns.total + 1 %}
  {% do ns.names.append(c | upper) %}
{% endfor %}
{{ ns.total }}   {# 3 #}

Assigning to an attribute (ns.total = …) changes an existing object instead of creating a variable, so the change is still there after the loop. Appending to a list declared outside the loop also works, for the same reason.

Rule 2: if blocks don't have their own scope

{% if is_incremental() %}
  {% set mode = 'merge' %}
{% else %}
  {% set mode = 'full' %}
{% endif %}
-- mode: {{ mode }}

Rule 3: macros only see their arguments and the global context

A macro can't see variables set in the model that calls it. It sees its own arguments plus the global context: this, var, adapter, other macros and so on. Note that this inside a macro refers to the calling node. That's why your record_dim_stats can use {{ this }} without taking it as an argument.

{% set business_key = 'employeenationalidalternatekey' %}
{{ scd2_close_versions(business_key) }}   {# the macro can't see business_key otherwise #}

Rule 4: set at the top of a file is file-level only

Each model renders with its own context. Nothing you set in one model is visible in another, or in another render of the same model, since parse and execute are separate renders.

Block set: capturing text

{% set name %}…{% endset %} renders the body and stores the resulting string. This is the cleanest way to hold a SQL snippet you'll run with run_query or use more than once:

{% set current_versions_sql %}
    select employeenationalidalternatekey, employeekey
    from {{ this }}
    where status = 'Current'
{% endset %}

{% set q | trim %}select count(*) from {{ this }}{% endset %}   {# filter applied to the captured text #}

dbt's YAML filters

In .yml config values (rendered with native types), use dbt's filters as_bool, as_number, as_native and as_text to choose the resulting type, as in +enabled: "{{ env_var('ENABLE_RPT', 'true') | as_bool }}". Without them, the value stays a string and enabled: 'false' is still enabled.

Key takeaways

  • Use {% do %} for changes like append and update. {{ }} would print None.
  • Loops have their own scope, so use namespace() or change an outer object. if blocks don't have their own scope.
  • Macros only see their arguments and the global context. Pass values in explicitly.
  • Block set captures rendered text, which is ideal for SQL snippets.
  • Never trust string truthiness. Convert env_var values explicitly.

Exercises

1 · Collect columns per type

Given columns = adapter.get_columns_in_relation(ref('int_dimemployee_prepared')), build a dict mapping each data type to a list of column names.

Answer 
{% set by_type = {} %}
{% for c in columns %}
  {% do by_type.setdefault(c.dtype, []).append(c.name) %}
{% endfor %}
{{ log(tojson(by_type), info=True) }}

This works because the dict exists outside the loop and is only changed in place, never reassigned. Wrap it in {% if execute %}, since column introspection needs the database.

2 · Why is the flag ignored?

An Airflow task sets DWLAB_SKIP_STATS=false, and the model checks {% if env_var('DWLAB_SKIP_STATS', '') %}. The stats are skipped anyway. Explain.

Answer

'false' is a non-empty string, so it's truthy. Compare explicitly: env_var('DWLAB_SKIP_STATS', 'false') | lower == 'true'.
