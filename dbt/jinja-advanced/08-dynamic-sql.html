The hidden flaw in concat_ws hashes

Your int_dimemployee_prepared computes:

md5(concat_ws('|',
    parentemployeenationalidalternatekey, salesterritorykey, firstname, lastname, middlename, …,
    departmentname, enddate, status)) as row_hash

PostgreSQL's concat_ws skips NULL arguments entirely, separator included. So a value moving between two adjacent nullable columns doesn't change the hash:

select md5(concat_ws('|', 'Smith', null, 'X')) = md5(concat_ws('|', 'Smith', 'X', null));   -- true!

For your columns: an employee with middlename = 'A' and title = null hashes the same as middlename = null and title = 'A'. That's rare, but the result is a missed SCD change that you'd never notice. The fix is to make every column always take up its position:

{#- Null-safe, position-preserving row hash.
    Every column always contributes "value|" or "\N|", so a value moving between columns changes the hash. -#}
{% macro row_hash(columns, alias=none) -%}
    {%- set prefix = alias ~ '.' if alias else '' -%}
    md5(
    {%- for c in columns %}
        coalesce({{ prefix }}{{ c }}::text, '\N'){% if not loop.last %} || '|' ||{% endif %}
    {%- endfor %}
    )
{%- endmacro %}

Changing the hash formula updates every row

When you deploy a new hash formula, every row's row_hash changes, so on the next run your model treats every version as "changed". The merge updates them all (with no Type 2 effect, since startdate is unchanged), and dw_last_run_id jumps for the whole table. Plan the switch: either accept one noisy run, or run a one-off update … set row_hash = <new formula> on the dimension in the same deployment.

Generating the hash list from YAML

Instead of listing hash columns in SQL, mark them in the model's YAML. The documentation and the change-detection rule then live in one place:

  - name: int_dimemployee_prepared
    columns:
      - name: employeenationalidalternatekey
        description: "Business key"
      - name: firstname
        meta: {scd_hash: true}
      - name: lastname
        meta: {scd_hash: true}
      - name: departmentname
        meta: {scd_hash: true}
      # … one entry per tracked column
{% macro scd_hash_columns(node=none) %}
    {%- set node = node or model -%}          {#- default: the calling model -#}
    {%- set cols = [] -%}
    {%- for name, col in node.columns.items() -%}
        {%- if (col.meta or {}).get('scd_hash') -%}{%- do cols.append(name) -%}{%- endif -%}
    {%- endfor -%}
    {%- if execute and cols | length == 0 -%}
        {{ exceptions.raise_compiler_error(node.name ~ ": no columns with meta.scd_hash in YAML") }}
    {%- endif -%}
    {{ return(cols) }}
{% endmacro %}
select
    *,
    {{ row_hash(scd_hash_columns()) }} as row_hash
from prepared

Under the hood: YAML columns and parsing

YAML properties are applied after the SQL file has been parsed (internals ch. 04), so during the parse pass model.columns is still empty. That's why the "no columns" error only fires when execute is true. At run time the node has been patched and the list is complete.

Introspection: star and friends

select
    {{ dbt_utils.star(from=ref('int_dimemployee_prepared'), except=['row_hash'], relation_alias='s') }}
from {{ ref('int_dimemployee_prepared') }} s

star queries the database's column list at compile time, and returns * during parsing. It needs the relation to exist, so on a brand-new database the parent must be built first. In one dbt build it always is. Hand-written introspection follows the same pattern:

{% if execute %}
  {% set cols = adapter.get_columns_in_relation(ref('int_dimemployee_prepared')) %}
  {% set names = cols | map(attribute='name') | reject('in', ['row_hash']) | list %}
{% else %}
  {% set names = [] %}
{% endif %}

{% macro sql_str(value) -%}
    {%- if value is none -%}null{%- else -%}'{{ value | string | replace("'", "''") }}'{%- endif -%}
{%- endmacro %}

{% macro case_from_map(column, mapping, else_value=none) -%}
    case {{ column }}
    {%- for k, v in mapping.items() %}
        when {{ k if k is number else sql_str(k) }} then {{ sql_str(v) }}
    {%- endfor %}
        else {{ sql_str(else_value) }}
    end
{%- endmacro %}

Cross-database macros

dbt has a set of dbt.* macros that write each database's own syntax. Using them keeps a macro portable, which matters as soon as it lives in a package:

{{ dbt.current_timestamp() }}                         now()
{{ dbt.dateadd('day', -7, 'current_date') }}          current_date + ((interval '1 day') * (-7))
{{ dbt.datediff('hiredate', 'current_date', 'year') }}
{{ dbt.date_trunc('month', 'hiredate') }}
{{ dbt.concat(['firstname', "' '", 'lastname']) }}
{{ dbt.hash('loginid') }}                             md5(cast(loginid as <string type>))
{{ dbt.safe_cast('vacationhours', api.Column.translate_type('integer')) }}
{{ dbt.type_string() }} / {{ dbt.type_timestamp() }} / {{ dbt.type_int() }}
{{ dbt.listagg('departmentname', "', '", 'order by startdate') }}
{{ dbt.split_part('emailaddress', "'@'", 2) }}         domain part of the e-mail

Escaping and quoting checklist

A data value as an identifierSanitise (modules.re.sub) and then adapter.quote(...)
A reserved word as a column ("group" in salesterritory){{ adapter.quote('group') }}
A tableNever a string. Use ref, source or api.Relation.create
A numberConvert first (| int, | float) to make sure it really is one
NoneWrite null explicitly, because {{ none }} renders as None

Key takeaways

  • Pick column lists from YAML, introspection or code deliberately, knowing what each costs.
  • concat_ws hashes ignore NULL positions. Use a coalesce-and-separator hash, and plan for the one-time re-hash.
  • meta in YAML plus a small macro turns documentation into code generation.
  • Use dbt.* cross-database macros, escape values, quote identifiers, and never build table names from strings.

Exercises

1 · Hash collision test

Write a singular test that fails if two different current versions in int_dimemployee_prepared share the same row_hash.

Answer 
select row_hash, count(distinct employeenationalidalternatekey) as employees
from {{ ref('int_dimemployee_prepared') }}
where status = 'Current'
group by row_hash
having count(distinct employeenationalidalternatekey) > 1

Two people can legitimately have identical tracked attributes (unlikely with names and login IDs), so treat a failure as a reason to investigate, not proof of a bug. config(severity='warn') fits.
