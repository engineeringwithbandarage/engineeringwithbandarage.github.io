Chapter 11 · Metaprogramming

Overriding dbt Internals

Some of dbt's built-in behaviour is implemented as ordinary macros that you override simply by defining a macro with the same name in your project. The most important ones decide where every model is built. Your project already overrides one of them. This chapter explains what it changes and the risk it creates, and builds a safer version.

~30 min read Lab: generate_schema_name

The three naming macros

For every model, seed and snapshot, dbt calls these during parsing:

MacroInputDecides
generate_database_name(custom_database_name, node)+database configthe database part
generate_schema_name(custom_schema_name, node)+schema configthe schema part
generate_alias_name(custom_alias_name, node)+alias configthe table/view name

The result is stored in the node (database, schema, alias, relation_name), and from then on every ref, this and DDL statement uses it.

dbt's default schema behaviour

{% macro default__generate_schema_name(custom_schema_name, node) -%}
    {%- set default_schema = target.schema -%}
    {%- if custom_schema_name is none -%}
        {{ default_schema }}
    {%- else -%}
        {{ default_schema }}_{{ custom_schema_name | trim }}
    {%- endif -%}
{%- endmacro %}

With your profile's schema: public and +schema: mart, the default would build public_mart. The prefix exists so that each developer and environment gets its own schemas (dev_sameera_mart, ci_mart, prod_mart).

Your override

{% macro generate_schema_name(custom_schema_name, node) -%}
    {%- if custom_schema_name is none -%}
        {{ target.schema }}
    {%- else -%}
        {{ custom_schema_name | trim }}
    {%- endif -%}
{%- endmacro %}

This gives clean names that match AdventureWorksDW (mart, int, rpt). The cost is that every target builds into the same schemas. A dbt run with --target dev on a laptop pointed at the lab database replaces the "production" mart.dimemployee. Deferral and slim CI (internals ch. 08) can't work either, because there's no second set of schemas to compare against.

An environment-aware version

{#
  prod  (target.name == 'prod' or 'dev' on the lab server) → mart, int, rpt         (clean names)
  other targets                                             → <target.schema>_mart … (isolated)
#}
{% macro generate_schema_name(custom_schema_name, node) -%}
    {%- set clean_targets = var('clean_schema_targets', ['prod']) -%}
    {%- if custom_schema_name is none -%}
        {{ target.schema }}
    {%- elif target.name in clean_targets -%}
        {{ custom_schema_name | trim }}
    {%- else -%}
        {{ target.schema }}_{{ custom_schema_name | trim }}
    {%- endif -%}
{%- endmacro %}

dbt also ships a ready-made variant, generate_schema_name_for_env, that applies the clean names only when target.name == 'prod':

{% macro generate_schema_name(custom_schema_name, node) -%}
    {{ generate_schema_name_for_env(custom_schema_name, node) }}
{%- endmacro %}

Migrating your lab

Your lab target is called dev but acts as production. Before switching macros, either rename the target to prod in profiles.yml, or set clean_schema_targets: ['dev'] for now. Otherwise the next run builds a fresh public_mart.dimemployee with new keys next to the old one. Remember too that editing this macro forces a full re-parse (internals ch. 04).

What the naming context can use

These macros run during parsing, in a restricted context. target, var, env_var, the node argument and other macros are all available. Database queries aren't, and this doesn't exist yet, since this macro is what creates it. The node argument opens interesting possibilities:

{#- models/mart/finance/x.sql → mart_finance (when no +schema is set) -#}
{%- if custom_schema_name is none and node.resource_type == 'model' -%}
    {{ node.fqn[1:-1] | join('_') or target.schema }}
{%- endif -%}

Alias overrides

{#- versioned models: dim_customer_v2; otherwise custom alias or file name -#}
{% macro generate_alias_name(custom_alias_name=none, node=none) -%}
    {%- if custom_alias_name -%}
        {{ custom_alias_name | trim }}
    {%- elif node.version -%}
        {{ node.name ~ '_v' ~ (node.version | replace('.', '_')) }}
    {%- else -%}
        {{ node.name }}
    {%- endif -%}
{%- endmacro %}

That's essentially dbt's default. A real use for overriding it would be stripping a prefix, for example turning int_employee_person into the view employee_person in the int schema.

Wrapping ref with builtins

You can define your own macro called ref. dbt then calls it for every {{ ref(...) }} in the project, and builtins.ref still reaches the original. Since model versions were introduced, a correct wrapper has to forward package names and versions:

{% macro ref(model_name_or_package, model_name=none, version=none, v=none) -%}
    {%- set version = version or v -%}
    {%- if model_name is none -%}
        {%- set rel = builtins.ref(model_name_or_package, version=version) -%}
    {%- else -%}
        {%- set rel = builtins.ref(model_name_or_package, model_name, version=version) -%}
    {%- endif -%}

    {#- example policy: in the "ci" target, read int_* views from a frozen snapshot schema -#}
    {%- if target.name == 'ci' and rel.schema == 'ci_int' -%}
        {%- set rel = rel.incorporate(path={'schema': 'int_frozen'}) -%}
    {%- endif -%}

    {{ return(rel) }}
{%- endmacro %}

Global effect

A ref override changes every model, every test and every package that calls ref. Keep it tiny, return a Relation (never a string), and add a test model that compiles the special cases.

Overriding built-in generic tests

The SQL behind unique, not_null, accepted_values and relationships is dispatched (default__test_unique and so on), so you override it like any dispatched macro. For example, the following makes not_null also treat empty strings as missing:

{% macro default__test_not_null(model, column_name) %}
select {{ column_name }}
from {{ model }}
where {{ column_name }} is null
   or trim(cast({{ column_name }} as {{ dbt.type_string() }})) = ''
{% endmacro %}

Every not_null test in the project, including those on your stg sources, now enforces the stricter rule. If that's too broad, write a new generic test with its own name instead (chapter 13).

Key takeaways

  • generate_schema_name, generate_alias_name and generate_database_name decide where every node lives. They run during parsing in a limited context.
  • Clean names in every environment mean environments overwrite each other. Make naming depend on the target.
  • builtins.ref lets you wrap ref. Forward the package and version, and return a Relation.
  • Built-in test SQL is dispatched, so you can override it, with project-wide effect.

Exercises

1 · Predict the schema

With the proposed macro and clean_schema_targets: ['prod'], where does dimemployee build for --target dev (profile schema public) and for --target prod?

Answer

public_mart.dimemployee for dev, and mart.dimemployee for prod.

2 · Sequence name

After the switch, does your pre-hook create sequence if not exists {{ this.schema }}.dimemployee_key_seq still work in dev? Does dev share key numbers with prod?

Answer

Yes, it creates public_mart.dimemployee_key_seq. No: each schema has its own sequence, so dev keys are independent of prod. That's what you want for isolation, and also why dev keys can't be compared with prod keys.
