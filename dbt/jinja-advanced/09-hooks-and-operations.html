Chapter 09 · Macros

Hooks & Operations

Hooks let you run SQL around a model or around a whole invocation. Operations let you run a macro on its own, with no model at all. Your project already uses both kinds of model hook. This chapter explains exactly when and how they run, then adds invocation-level logging and maintenance operations.

~35 min read Lab: record_dim_stats, audit logging

Model hooks: why they are strings

{{ config(
    materialized='table',
    post_hook="{{ record_dim_stats(scd2=false) }}"
) }}

The hook is a quoted string containing Jinja. The outer config() call is rendered during parsing, and at that point the inner {{ … }} is just characters inside a Python string. dbt stores it unrendered and renders it when the hook runs, with the runtime context, so this is the real table and var('run_id') is the real value.

✗ Rendered at parse time

{{ config(
    post_hook=record_dim_stats(scd2=false)
) }}

✓ Rendered when the hook runs

{{ config(
    post_hook="{{ record_dim_stats(scd2=false) }}"
) }}

In the version on the left, the macro runs during parsing with the parse context, and its output (built from a placeholder this and whatever run_id was at parse time) is frozen into the config.

Execution order and transactions

For table, view and incremental models on Postgres, the built-in materializations run:

  1. pre-hooks marked "outside transaction"
  2. BEGIN, then pre-hooks inside the transaction (the default). Your create sequence if not exists runs here.
  3. The main statement (create / merge)
  4. post-hooks inside the transaction (the default). Your parent-key update and record_dim_stats run here, in order.
  5. COMMIT
  6. post-hooks marked "outside transaction"
{{ config(
    pre_hook  = before_begin("set local statement_timeout = '5min'"),     {# runs before BEGIN #}
    post_hook = [
        "{{ record_dim_stats(scd2=true) }}",                               {# inside — atomic with the merge #}
        after_commit("analyze {{ this }}"),                                {# after COMMIT #}
        {"sql": "select pg_notify('dwlab', '{{ this }} loaded')", "transaction": false},   {# dict form #}
    ]
) }}

set local before BEGIN does nothing

The first line above is a deliberate counter-example. set local only lasts for the current transaction, so running it before the transaction starts has no effect. Put session settings inside the transaction (a plain pre-hook), or use set without local. Transaction placement really does change what SQL does.

Hooks from several levels

models:
  dwlab:
    mart:
      +schema: mart
      +post-hook:
        - "grant select on {{ this }} to reporting"

Hooks add up across levels: with the config above, every mart model also gets the grant after its own hooks. (For grants specifically, the grants config is better. It works out the difference between current and desired grants and is aware of the adapter.)

Deep dive: record_dim_stats

{% macro record_dim_stats(scd2=false) %}
    insert into audit.dim_load_stats
        (run_id, dim_table, total_rows, current_rows, inserted_rows, updated_rows, expired_rows, recorded_at)
    select
        {{ var('run_id') }},
        '{{ this.schema }}.{{ this.identifier }}',
        count(*),
        {% if scd2 %}
        count(*) filter (where status = 'Current'),
        count(*) filter (where dw_first_run_id = {{ var('run_id') }}),
        count(*) filter (where dw_last_run_id = {{ var('run_id') }} and dw_first_run_id <> {{ var('run_id') }}),
        count(*) filter (where dw_expired_run_id = {{ var('run_id') }}),
        {% else %}
        count(*), null, null, null,
        {% endif %}
        now()
    from {{ this }}
    on conflict (run_id, dim_table) do update
        set total_rows = excluded.total_rows, …
{% endmacro %}
Design choiceWhy it works
Runs as a post-hook inside the transactionStats are only committed together with the data they describe
Counts are derived from audit columns rather than from rows_affectedThe merge's single row count can't separate inserts, updates and expirations. The dw_*_run_id columns can
on conflict … do updateRe-running the same run_id (an Airflow retry) replaces the row instead of failing
this used inside the macroHooks render with the model's context, so one macro serves every dimension

Two improvements, which chapter 17 applies:

  • Use {{ source('audit', 'dim_load_stats') }} instead of the hard-coded table name, so the location is defined in one place. (Refs and sources inside hooks don't add DAG edges, which is fine here.)
  • Call var('run_id') once and store it: {% set rid = var('run_id') %}. The SQL reads better and the value is guaranteed to be identical everywhere.

Invocation hooks: on-run-start / on-run-end

on-run-start:
  - "create table if not exists audit.dbt_node_result (
       run_id int, invocation_id uuid, unique_id text, status text,
       seconds numeric, rows_affected bigint, message text, recorded_at timestamptz,
       primary key (invocation_id, unique_id))"
on-run-end:
  - "{{ log_dbt_results(results) }}"

In on-run-end, results is the list of node results for this invocation, the same information that's written to run_results.json:

AttributeExample
r.node.unique_id, r.node.name, r.node.resource_typemodel.dwlab.dimemployee
r.statussuccess, error, pass, fail, skipped …
r.execution_timeseconds (float)
r.adapter_response{'_message': 'MERGE 290', 'code': 'MERGE', 'rows_affected': 290}
r.message, r.failureserror text / failing-row count for tests
 
{% macro log_dbt_results(results) %}
    {%- if not execute or results | length == 0 -%}{{ return('') }}{%- endif -%}
    {%- set rows = [] -%}
    {%- for r in results -%}
        {%- set ra = r.adapter_response or {} -%}
        {%- set affected = ra.get('rows_affected') -%}
        {%- do rows.append(
            "(" ~ var('run_id') ~ ", '" ~ invocation_id ~ "', '" ~ r.node.unique_id ~ "', '" ~ r.status ~ "', "
            ~ ((r.execution_time or 0) | round(3)) ~ ", "
            ~ (affected if affected is not none else 'null') ~ ", "
            ~ ("'" ~ (r.message | string | replace("'", "''"))[:500] ~ "'" if r.message else 'null')
            ~ ", now())"
        ) -%}
    {%- endfor -%}
    {%- call statement('log_dbt_results', auto_begin=true) -%}
        insert into audit.dbt_node_result
            (run_id, invocation_id, unique_id, status, seconds, rows_affected, message, recorded_at)
        values {{ rows | join(',\n               ') }}
        on conflict (invocation_id, unique_id) do nothing
    {%- endcall -%}
    {%- do adapter.commit() -%}
{% endmacro %}

The macro does its own work through a statement and commits explicitly. Its output is empty, so dbt has no SQL left to run for the hook itself. This "the macro does the work" style makes transaction behaviour explicit, so you don't depend on how a particular dbt version handles hooks.

Compared with your Airflow callback

record_dbt_step reads run_results.json after the process exits, which also covers crashes where dbt never reaches on-run-end. The hook records per-node detail from inside dbt with no file handling. They complement each other: keep the callback for step status and add the hook for node detail.

Operations: dbt run-operation

An operation runs one macro with the macro context: there's no current model, there are no selected nodes, and the arguments come from --args as YAML.

{#- Re-align a surrogate-key sequence with the table, e.g. after a manual repair.
    dbt run-operation sync_key_sequence --args '{model_name: dimemployee, key: employeekey}' -#}
{% macro sync_key_sequence(model_name, key) %}
    {%- set rel = ref(model_name) -%}
    {%- set seq = rel.schema ~ '.' ~ rel.identifier ~ '_key_seq' -%}
    {%- set q -%}
        select setval('{{ seq }}', coalesce((select max({{ key }}) from {{ rel }}), 0) + 1, false)
    {%- endset -%}
    {%- set next_value = run_query(q).columns[0].values()[0] -%}
    {{ log("sequence " ~ seq ~ " now returns " ~ next_value ~ " next", info=True) }}
{% endmacro %}
{#- dbt run-operation purge_audit --args '{keep_days: 90}' -#}
{% macro purge_audit(keep_days=90) %}
    {%- call statement('purge', fetch_result=false, auto_begin=true) -%}
        delete from audit.dbt_node_result
        where recorded_at < now() - interval '{{ keep_days | int }} days'
    {%- endcall -%}
    {%- set n = load_result('purge')['response'].rows_affected -%}
    {%- do adapter.commit() -%}
    {{ log("purged " ~ n ~ " rows older than " ~ keep_days ~ " days", info=True) }}
{% endmacro %}
  • setval isn't transactional in PostgreSQL, so sync_key_sequence needs no commit.
  • purge_audit deletes data, so it opens a transaction (auto_begin=true) and commits explicitly. This is the most reliable pattern for operations that change data.
  • ref() works in operations because the manifest is loaded, but it creates no dependencies, since there's no DAG run.

Key takeaways

  • Hook strings are rendered when they run. Always quote them so the inner Jinja waits until then.
  • Default model hooks run inside the model's transaction. Use before_begin/after_commit deliberately.
  • Hooks add up across config levels.
  • on-run-end receives results. A macro that does its own statement + commit makes logging reliable.
  • run-operation runs a macro with --args. Commit explicitly when you change data.

Exercises

1 · Stats after a failed merge

The merge for dimemployee fails. Is a row written to audit.dim_load_stats? Is one written to audit.dbt_node_result?

Answer

No stats row: post-hooks don't run after a failed main statement, and the transaction rolls back. Yes, a dbt_node_result row is written with status error, because on-run-end still runs after node failures.

2 · Analyze after load

Add analyze of the dimension after every load without making it part of the merge transaction.

Answer

Add after_commit("analyze {{ this }}") to the post_hook list. analyze can run inside a transaction, but keeping it outside means the merge's locks are released first.
