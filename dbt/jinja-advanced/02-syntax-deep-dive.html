Chapter 02 · Foundations

Syntax Deep Dive

You already know {{ }} and {% %}. This chapter covers the rest of the syntax that matters for SQL generation: whitespace control, the full set of operators, loop variables, filters, tests and raw blocks. It points out the dbt-specific traps along the way.

~30 min read Jinja2 3.1

The three delimiters

DelimiterPurposeWrites output?
{{ … }}Expression: evaluate and printYes
{% … %}Statement: if, for, set, macro, do, call, …No (but the blocks it contains can)
{# … #}Comment, removed before renderingNo

SQL comments don't disable Jinja

Jinja doesn't know about SQL comments. In -- {{ ref('old_model') }}, the ref still runs. It creates a DAG edge, and it fails if old_model no longer exists. To disable Jinja, use {# … #}. (Chapter 04 of the internals tutorial uses this behaviour on purpose, for -- depends_on: hints.)

Whitespace control

Every tag keeps the newlines and indentation around it. dbt uses Jinja's default settings (no trim_blocks), so loops and conditionals leave blank lines in the compiled SQL. A - inside a delimiter removes the whitespace on that side:

  • {%- … %} removes whitespace, including newlines, before the tag
  • {% … -%} removes whitespace after the tag
  • The same works for {{- -}} and {#- -#}

Template

select
{% for c in ['a','b','c'] %}
    {{ c }}{% if not loop.last %},{% endif %}
{% endfor %}
from t

select
{%- for c in ['a','b','c'] %}
    {{ c }}{% if not loop.last %},{% endif %}
{%- endfor %}
from t

Compiled

select

    a,

    b,

    c

from t

select
    a,
    b,
    c
from t

Blank lines are harmless to PostgreSQL, but they make compiled SQL hard to read and diff. Your generate_schema_name trims for a reason that does matter: its output becomes a schema name, and a schema called "\n mart\n" would be a real bug. That's why it uses {%- -%} everywhere and also applies | trim.

~ vs +

'run ' + var('run_id') fails when run_id is an integer (you can't add a str and an int). 'run ' ~ var('run_id') always works, because ~ converts both sides to strings. Use ~ whenever you build text.

    select * from {{ t }} {% if not loop.last %}union all{% endif %}

No break or continue

dbt doesn't enable Jinja's loop-controls extension, so {% break %} and {% continue %} are syntax errors. Filter in the loop header, or use selectattr/reject, instead.

Filters

A filter is a function applied with |, and filters can be chained. These are the ones you'll use most when generating SQL. Appendix B has the full list.

{{ cols | join(', ') }}                                   {# a, b, c #}
{{ cols | map('upper') | join(', ') }}                    {# A, B, C #}
{{ cols | reject('in', ['row_hash']) | list }}            {# drop items #}
{{ nodes | selectattr('resource_type', 'equalto', 'model') | map(attribute='name') | list }}
{{ custom_schema_name | trim }}
{{ "o'brien" | replace("'", "''") }}                       {# SQL-escape a quote #}
{{ var('tables', []) | length }}
{{ some_value | default('fallback') }}                    {# only when undefined #}
{{ some_value or 'fallback' }}                            {# when undefined, none, '' or 0 #}
{{ model.config | tojson }}                               {# debug-print a structure #}

Tests (the is operator)

{% if custom_schema_name is none %} … {% endif %}
{% if my_var is defined %} … {% endif %}
{% if value is string %} … {% elif value is number %} … {% endif %}
{% if cols is iterable and cols is not string %} … {% endif %}   {# strings are iterable too! #}
{% if config is mapping %} … {% endif %}
{% if n is divisibleby 2 %} … {% endif %}

Calling Python methods

Values in Jinja are Python objects, and the sandbox lets you call their ordinary public methods:

{{ this.identifier.upper() }}
{{ 'a,b,c'.split(',') }}
{{ model.name.startswith('int_') }}
{{ model.config.get('meta', {}).get('owner', 'unknown') }}
{{ '{}_{}'.format(this.schema, this.identifier) }}
{% do my_list.append('x') %}          {# mutate — needs do #}
{% do my_dict.update({'k': 'v'}) %}

Raw blocks and literal braces

PostgreSQL can contain characters that look like Jinja, for example in JSON literals or regular expressions. {% raw %} switches Jinja off for a section:

select '{% raw %}{{ not jinja }}{% endraw %}' as literal_text,
       regexp_matches(phone, '{% raw %}^\d{3}-\d{3}{% endraw %}') as m

A { on its own is fine. Only {{, {% and {# start Jinja.

Key takeaways

  • SQL comments don't hide Jinja. Use {# #}.
  • Use - trimming for readable output, and for correctness when the output is a name.
  • Use ~ for string building and is none/is defined for checks. There's no break/continue.
  • Python methods work on values, and mutating them needs {% do %}.

Exercises

1 · Generate the row hash

Write a Jinja expression that turns a list cols into md5(concat_ws('|', a, b, c)) with no trailing comma and no blank lines.

Answer 
md5(concat_ws('|', {{ cols | join(', ') }}))

A filter is shorter and safer than a loop. Chapter 08 explains why concat_ws is a risky way to hash, and how to fix it.

2 · Spot the bug

{% if model.config.tags %}{{ 'tags: ' + model.config.tags }}{% endif %} fails. Why, and how would you fix it?

Answer

tags is a list, and + can't add a str and a list. Use 'tags: ' ~ model.config.tags | join(', '). Filters bind more tightly than ~, so that expression joins the list first.
