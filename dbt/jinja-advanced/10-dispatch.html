Dispatch & Adapter Macros

adapter.dispatch is dbt's version of polymorphism. A single macro name resolves to different implementations depending on the database adapter, and also depending on which project is asking. It's how dbt and its packages support many warehouses, and how you replace a package's behaviour without forking it.

~30 min read Builds on: Internals ch. 02, 06

The pattern

{#- public entry point: always call this one -#}
{% macro row_hash(columns, alias=none) -%}
    {{ return(adapter.dispatch('row_hash', 'dwlab')(columns, alias)) }}
{%- endmacro %}

{#- generic implementation -#}
{% macro default__row_hash(columns, alias=none) -%}
    {%- set p = alias ~ '.' if alias else '' -%}
    md5({% for c in columns %}coalesce(cast({{ p }}{{ c }} as {{ dbt.type_string() }}), '\N'){% if not loop.last %} || '|' || {% endif %}{% endfor %})
{%- endmacro %}

{#- Postgres: hash the row as a single composite value — handles nulls and positions natively -#}
{% macro postgres__row_hash(columns, alias=none) -%}
    {%- set p = alias ~ '.' if alias else '' -%}
    md5(row({% for c in columns %}{{ p }}{{ c }}{% if not loop.last %}, {% endif %}{% endfor %})::text)
{%- endmacro %}
  • The first argument is the macro name without a prefix.
  • The second argument (macro_namespace) names the package that owns the macro. It's what makes overrides possible (below).
  • dispatch returns a macro. You call it with the arguments, and return(...) passes the result through unchanged, whether it's a string or an object.

Why row(...)::text works on Postgres

A composite row cast to text gives something like (Smith,,X), where NULL is an empty slot and every position keeps its comma. Values containing commas or quotes are quoted automatically. That's exactly the null-safe, position-preserving property chapter 08 had to build by hand, and dispatch lets you use it on Postgres while keeping a portable fallback.

How dbt picks the implementation

For adapter.dispatch('row_hash', 'dwlab') on the postgres adapter, dbt tries these names in order, in each namespace of the search order:

  1. postgres__row_hash
  2. names for parent adapters, if the adapter has any (for example, for redshift it tries redshift__ then postgres__)
  3. default__row_hash

The search order is the list of packages to look in. By default it's just the namespace you passed (dwlab). If nothing matches, compilation fails with a message listing every name it tried, which is very useful when debugging.

Overriding a package's implementation

Suppose a package dwlab_utils (yours, or one from the dbt Hub) dispatches row_hash in its own namespace, and you want your project's version to win:

dispatch:
  - macro_namespace: dwlab_utils
    search_order: ['dwlab', 'dwlab_utils']     # look in my project first, then the package

Now every call inside the package that does adapter.dispatch('row_hash', 'dwlab_utils') first looks for postgres__row_hash / default__row_hash in your project. You've changed the package's behaviour without editing its code.

This is also how compatibility "shim" packages work. For example, spark_utils adds Spark implementations of dbt_utils macros by being added to the dbt_utils search order.

Packages must pass their namespace

If a package author writes adapter.dispatch('x') with no namespace, the lookup is fixed to the package and your dispatch: config can't reach it. When you write a package, always pass your package name as the second argument.

Overriding dbt's built-in macros

dbt's own macros dispatch in the dbt namespace, for example adapter.dispatch('create_table_as', 'dbt'). The root project is searched before the internal packages, so defining a postgres__ or default__ version in your project overrides the built-in one:

{#- Make dbt.current_timestamp() return Sri Lanka local time instead of now() -#}
{% macro postgres__current_timestamp() -%}
    (now() at time zone 'Asia/Colombo')
{%- endmacro %}

Every built-in macro that uses dbt.current_timestamp() would now see Colombo time. That's powerful, and it's also why built-in overrides deserve a comment, a test, and a note in your README.

Finding dispatch points

To find out whether a built-in behaviour can be overridden, look for adapter.dispatch in its source:

$ grep -rn "adapter.dispatch('get_merge_sql'" global_project/
$ grep -rln "macro postgres__" postgres/macros/ | head

Worked example: an "update only when changed" merge

Your dimemployee already filters unchanged rows in the SELECT. Another approach puts the check in the merge, so that any incremental model with a row_hash benefits automatically. Here is a deliberately small override of the Postgres incremental merge entry point:

{% macro postgres__get_incremental_merge_sql(arg_dict) -%}
    {%- set sql = default__get_incremental_merge_sql(arg_dict) -%}
    {%- if 'row_hash' in (arg_dict['dest_columns'] | map(attribute='name') | list) -%}
        {#- add a condition to "when matched" so identical rows aren't rewritten -#}
        {%- set sql = sql | replace(
              'when matched then update set',
              'when matched and DBT_INTERNAL_DEST.row_hash is distinct from DBT_INTERNAL_SOURCE.row_hash then update set') -%}
    {%- endif -%}
    {{ return(sql) }}
{%- endmacro %}

Fragile by design: use it to learn, not as is

String-replacing generated SQL depends on the exact text dbt produces, and that can change in any release. It's here to show the mechanism. For production, copy the full built-in macro into your project and edit it properly, or use the merge_update_columns/merge_exclude_columns configs and an incremental predicate where they're enough. Check which strategy entry-point names your dbt version uses before overriding.

Key takeaways

  • Pattern: a public macro that dispatches, plus <adapter>__ and default__ implementations.
  • Lookup order: the adapter, then its parent adapters, then default, in each package of the search order.
  • dispatch: in dbt_project.yml puts your project ahead of a package, so you override without forking.
  • Your root project overrides built-in dbt-namespace implementations, so use that power carefully.

Exercises

1 · Read the error

You call adapter.dispatch('row_hash', 'dwlab') but only wrote snowflake__row_hash. What does dbt report on Postgres?

Answer

A compilation error saying that no implementation of row_hash was found in namespace dwlab, listing the candidates it tried (postgres__row_hash, default__row_hash). Add a default__ version.

2 · Override dbt_utils.generate_surrogate_key

You want dbt_utils.generate_surrogate_key to use your row_hash on Postgres. What do you write, and where?

Answer 
dispatch:
  - macro_namespace: dbt_utils
    search_order: ['dwlab', 'dbt_utils']
{% macro postgres__generate_surrogate_key(field_list) -%}
    {{ dwlab.row_hash(field_list) }}
{%- endmacro %}

The name must match the implementation name the package dispatches to. Check its source in dbt_packages/dbt_utils/macros/.
