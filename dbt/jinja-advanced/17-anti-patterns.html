Chapter 17 · Engineering Discipline

Anti-patterns & Performance

The techniques in this tutorial are powerful, and that's the danger. A project where every model is three macro calls can't be reviewed, debugged or handed over. This chapter covers the patterns that cause trouble, what they cost, and how to tell when not to use Jinja. It also applies a few fixes to dwlab.

~25 min read Lab: hardening dwlab

1. Over-templating

✗ Clever

{{ build_model(
    src='int_dimemployee_prepared',
    kind=var('kinds')['emp'],
    opts=get_opts(model.name)) }}

✓ Clear

select
    s.employeenationalidalternatekey,
    s.firstname,
    …
    {{ audit_columns(incremental=is_incremental()) }}
from {{ ref('int_dimemployee_prepared') }} s

Rule of thumb: a reader should be able to tell what a model selects without opening a macro. Use macros for repetitive mechanics (audit columns, hashes, joins on keys), not to hide business logic. CASE expressions, joins and filters that are specific to one model belong in that model's SQL.

2. Hidden dependencies

  • Tables named as strings (from audit.dim_load_stats, from mart.dimemployee) don't create DAG edges, aren't renamed by generate_schema_name, and don't appear in lineage.
  • Refs inside {% if execute %} or inside hooks don't create edges.
  • Dependencies that go through side effects (a post-hook writes a table that another model reads) are invisible to dbt, as with rpt_load_summary in internals ch. 05.

Fix: declare every table you read as a source or ref, and add -- depends_on: hints for dependencies that go through side effects.

3. Silent defaults

vars: {run_id: 0} in your dbt_project.yml means a run without --vars succeeds and writes audit rows for run 0. A default should only exist when it's genuinely correct, not just convenient:

{% macro require_run_id() -%}
    {%- set rid = var('run_id', none) -%}
    {%- if execute and (rid is none or rid | int == 0) and target.name not in var('adhoc_targets', ['dev_local']) -%}
        {{ exceptions.raise_compiler_error(
             "run_id is missing. Run via Airflow, or pass --vars '{\"run_id\": N}'. (" ~ model.unique_id ~ ")") }}
    {%- endif -%}
    {{ return(rid | int if rid is not none else 0) }}
{%- endmacro %}

Use {% set rid = require_run_id() %} in models and hooks that write audit data, and remove run_id: 0 from dbt_project.yml. Replace every plain var('run_id') at the same time (in dimemployee, rpt_load_summary and matches_source_metrics). Without a project default, a plain var('run_id') fails during parsing, so even dbt ls would need --vars. The helper only complains when execute is true.

4. Hard-coded locations in macros

{% macro record_dim_stats(scd2=false) %}
    {%- set rid = require_run_id() -%}
    insert into {{ source('audit', 'dim_load_stats') }}
        (run_id, dim_table, total_rows, current_rows, inserted_rows, updated_rows, expired_rows, recorded_at)
    select
        {{ rid }},
        '{{ this.schema }}.{{ this.identifier }}',
        count(*),
        {% if scd2 -%}
        count(*) filter (where status = 'Current'),
        count(*) filter (where dw_first_run_id = {{ rid }}),
        count(*) filter (where dw_last_run_id = {{ rid }} and dw_first_run_id <> {{ rid }}),
        count(*) filter (where dw_expired_run_id = {{ rid }}),
        {%- else -%}
        count(*), null, null, null,
        {%- endif %}
        now()
    from {{ this }}
    on conflict (run_id, dim_table) do update
        set total_rows = excluded.total_rows, current_rows = excluded.current_rows,
            inserted_rows = excluded.inserted_rows, updated_rows = excluded.updated_rows,
            expired_rows = excluded.expired_rows, recorded_at = excluded.recorded_at
{% endmacro %}

5. Parse-time cost

PatternCostBetter
Complex Jinja in simple modelsThe static parser can't handle it, so every such file goes through full Jinja renderingKeep staging/int models plain: just ref/source/config
env_var in many configsPartial parsing re-parses every node that uses an env var whose value changedRead it once in dbt_project.yml, or use target
Fast-changing --varsFull re-parse on every change (your run_id)Accept it, but parse once per DAG run and reuse target/
Big loops over graph in every modelMultiplied by the number of models, on every compileOperations and on-run-end

6. Compile-time query cost

  • Every run_query, get_columns_in_relation and dbt_utils.star is a round trip on every compile: run, build, compile, docs generate and show.
  • Queries in macros called from many models run many times. Get the data once (an operation, a seed or a var) when it doesn't change per model.
  • Prefer YAML metadata (model.columns) to introspection when you control the YAML.

7. Logic in hooks

Hooks are invisible in lineage, aren't tested by data tests, and their SQL appears only in debug logs. Your parent-key update is a reasonable hook: it's local to the table and idempotent. As a rule, if a hook's SQL is longer than a few lines or reads other models, it should probably be a model, or a step in a materialization.

When not to use Jinja

TemptationUse instead
Generating a fixed CASE with a loop over a 3-item dictWrite the CASE. It's shorter and you can search for it
A macro used onceInline SQL, or a CTE
Jinja if on a value that's in the dataSQL CASE/WHERE. Jinja branches happen at compile time, not per row
Building a dimension's history yourselfSnapshots first. A custom materialization only when they don't fit
Copying a whole built-in macro to change one lineLook for a config first (merge_update_columns, incremental_predicates, unlogged, grants)

Review checklist

  1. Does every table read appear as ref/source? Are side-effect dependencies hinted?
  2. Is every database query guarded by execute, and is the parse-time output harmless?
  3. Do macros return data with return() and text by output, never mixed up?
  4. Are values escaped, identifiers quoted, and none rendered as null?
  5. Is whitespace controlled where the output is a name, and acceptable elsewhere?
  6. Do required inputs fail loudly instead of falling back to defaults?
  7. Does every public macro have a YAML description, and does every package macro dispatch with its namespace?
  8. Can someone understand what the model selects without opening its macros?

Key takeaways

  • Macros are for mechanics, and business logic stays visible in the model.
  • Make every dependency explicit, and make required inputs required.
  • Be aware of parse-time and compile-time costs. Keep simple models simple.
  • Jinja branches at compile time and SQL branches per row, so choose the right one.

Exercises

1 · Find the anti-patterns

Name two anti-patterns from this chapter that exist in the current dwlab project.

Answer

(1) The silent default run_id: 0. (2) The hard-coded audit.dim_load_stats in record_dim_stats. A third is the hidden dependency from rpt_load_summary on the dimensions' post-hooks.

2 · Jinja or SQL?

A colleague writes {% if status == 'Current' %}1{% else %}0{% endif %} as is_current in a model. What will it produce?

Answer

status is a database column, not a Jinja variable, so in Jinja it's undefined. The comparison is false and every row gets 0 (or the render fails). Use SQL: (status = 'Current')::int as is_current.
