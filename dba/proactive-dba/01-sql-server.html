Chapter 01

Proactive SQL Server Administration

SQL Server rarely fails without warning. Backups stop, logs grow, plans regress and statistics go stale for days before anyone notices. This chapter builds a daily health check that looks for each of those signals, records what it finds in a table, and emails the DBA only when something needs a human.

~45 min read SQL Server 2022 (most checks work from 2016 SP2) Tools: DMVs, msdb, Query Store, SQL Server Agent

Reactive vs. proactive

The difference is not the tools; it is when you look. A reactive DBA runs sp_who2 after the phone rings. A proactive DBA runs the same kind of query every morning, compares it to yesterday, and acts on the trend.

ProblemReactive: found when…Proactive: found when…
Backups stoppedA restore is needed and the newest backup is three weeks oldThe first day a full backup is older than its schedule allows
CorruptionA query fails with error 824 in productionAn Agent alert fires on the first 823/824/825, or CHECKDB hasn't succeeded in 7 days
Disk fullThe log can't grow and every write fails (error 9002)A volume drops below 15% free, or log_reuse_wait_desc stays on LOG_BACKUP
Slow queryUsers complain the report "suddenly" takes minutesQuery Store shows a query twice as slow as its 7-day baseline
Security driftAn audit finds an unexpected sysadminThe daily check compares role members against an approved list

The proactive loop

Baseline: what normal looks like→ Check: on a schedule→ Record: a finding with a severity→ Alert: only severity 1→ Trend: review the rest weekly

The most important design decision is the last two steps. If every finding sends an email, people stop reading the emails within a week. So the checks below write everything to a table, and only critical findings (severity 1) page someone. Warnings (severity 2) go into a weekly review.

Set up a DBA toolkit database

Keep your monitoring objects out of the user databases and out of master. A small utility database, here called DBAdmin, holds the findings table and the snapshots the checks compare against.

CREATE DATABASE DBAdmin;
GO
USE DBAdmin;
GO
CREATE SCHEMA dba;
GO
-- One row per problem found. Severity: 1 = critical (alert now), 2 = warning (weekly review), 3 = info
CREATE TABLE dba.HealthFinding (
    FindingID   bigint IDENTITY(1,1) PRIMARY KEY,
    CheckedAt   datetime2(0)   NOT NULL DEFAULT SYSDATETIME(),
    CheckName   varchar(60)    NOT NULL,
    Severity    tinyint        NOT NULL,
    ObjectName  nvarchar(256)  NULL,
    Detail      nvarchar(4000) NOT NULL
);
CREATE INDEX IX_HealthFinding_CheckedAt ON dba.HealthFinding (CheckedAt, Severity);

Each check in this chapter is a single INSERT … SELECT into that table. A check that finds nothing inserts nothing, so an empty result for today means a healthy server.

Check 1: Backups match the recovery objective

Your RPO (recovery point objective) is how much data the business can afford to lose. If it is one day, a full backup must never be older than about a day; if it is 15 minutes, log backups must run at least that often. msdb.dbo.backupset records every backup, so the check is a question about ages.

INSERT dba.HealthFinding (CheckName, Severity, ObjectName, Detail)
SELECT 'backup-full', 1, d.name,
       CONCAT('Last full backup: ', COALESCE(CONVERT(varchar(19), b.last_full, 120), 'never'))
FROM sys.databases AS d
OUTER APPLY (SELECT MAX(bs.backup_finish_date) AS last_full
             FROM msdb.dbo.backupset AS bs
             WHERE bs.database_name = d.name AND bs.type = 'D') AS b
WHERE d.database_id <> 2                 -- tempdb is never backed up
  AND d.state_desc = 'ONLINE'
  AND (b.last_full IS NULL OR b.last_full < DATEADD(HOUR, -26, SYSDATETIME()));
INSERT dba.HealthFinding (CheckName, Severity, ObjectName, Detail)
SELECT 'backup-log', 1, d.name,
       CONCAT('Recovery model FULL, last log backup: ', COALESCE(CONVERT(varchar(19), l.last_log, 120), 'never'))
FROM sys.databases AS d
OUTER APPLY (SELECT MAX(bs.backup_finish_date) AS last_log
             FROM msdb.dbo.backupset AS bs
             WHERE bs.database_name = d.name AND bs.type = 'L') AS l
WHERE d.database_id > 4                  -- skip master, tempdb, model, msdb
  AND d.recovery_model_desc = 'FULL'
  AND d.state_desc = 'ONLINE'
  AND (l.last_log IS NULL OR l.last_log < DATEADD(MINUTE, -30, SYSDATETIME()));

The 26 hours (not 24) leave room for a nightly job that runs a little late. Set the thresholds from your own schedule: an alert that fires every day because the threshold is too tight is worse than no alert.

A backup you never restored is a hope, not a backup

This check proves a backup ran; it doesn't prove it can be restored. Take backups WITH CHECKSUM so page checksums are verified as they are read, and schedule a regular test restore to another server, followed by DBCC CHECKDB on the restored copy. That one job tests the backup, the restore procedure and the restored database's consistency.

Why model is excluded from 1b

model is in FULL recovery by default on many installs, but nobody backs up its log. Without database_id > 4, the check would raise a critical finding about it every day, and the team would learn to ignore the email.

Check 2: Corruption is caught on the first error

Corruption is almost always caused by the I/O subsystem, and SQL Server tells you the moment it sees it, if someone is listening. Three things make sure someone is.

2a. CHECKDB has succeeded recently

DATABASEPROPERTYEX(name, 'LastGoodCheckDbTime') returns when DBCC CHECKDB last finished without errors. A value of 1900-01-01 means never.

INSERT dba.HealthFinding (CheckName, Severity, ObjectName, Detail)
SELECT 'checkdb', 2, d.name,
       CONCAT('Last clean CHECKDB: ', CONVERT(varchar(19), c.last_good, 120))
FROM sys.databases AS d
CROSS APPLY (SELECT CONVERT(datetime2(0), DATABASEPROPERTYEX(d.name, 'LastGoodCheckDbTime')) AS last_good) AS c
WHERE d.database_id <> 2
  AND d.state_desc = 'ONLINE'
  AND c.last_good < DATEADD(DAY, -7, SYSDATETIME());

2b. Suspect pages

SQL Server writes every page it failed to read to msdb.dbo.suspect_pages. Event types 1–3 are errors (823, bad checksum, torn page); 4, 5 and 7 mean the page was later restored, repaired or deallocated.

INSERT dba.HealthFinding (CheckName, Severity, ObjectName, Detail)
SELECT 'suspect-page', 1, DB_NAME(sp.database_id),
       CONCAT('File ', sp.file_id, ', page ', sp.page_id, ', event type ', sp.event_type,
              ', errors ', sp.error_count, ', last seen ', CONVERT(varchar(19), sp.last_update_date, 120))
FROM msdb.dbo.suspect_pages AS sp
WHERE sp.event_type IN (1, 2, 3);

2c. Agent alerts for errors 823, 824, 825 and severities 17–25

The daily check runs once a day; these alerts fire within seconds. Error 825 deserves special attention: it means a read failed and then succeeded on retry. Nothing broke yet, which makes it the earliest warning you will ever get that a disk is dying.

USE msdb;
GO
EXEC dbo.sp_add_operator @name = N'DBA Team', @email_address = N'dba-team@example.com';

-- I/O errors: 823 (OS read failed), 824 (logical consistency), 825 (read succeeded only on retry)
DECLARE @msg int = 823, @name sysname;
WHILE @msg <= 825
BEGIN
    SET @name = CONCAT(N'Error ', @msg);
    EXEC dbo.sp_add_alert @name = @name, @message_id = @msg, @severity = 0,
         @delay_between_responses = 900, @include_event_description_in = 1;
    EXEC dbo.sp_add_notification @alert_name = @name, @operator_name = N'DBA Team', @notification_method = 1;
    SET @msg += 1;
END;

-- Severity 17-25: resource problems, software errors and fatal errors
DECLARE @sev int = 17;
WHILE @sev <= 25
BEGIN
    SET @name = CONCAT(N'Severity ', @sev);
    EXEC dbo.sp_add_alert @name = @name, @severity = @sev,
         @delay_between_responses = 900, @include_event_description_in = 1;
    EXEC dbo.sp_add_notification @alert_name = @name, @operator_name = N'DBA Team', @notification_method = 1;
    SET @sev += 1;
END;

Under the hood

Agent alerts work by reading the SQL Server error log. An alert on a message ID fires only for errors that are logged, which is why 823, 824 and 825 work (they are always written to the log) while an ordinary error 547 from a failed foreign key does not. @delay_between_responses = 900 stops a failing disk from sending hundreds of emails in a minute.

Check 3: Space runs out slowly, then all at once

3a. Volume free space

sys.dm_os_volume_stats reports the free space of the volume under each database file, so one query covers every drive SQL Server uses.

INSERT dba.HealthFinding (CheckName, Severity, ObjectName, Detail)
SELECT DISTINCT 'disk-free',
       CASE WHEN p.free_pct < 10 THEN 1 ELSE 2 END,
       v.volume_mount_point,
       CONCAT(p.free_pct, '% free (', v.available_bytes / 1073741824, ' GB of ', v.total_bytes / 1073741824, ' GB)')
FROM sys.master_files AS f
CROSS APPLY sys.dm_os_volume_stats(f.database_id, f.file_id) AS v
CROSS APPLY (SELECT CAST(100.0 * v.available_bytes / v.total_bytes AS decimal(5,1)) AS free_pct) AS p
WHERE p.free_pct < 15;

3b. Why the log can't be reused

A transaction log only grows when it can't reuse space it already has. log_reuse_wait_desc says why, and each value has its own fix.

log_reuse_wait_descMeaningUsual fix
LOG_BACKUPFULL recovery, and no log backup since the space was usedFix the log backup job (Check 1b usually fires too)
ACTIVE_TRANSACTIONA long-running or forgotten open transactionFind it (Check 5b) and commit or kill it
REPLICATIONThe log reader hasn't processed the records yetCheck the replication or CDC agents
AVAILABILITY_REPLICAA secondary replica hasn't received or redone the logCheck the replica's health and the network
 
INSERT dba.HealthFinding (CheckName, Severity, ObjectName, Detail)
SELECT 'log-reuse-wait', 2, d.name, CONCAT('Log reuse waiting on ', d.log_reuse_wait_desc)
FROM sys.databases AS d
WHERE d.log_reuse_wait_desc NOT IN ('NOTHING', 'CHECKPOINT')
  AND d.state_desc = 'ONLINE';

3c. Percent growth and too many VLFs

A file that grows by a percentage grows by more each time, and a log that grew in many tiny steps is split into thousands of virtual log files (VLFs), which slows down recovery, restores and log backups. Both are easy to detect and to fix before they matter.

INSERT dba.HealthFinding (CheckName, Severity, ObjectName, Detail)
SELECT 'percent-growth', 2, CONCAT(DB_NAME(f.database_id), '.', f.name),
       CONCAT('Grows by ', f.growth, '%; set a fixed growth in MB instead')
FROM sys.master_files AS f
WHERE f.is_percent_growth = 1;

INSERT dba.HealthFinding (CheckName, Severity, ObjectName, Detail)
SELECT 'vlf-count', 2, d.name, CONCAT(COUNT(*), ' virtual log files')
FROM sys.databases AS d
CROSS APPLY sys.dm_db_log_info(d.database_id) AS li
WHERE d.state_desc = 'ONLINE'
GROUP BY d.name
HAVING COUNT(*) > 1000;
Exercise: a log at 95% with LOG_BACKUP

A database's log is 95% full and log_reuse_wait_desc is LOG_BACKUP. A colleague suggests switching to SIMPLE recovery and shrinking the log. What is wrong with that, and what should you do?

Answer

Switching to SIMPLE breaks the log backup chain: you lose point-in-time recovery until the next full (or differential) backup, which violates the RPO. Instead, take a log backup now (that frees the space for reuse), then find out why the log backup job stopped, since Check 1b should have raised it already. Only shrink if the log grew far beyond its normal size, and then shrink to that normal size, not to zero, so it doesn't have to regrow in small steps (and create more VLFs).

Check 4: Performance against a baseline

"The server is slow" means nothing without a baseline. Two baselines cover most cases: wait statistics for the server as a whole, and Query Store for individual queries.

4a. Wait statistics snapshots

Every time a task has to wait (for a disk read, a lock, a log write, a CPU), SQL Server adds to a counter in sys.dm_os_wait_stats. The counters only ever grow until a restart, so the useful number is the difference between two snapshots.

CREATE TABLE dba.WaitSnapshot (
    CapturedAt          datetime2(0) NOT NULL,
    wait_type           nvarchar(60) NOT NULL,
    waiting_tasks_count bigint       NOT NULL,
    wait_time_ms        bigint       NOT NULL,
    signal_wait_time_ms bigint       NOT NULL,
    CONSTRAINT PK_WaitSnapshot PRIMARY KEY (CapturedAt, wait_type)
);
GO
INSERT dba.WaitSnapshot
SELECT SYSDATETIME(), wait_type, waiting_tasks_count, wait_time_ms, signal_wait_time_ms
FROM sys.dm_os_wait_stats
WHERE wait_time_ms > 0
  -- background waits that are always present and mean nothing (abbreviated list; extend as you meet more)
  AND wait_type NOT IN (N'SLEEP_TASK', N'LAZYWRITER_SLEEP', N'SQLTRACE_BUFFER_FLUSH', N'CHECKPOINT_QUEUE',
                        N'LOGMGR_QUEUE', N'REQUEST_FOR_DEADLOCK_SEARCH', N'XE_TIMER_EVENT', N'XE_DISPATCHER_WAIT',
                        N'BROKER_TO_FLUSH', N'BROKER_TASK_STOP', N'BROKER_EVENTHANDLER', N'BROKER_RECEIVE_WAITFOR',
                        N'CLR_AUTO_EVENT', N'CLR_MANUAL_EVENT', N'DIRTY_PAGE_POLL', N'FT_IFTS_SCHEDULER_IDLE_WAIT',
                        N'HADR_FILESTREAM_IOMGR_IOCOMPLETION', N'SP_SERVER_DIAGNOSTICS_SLEEP', N'WAITFOR',
                        N'QDS_PERSIST_TASK_MAIN_LOOP_SLEEP', N'QDS_ASYNC_QUEUE',
                        N'QDS_CLEANUP_STALE_QUERIES_TASK_MAIN_LOOP_SLEEP', N'SOS_WORK_DISPATCHER',
                        N'ONDEMAND_TASK_QUEUE', N'SLEEP_SYSTEMTASK', N'PWAIT_EXTENSIBILITY_CLEANUP_TASK');
DECLARE @t1 datetime2(0) = (SELECT MAX(CapturedAt) FROM dba.WaitSnapshot);
DECLARE @t0 datetime2(0) = (SELECT MAX(CapturedAt) FROM dba.WaitSnapshot WHERE CapturedAt < @t1);

SELECT TOP (10)
       n.wait_type,
       n.wait_time_ms - ISNULL(o.wait_time_ms, 0)               AS wait_ms,
       n.waiting_tasks_count - ISNULL(o.waiting_tasks_count, 0) AS waits,
       CAST(100.0 * (n.signal_wait_time_ms - ISNULL(o.signal_wait_time_ms, 0))
            / NULLIF(n.wait_time_ms - ISNULL(o.wait_time_ms, 0), 0) AS decimal(5,1)) AS signal_pct
FROM dba.WaitSnapshot AS n
LEFT JOIN dba.WaitSnapshot AS o ON o.wait_type = n.wait_type AND o.CapturedAt = @t0
WHERE n.CapturedAt = @t1
ORDER BY wait_ms DESC;

Compare today's top waits with the same hour last week. A wait that moves up the list is the signal; the absolute numbers matter much less. The common ones point in quite different directions:

Wait typeWhat tasks are waiting forLook at
PAGEIOLATCH_SH / _EXData pages being read from disk into memoryMissing indexes causing scans, memory pressure, storage latency
WRITELOGTransaction log writes to finishLog disk latency, many tiny commits in a loop
LCK_M_*Locks held by another sessionBlocking (Check 5), long transactions
CXPACKET / CXCONSUMERParallel threads of the same queryMAXDOP and cost threshold for parallelism, skewed parallel plans
SOS_SCHEDULER_YIELDA turn on the CPUCPU pressure; a high signal_pct confirms it
RESOURCE_SEMAPHOREA memory grant to start runningQueries with huge sorts or hashes, oversized grants
PAGELATCH_* on tempdbAllocation pages in tempdbNumber of tempdb data files, temp table churn

Restarts reset the counters

After a restart or failover, the new snapshot is smaller than the old one and the differences turn negative. Store sqlserver_start_time from sys.dm_os_sys_info with each snapshot, and skip any pair of snapshots that spans a restart.

4b. Query Store regressions

Query Store records the plans and runtime statistics of every query in a database, and is on by default for new databases in SQL Server 2022. That makes it the perfect baseline for single queries: compare the last 24 hours with the 7 days before.

WITH rs AS (
    SELECT p.query_id, i.start_time, r.avg_duration, r.count_executions
    FROM sys.query_store_runtime_stats AS r
    JOIN sys.query_store_runtime_stats_interval AS i ON i.runtime_stats_interval_id = r.runtime_stats_interval_id
    JOIN sys.query_store_plan AS p ON p.plan_id = r.plan_id
    WHERE i.start_time >= DATEADD(DAY, -8, SYSUTCDATETIME())
),
agg AS (
    SELECT query_id,
           SUM(CASE WHEN start_time >= DATEADD(DAY, -1, SYSUTCDATETIME()) THEN avg_duration * count_executions END)
             / NULLIF(SUM(CASE WHEN start_time >= DATEADD(DAY, -1, SYSUTCDATETIME()) THEN count_executions END), 0) AS recent_us,
           SUM(CASE WHEN start_time <  DATEADD(DAY, -1, SYSUTCDATETIME()) THEN avg_duration * count_executions END)
             / NULLIF(SUM(CASE WHEN start_time <  DATEADD(DAY, -1, SYSUTCDATETIME()) THEN count_executions END), 0) AS baseline_us,
           SUM(CASE WHEN start_time >= DATEADD(DAY, -1, SYSUTCDATETIME()) THEN count_executions END) AS recent_execs
    FROM rs
    GROUP BY query_id
)
SELECT TOP (20)
       a.query_id, a.recent_execs,
       CAST(a.baseline_us / 1000 AS decimal(12,1)) AS baseline_ms,
       CAST(a.recent_us   / 1000 AS decimal(12,1)) AS recent_ms,
       CAST(a.recent_us / a.baseline_us AS decimal(8,1)) AS slowdown,
       LEFT(qt.query_sql_text, 200) AS query_text
FROM agg AS a
JOIN sys.query_store_query      AS q  ON q.query_id = a.query_id
JOIN sys.query_store_query_text AS qt ON qt.query_text_id = q.query_text_id
WHERE a.recent_us > 2 * a.baseline_us
  AND a.recent_execs >= 10                    -- ignore one-off queries
ORDER BY (a.recent_us - a.baseline_us) * a.recent_execs DESC;   -- total extra time, not just the ratio

Durations in Query Store are in microseconds, and averages are weighted by executions so a busy hour counts more than a quiet one. The final ORDER BY ranks by total extra time: a query that went from 2 ms to 5 ms but runs a million times a day costs more than a nightly report that went from 1 to 3 minutes.

When the cause is a plan change, compare the plans in sys.query_store_plan and, as a stop-gap, force the good one with EXEC sp_query_store_force_plan @query_id = …, @plan_id = …;. Then fix the root cause (usually stale statistics, Check 6, or parameter sensitivity), because a forced plan is a decision someone has to remember.

Let SQL Server do the first response

On Enterprise and Developer editions, ALTER DATABASE CURRENT SET AUTOMATIC_TUNING (FORCE_LAST_GOOD_PLAN = ON); makes SQL Server detect plan-choice regressions itself and revert to the last good plan. The check above still matters: it catches regressions that aren't plan changes, and it tells you what automatic tuning did.

Check 5: Blocking and long transactions

5a. Who is blocking whom

-- Requests that are waiting on another session
SELECT r.session_id, r.blocking_session_id, r.wait_type, r.wait_time / 1000 AS wait_s,
       DB_NAME(r.database_id) AS db, s.login_name, s.host_name, s.program_name,
       LEFT(t.text, 200) AS sql_text
FROM sys.dm_exec_requests AS r
JOIN sys.dm_exec_sessions AS s ON s.session_id = r.session_id
CROSS APPLY sys.dm_exec_sql_text(r.sql_handle) AS t
WHERE r.blocking_session_id <> 0
ORDER BY r.wait_time DESC;

-- Head blockers: block others but are not blocked themselves (often "sleeping" with an open transaction)
SELECT s.session_id, s.status, s.login_name, s.host_name, s.program_name,
       s.open_transaction_count, s.last_request_end_time
FROM sys.dm_exec_sessions AS s
WHERE s.session_id IN (SELECT blocking_session_id FROM sys.dm_exec_requests WHERE blocking_session_id <> 0)
  AND s.session_id NOT IN (SELECT session_id FROM sys.dm_exec_requests WHERE blocking_session_id <> 0);

A head blocker with status sleeping and open_transaction_count > 0 is the classic case: an application opened a transaction, did some work and never committed. It isn't running anything, so it never shows up in a "top CPU" view, yet it holds its locks indefinitely.

Querying the DMVs only shows blocking that is happening right now. To catch blocking that happened at 03:00, let SQL Server report it: set a threshold, and capture the report with Extended Events.

EXEC sp_configure 'show advanced options', 1;  RECONFIGURE;
EXEC sp_configure 'blocked process threshold (s)', 20;  RECONFIGURE;   -- report blocks longer than 20 s

CREATE EVENT SESSION blocked_process ON SERVER
ADD EVENT sqlserver.blocked_process_report
ADD TARGET package0.event_file (SET filename = N'blocked_process')
WITH (STARTUP_STATE = ON);
ALTER EVENT SESSION blocked_process ON SERVER STATE = START;

Deadlocks need no setup: the built-in system_health session already records every xml_deadlock_report.

5b. Transactions open too long

INSERT dba.HealthFinding (CheckName, Severity, ObjectName, Detail)
SELECT 'long-transaction', 2, CONCAT('session ', st.session_id),
       CONCAT('Open for ', DATEDIFF(MINUTE, at.transaction_begin_time, SYSDATETIME()),
              ' min, login ', s.login_name, ', host ', s.host_name, ', program ', s.program_name)
FROM sys.dm_tran_active_transactions AS at
JOIN sys.dm_tran_session_transactions AS st ON st.transaction_id = at.transaction_id
JOIN sys.dm_exec_sessions AS s ON s.session_id = st.session_id
WHERE at.transaction_begin_time < DATEADD(MINUTE, -15, SYSDATETIME());

Check 6: Statistics that drifted

The optimizer picks plans from statistics. When a table changes a lot but its statistics don't, the row estimates go wrong and so do the plans: the most common root cause of a Query Store regression. sys.dm_db_stats_properties shows how many rows changed since each statistic was last updated.

SELECT OBJECT_SCHEMA_NAME(s.object_id) AS schema_name,
       OBJECT_NAME(s.object_id)        AS table_name,
       s.name                          AS stat_name,
       sp.last_updated, sp.rows, sp.modification_counter,
       CAST(100.0 * sp.modification_counter / NULLIF(sp.rows, 0) AS decimal(7,1)) AS pct_changed
FROM sys.stats AS s
CROSS APPLY sys.dm_db_stats_properties(s.object_id, s.stats_id) AS sp
WHERE OBJECTPROPERTY(s.object_id, 'IsUserTable') = 1
  AND sp.rows > 10000
  AND sp.modification_counter > 0.1 * sp.rows
ORDER BY pct_changed DESC;

Under the hood

From compatibility level 130 (SQL Server 2016), automatic statistics updates use a dynamic threshold of roughly √(1000 × rows) modifications instead of a fixed 20%. A 100-million-row table now refreshes after about 316,000 changes instead of 20 million. Auto-update still only triggers when a query reads the statistic, though, so a scheduled update after big loads, the job of index and statistics maintenance, is still worth having. On SSD storage, keep that job focused on statistics; rebuilding indexes just because of fragmentation rarely pays for itself.

Check 7: Security drift and failed jobs

Two cheap checks catch things that otherwise surface only in an audit or a missed load.

CREATE TABLE dba.ApprovedSysadmin (LoginName sysname PRIMARY KEY);   -- fill once, review on change

INSERT dba.HealthFinding (CheckName, Severity, ObjectName, Detail)
SELECT 'sysadmin-drift', 1, m.name, CONCAT('Unapproved sysadmin (', m.type_desc, ')')
FROM sys.server_role_members AS rm
JOIN sys.server_principals AS r ON r.principal_id = rm.role_principal_id
JOIN sys.server_principals AS m ON m.principal_id = rm.member_principal_id
WHERE r.name = 'sysadmin'
  AND m.name NOT IN (SELECT LoginName FROM dba.ApprovedSysadmin);

INSERT dba.HealthFinding (CheckName, Severity, ObjectName, Detail)
SELECT 'sa-enabled', 2, name, 'The sa login (principal_id 1) is enabled'
FROM sys.sql_logins
WHERE principal_id = 1 AND is_disabled = 0;
INSERT dba.HealthFinding (CheckName, Severity, ObjectName, Detail)
SELECT 'job-failed', 2, j.name,
       CONCAT('Step ', h.step_id, ' (', h.step_name, ') failed at ',
              CONVERT(varchar(19), msdb.dbo.agent_datetime(h.run_date, h.run_time), 120), ': ', LEFT(h.message, 300))
FROM msdb.dbo.sysjobhistory AS h
JOIN msdb.dbo.sysjobs AS j ON j.job_id = h.job_id
WHERE h.run_status = 0          -- 0 = failed
  AND h.step_id > 0             -- step rows, not the job outcome row
  AND msdb.dbo.agent_datetime(h.run_date, h.run_time) >= DATEADD(DAY, -1, GETDATE());

sysjobhistory stores dates and times as integers (20261030, 61500). msdb.dbo.agent_datetime converts them; it is undocumented but has shipped in msdb for many versions. If you'd rather avoid it, compare run_date as an integer.

Check 8: Defragmentation

An index can be fragmented in two different ways, and they don't hurt in the same way:

KindWhat it isWhat it costsDMV column
Low page density (internal)Pages are partly empty, usually after page splits or deletesMore pages to read and to cache for the same rows: more I/O and more memory, on any storageavg_page_space_used_in_percent
Logical fragmentation (external)The order of pages on disk differs from the order of the keysRange scans can't use large sequential reads. Matters on spinning disks; much less on SSDavg_fragmentation_in_percent

That is why the old rule "reorganize above 5%, rebuild above 30%" is only a starting point. A rebuild rewrites the whole index, generates a lot of transaction log and can block, so do it where it pays off: large indexes with low page density, or heavily range-scanned indexes on slow storage.

SELECT OBJECT_SCHEMA_NAME(ips.object_id) AS schema_name,
       OBJECT_NAME(ips.object_id)        AS table_name,
       i.name                            AS index_name,
       ips.page_count,
       CAST(ips.avg_fragmentation_in_percent   AS decimal(5,1)) AS frag_pct,
       CAST(ips.avg_page_space_used_in_percent AS decimal(5,1)) AS page_density_pct,
       CASE WHEN ips.avg_page_space_used_in_percent < 70 OR ips.avg_fragmentation_in_percent > 30
            THEN CONCAT('ALTER INDEX ', QUOTENAME(i.name), ' ON ', QUOTENAME(OBJECT_SCHEMA_NAME(ips.object_id)), '.',
                        QUOTENAME(OBJECT_NAME(ips.object_id)), ' REBUILD WITH (ONLINE = ON, RESUMABLE = ON, MAXDOP = 4);')
            WHEN ips.avg_fragmentation_in_percent > 5
            THEN CONCAT('ALTER INDEX ', QUOTENAME(i.name), ' ON ', QUOTENAME(OBJECT_SCHEMA_NAME(ips.object_id)), '.',
                        QUOTENAME(OBJECT_NAME(ips.object_id)), ' REORGANIZE;')
       END AS suggested_action
FROM sys.dm_db_index_physical_stats(DB_ID(), NULL, NULL, NULL, 'SAMPLED') AS ips
JOIN sys.indexes AS i ON i.object_id = ips.object_id AND i.index_id = ips.index_id
WHERE ips.page_count > 1000                                   -- small indexes: not worth the effort
  AND ips.index_type_desc IN ('CLUSTERED INDEX', 'NONCLUSTERED INDEX')
  AND ips.alloc_unit_type_desc = 'IN_ROW_DATA'
ORDER BY ips.page_count * (100 - ips.avg_page_space_used_in_percent) DESC;   -- most wasted space first

'SAMPLED' reads about 1% of the pages of large indexes, enough for page density and far cheaper than 'DETAILED'. ('LIMITED' is cheaper still but returns no page density.) Run the check weekly, off-peak, and store the results so you can see which indexes fragment again within days: those need a FILLFACTOR below 100, or a better key, not more rebuilds.

8b. Columnstore indexes

Columnstore indexes (the lab's fact tables use them) fragment differently: deleted and updated rows are only marked as deleted, and trickle inserts leave small, open row groups. Check the row groups and reorganize when a table has many deleted rows or small row groups.

SELECT OBJECT_SCHEMA_NAME(rg.object_id) AS schema_name,
       OBJECT_NAME(rg.object_id)        AS table_name,
       rg.state_desc,
       COUNT(*)                         AS row_groups,
       SUM(rg.total_rows)               AS total_rows,
       SUM(rg.deleted_rows)             AS deleted_rows,
       CAST(100.0 * SUM(rg.deleted_rows) / NULLIF(SUM(rg.total_rows), 0) AS decimal(5,1)) AS deleted_pct
FROM sys.dm_db_column_store_row_group_physical_stats AS rg
GROUP BY rg.object_id, rg.state_desc
ORDER BY deleted_rows DESC;

-- Merge small row groups, remove deleted rows, and compress open (delta store) row groups
ALTER INDEX CCI_FactSale ON dbo.FactSale REORGANIZE WITH (COMPRESS_ALL_ROW_GROUPS = ON);

Don't write your own maintenance job from scratch

The free, open-source Ola Hallengren Maintenance Solution (IndexOptimize) implements exactly this logic, with thresholds for fragmentation and page count, online rebuilds when the edition allows, a time limit for the maintenance window, and logging. It is the de facto standard; use the query above to understand and tune what it does.

Check 9: Reclaiming space

Deleting rows does not make a database file smaller. The freed pages stay inside the file and are reused by new data. That is usually exactly what you want: a file that shrinks today has to grow again tomorrow, and both operations cost time. Reclaiming space is the right move only after a one-off change, such as archiving years of history or dropping a large table, and only if the space is needed elsewhere.

9a. Where the free space is

SELECT name, type_desc,
       CAST(size / 128.0                                 AS decimal(12,1)) AS size_mb,
       CAST(FILEPROPERTY(name, 'SpaceUsed') / 128.0      AS decimal(12,1)) AS used_mb,
       CAST((size - FILEPROPERTY(name, 'SpaceUsed')) / 128.0 AS decimal(12,1)) AS free_mb
FROM sys.database_files;      -- size and SpaceUsed are 8 KB pages; 128 pages = 1 MB

9b. Space that deleting doesn't free

  • Heaps. A DELETE on a table without a clustered index can leave empty pages allocated to it. Use DELETE … WITH (TABLOCK) for large deletes, or rebuild the heap: ALTER TABLE dbo.StagingOrders REBUILD;. Heaps also collect forwarded records when rows grow, and the same rebuild removes them.
  • Dropped columns. Dropping a variable-length column only removes it from the metadata. DBCC CLEANTABLE (N'SalesDB', N'dbo.Orders'); reclaims the space; rebuilding the clustered index does too.
  • Low page density. An index whose pages are half empty holds twice the space it needs: Check 8's rebuild returns that space to the file.
  • Compression. Often the biggest win, with no data removed. Estimate it first with EXEC sp_estimate_data_compression_savings 'dbo', 'Orders', NULL, NULL, 'PAGE';, then rebuild with DATA_COMPRESSION = PAGE.
  • Old data. On a partitioned table, TRUNCATE TABLE dbo.Orders WITH (PARTITIONS (1 TO 3)); removes old partitions almost instantly, without logging every row.

9c. Shrinking a file, carefully

When the space really has to go back to the operating system, shrink in this order:

-- 1. Release only the free space at the END of the file. Moves no pages, so it causes no fragmentation.
DBCC SHRINKFILE (N'SalesDB_Data', TRUNCATEONLY);

-- 2. Still too big? Shrink to a target size in MB, in steps of a few GB rather than all at once.
--    WAIT_AT_LOW_PRIORITY (SQL Server 2022) stops the shrink from blocking user queries while it waits for locks.
DBCC SHRINKFILE (N'SalesDB_Data', 51200) WITH WAIT_AT_LOW_PRIORITY;

-- 3. A shrink moves pages from the end of the file into the first free slots it finds, which fragments
--    the indexes badly. REORGANIZE them afterwards (a REBUILD would need free space and grow the file again).
ALTER INDEX ALL ON dbo.Orders REORGANIZE;
-- First remove the cause (Check 3b). Then back up the log so the space can be reused, and shrink to the
-- NORMAL working size, not to zero: a log shrunk to nothing regrows in small steps and creates many VLFs.
BACKUP LOG SalesDB TO DISK = N'/var/opt/mssql/backup/SalesDB_log.trn' WITH CHECKSUM;
DBCC SHRINKFILE (N'SalesDB_log', 8192);
ALTER DATABASE SalesDB MODIFY FILE (NAME = N'SalesDB_log', FILEGROWTH = 1024MB);

Never schedule a shrink, and never turn on AUTO_SHRINK

A recurring shrink job and AUTO_SHRINK both do the same harmful thing: shrink the file, fragment every index, let the file grow back, repeat. The server spends its time moving pages back and forth while queries get slower. Add it to the health check:

INSERT dba.HealthFinding (CheckName, Severity, ObjectName, Detail)
SELECT 'auto-shrink', 2, name, 'AUTO_SHRINK is ON: ALTER DATABASE ... SET AUTO_SHRINK OFF'
FROM sys.databases
WHERE is_auto_shrink_on = 1;

-- Info only: a data file larger than 10 GB that is more than half empty (run in each user database)
INSERT DBAdmin.dba.HealthFinding (CheckName, Severity, ObjectName, Detail)
SELECT 'file-mostly-empty', 3, CONCAT(DB_NAME(), '.', name),
       CONCAT(CAST((size - FILEPROPERTY(name, 'SpaceUsed')) / 128 AS bigint), ' MB free of ', size / 128, ' MB')
FROM sys.database_files
WHERE type_desc = 'ROWS'
  AND size / 128 > 10240
  AND FILEPROPERTY(name, 'SpaceUsed') < size / 2;

Putting it together

Wrap the checks in one procedure, run it every morning, and email only when there is a critical finding.

USE DBAdmin;
GO
CREATE OR ALTER PROCEDURE dba.usp_HealthCheck
AS
BEGIN
    SET NOCOUNT ON;
    DECLARE @run datetime2(0) = SYSDATETIME();

    -- Paste the INSERT statements of Checks 1a, 1b, 2a, 2b, 3a, 3b, 3c, 5b, 7a, 7b and 9 (auto-shrink) here.
    -- Checks 4b, 6, 8 and 9 (file space) read per-database views: loop over the user databases, or run them
    -- from the scheduler in each database and insert into DBAdmin.dba.HealthFinding.

    IF EXISTS (SELECT 1 FROM dba.HealthFinding WHERE CheckedAt >= @run AND Severity = 1)
        EXEC msdb.dbo.sp_send_dbmail
             @profile_name = N'DBA',
             @recipients   = N'dba-team@example.com',
             @subject      = N'SQL Server health check: critical findings',
             @query        = N'SELECT CheckName, ObjectName, Detail
                               FROM DBAdmin.dba.HealthFinding
                               WHERE Severity = 1 AND CheckedAt >= DATEADD(HOUR, -1, SYSDATETIME())';
END;

Schedule it with SQL Server Agent:

USE msdb;
GO
EXEC dbo.sp_add_job        @job_name = N'DBA - Daily health check';
EXEC dbo.sp_add_jobstep    @job_name = N'DBA - Daily health check', @step_name = N'Run checks',
                           @subsystem = N'TSQL', @database_name = N'DBAdmin',
                           @command = N'EXEC dba.usp_HealthCheck;';
EXEC dbo.sp_add_jobschedule @job_name = N'DBA - Daily health check', @name = N'Daily 06:00',
                           @freq_type = 4, @freq_interval = 1, @active_start_time = 060000;
EXEC dbo.sp_add_jobserver  @job_name = N'DBA - Daily health check';

Or, if Airflow already runs your data platform (as in the Data Warehousing track), add a daily DAG with one BashOperator that runs sqlcmd -S <server> -d DBAdmin -Q "EXEC dba.usp_HealthCheck". You then get Airflow's retries, history and failure alerts for the health check itself, and the check can't silently stop running, which is exactly the failure this chapter is about.

The weekly review is one query: findings of the last 7 days grouped by check and object, so a warning that appears every day stands out from one that appeared once.

SELECT CheckName, ObjectName, MIN(Severity) AS worst_severity,
       COUNT(DISTINCT CAST(CheckedAt AS date)) AS days_seen, MAX(Detail) AS latest_detail
FROM dba.HealthFinding
WHERE CheckedAt >= DATEADD(DAY, -7, SYSDATETIME())
GROUP BY CheckName, ObjectName
ORDER BY worst_severity, days_seen DESC;
Exercise: the health check that never alerted

For a month, nobody received a health-check email, and everyone assumed the servers were healthy. Then a disk filled up. Name two ways the setup in this chapter could have failed silently, and how to guard against each.

Answer

(1) The job itself stopped running (disabled, Agent stopped, the server was rebuilt without it). Guard: monitor the monitor, for example with a "heartbeat" row written on every run and a check from a second system (Airflow, or another server) that alerts when the latest heartbeat is older than a day. (2) The email couldn't be sent (Database Mail profile broken, SMTP password expired). Guard: check msdb.dbo.sysmail_faileditems as part of the health check, and send a short "all clear" summary once a week so silence is never mistaken for health.

Key takeaways

  • Proactive administration means running the checks on a schedule and acting on trends, before users feel anything.
  • Write every finding to a table with a severity; alert only on critical ones, and review warnings weekly.
  • Backups: check their age against the RPO, take them WITH CHECKSUM, and test restores.
  • Corruption: alert on 823, 824 and 825 within seconds, and make sure CHECKDB succeeds weekly.
  • Space: watch volume free space, log_reuse_wait_desc, percent growth and VLF counts.
  • Performance needs a baseline: wait-statistics snapshots for the server, Query Store for each query.
  • Defragment by page density and benefit, not by a fixed percentage: reorganize is cheap and online, rebuild rewrites everything.
  • Deleted rows free space inside the file, not on disk. Shrink only after a one-off change, never on a schedule, and reorganize afterwards.
  • Monitor the monitor: a health check that silently stopped is worse than none.
