Chapter 02

Proactive Amazon Redshift Administration

On Redshift, AWS takes care of the hardware, patching and backups. What it can't take care of is your data and your workload: tables that skew across slices, sort order that decays with every load, statistics that go stale, queries that queue behind each other or spill to disk. This chapter builds the Redshift version of the daily health check from Chapter 1.

~40 min read Provisioned (RA3) and Serverless Tools: SYS, SVV and STL system views, WLM, CloudWatch

What changes from SQL Server

Redshift is a managed, massively parallel (MPP), columnar database. Some of Chapter 1's checks disappear, and new ones take their place.

AreaSQL Server (Chapter 1)Amazon Redshift
BackupsYou schedule and verify themAutomated snapshots; you choose the retention period and cross-Region copy
CorruptionCHECKDB and I/O alertsHandled by the service (data is replicated within the cluster and backed up to S3)
Data layoutIndexesDistribution style and sort keys: skew and unsorted rows are new failure modes
Space reclaimLog reuse, file growthVACUUM: deleted rows stay on disk until vacuumed
ConcurrencyLocks and blockingWorkload management (WLM) queues, plus locks on whole tables
Bad queriesQuery Store regressionsAlert events, query monitoring rules, disk-based (spilled) steps

Provisioned vs. Serverless: which system views exist

Redshift has several families of system views. The SYS_* monitoring views work on both provisioned clusters and Serverless, so prefer them. The older STL_*, STV_* and SVL_* views exist only on provisioned clusters. Each check below says which family it uses. SVV_* views such as SVV_TABLE_INFO work on both.

Where findings go

The same idea as Chapter 1: every check produces findings with a severity, stored in a table so you can trend them.

CREATE SCHEMA IF NOT EXISTS dba;

CREATE TABLE IF NOT EXISTS dba.health_finding (
    checked_at   TIMESTAMP     DEFAULT SYSDATE,
    check_name   VARCHAR(60)   NOT NULL,
    severity     SMALLINT      NOT NULL,      -- 1 critical, 2 warning, 3 info
    object_name  VARCHAR(256),
    detail       VARCHAR(4000) NOT NULL
)
DISTSTYLE ALL;

Some system views can't feed an INSERT … SELECT

Many Redshift catalog and system views are computed on the leader node only, and Redshift refuses queries that mix leader-node-only data with user tables, which live on the compute nodes. If INSERT INTO dba.health_finding SELECT … FROM <system view> fails with a "leader node" error, run the SELECT from your scheduler instead and write the rows back with a second statement. The Airflow job at the end of the chapter does exactly that, so every check below is written as a plain SELECT.

Check 1: Table health

SVV_TABLE_INFO has one row per table and most of what you need to know about its physical health.

SELECT "schema", "table", tbl_rows,
       size       AS size_mb,          -- 1 MB blocks
       pct_used,                        -- % of the cluster's storage
       unsorted,                        -- % of rows not in sort-key order
       stats_off,                       -- how stale the statistics are (0 = current, 100 = completely stale)
       skew_rows,                       -- rows on the fullest slice / rows on the emptiest slice
       encoded, diststyle, sortkey1
FROM svv_table_info
WHERE unsorted  > 20
   OR stats_off > 10
   OR skew_rows > 4
   OR encoded LIKE 'N%'
ORDER BY size DESC;
ColumnWhy it hurtsUsual fix
skew_rows highOne slice holds far more rows than the others. Every query waits for the slowest slice, so the cluster runs at the speed of that one slice.Choose a distribution key with many distinct, evenly spread values, or use DISTSTYLE AUTO / EVEN.
unsorted highNew rows are appended unsorted. Zone maps (min/max per block) stop pruning blocks, so range filters scan more data.VACUUM SORT ONLY, or rely on automatic vacuum sort for tables with SORTKEY AUTO.
stats_off highThe planner estimates row counts from stale statistics and picks bad join orders and distributions.ANALYZE the table, ideally PREDICATE COLUMNS only.
encoded = NColumns are stored uncompressed: more disk, more I/O, less in cache.ALTER TABLE … ALTER COLUMN … ENCODE AZ64 (or ENCODE AUTO).

Under the hood

Redshift stores each column in 1 MB blocks and keeps the minimum and maximum value of every block in memory (the zone map). A filter like WHERE sale_date = '2026-10-01' skips every block whose range doesn't include that date. That works beautifully on data sorted by sale_date, because each block covers a narrow range. On unsorted data every block covers almost the full range, nothing can be skipped, and the same query reads the whole column. That is why unsorted is a performance metric, not just housekeeping.

Check 2: Vacuum and analyze keep up with the loads

Redshift runs automatic vacuum delete, automatic vacuum sort and automatic analyze in the background when the cluster is quiet. For most tables that is enough. The proactive part is spotting the tables where it isn't: large tables loaded every hour on a cluster that is never quiet.

-- Vacuums that ran recently, automatic and manual
SELECT schema_name, table_name, vacuum_type, is_automatic, status, start_time, end_time
FROM sys_vacuum_history
ORDER BY start_time DESC
LIMIT 20;

-- Where sorting pays off most: SVV_TABLE_INFO estimates the benefit of a sort
SELECT "schema", "table", unsorted, vacuum_sort_benefit, tbl_rows
FROM svv_table_info
WHERE vacuum_sort_benefit > 0
ORDER BY vacuum_sort_benefit DESC
LIMIT 20;
VACUUM SORT ONLY sales.fact_sale TO 99 PERCENT;     -- re-sort without reclaiming deletes
VACUUM DELETE ONLY sales.fact_sale;                  -- reclaim space of deleted and updated rows
ANALYZE sales.fact_sale PREDICATE COLUMNS;           -- statistics only for columns used in filters and joins

Updates are deletes plus inserts

Redshift never changes a row in place: an UPDATE marks the old version deleted and appends a new one. A daily MERGE that touches 10% of a table therefore leaves 10% of the table as dead rows and appends 10% unsorted. If a table has a steady stream of updates, check both unsorted and its size trend every day.

Check 3: Queueing and slow queries

SYS_QUERY_HISTORY (provisioned and Serverless) records every query with its queue time and execution time, both in microseconds. Trend them by hour: the signal is queue time rising while the query mix stays the same.

SELECT DATE_TRUNC('hour', start_time)                          AS hour,
       COUNT(*)                                                  AS queries,
       ROUND(AVG(queue_time)     / 1000000.0, 2)                 AS avg_queue_s,
       ROUND(MAX(queue_time)     / 1000000.0, 1)                 AS max_queue_s,
       ROUND(AVG(execution_time) / 1000000.0, 2)                 AS avg_exec_s,
       SUM(CASE WHEN status = 'failed' THEN 1 ELSE 0 END)        AS failed
FROM sys_query_history
WHERE start_time >= DATEADD(day, -7, SYSDATE)
GROUP BY 1
ORDER BY 1;
SELECT query_id, user_id, database_name, query_type, status, start_time,
       ROUND(elapsed_time / 1000000.0, 1) AS elapsed_s,
       ROUND(queue_time   / 1000000.0, 1) AS queue_s,
       LEFT(query_text, 150)              AS query_text
FROM sys_query_history
WHERE start_time >= DATEADD(hour, -24, SYSDATE)
ORDER BY elapsed_time DESC
LIMIT 20;

3c. What the planner itself complained about

On provisioned clusters, Redshift writes an alert event whenever the query engine sees a known anti-pattern while running a query, together with a suggested solution. Grouping them by event is one of the highest-value checks you can run.

SELECT TRIM(event)          AS event,
       TRIM(solution)       AS solution,
       COUNT(DISTINCT query) AS queries,
       MAX(event_time)      AS last_seen
FROM stl_alert_event_log
WHERE event_time >= DATEADD(day, -7, SYSDATE)
GROUP BY 1, 2
ORDER BY queries DESC;
Typical eventWhat it means
Missing query planner statisticsA table was never analyzed or is very stale: Check 1's stats_off
Nested Loop Join in the query planUsually a missing or wrong join condition producing a cross join
Distributed a large number of rows across the networkJoined tables aren't co-located: distribution keys don't match the join
Scanned a large number of deleted rowsThe table needs VACUUM DELETE: Check 2
Very selective query filterA filter that a sort key would serve well

Check 4: Workload management guards the cluster

WLM decides which queries run, in which queue and with how much memory. With automatic WLM (the default), Redshift manages concurrency and memory itself, and you set priorities per queue (for example, dashboards HIGH, ad hoc analysts NORMAL, batch loads LOW).

The proactive tool is query monitoring rules (QMR): a predicate on a query's runtime metrics plus an action (log, hop, change_query_priority or abort). They live in the wlm_json_configuration parameter of the cluster's parameter group. Start every new rule with log, look at what it would have caught, and only then switch it to abort.

"rules": [
  {
    "rule_name": "log_runaway_nested_loop",
    "predicate": [ { "metric_name": "nested_loop_join_row_count", "operator": ">", "value": 100000000 } ],
    "action": "log"
  },
  {
    "rule_name": "abort_huge_spill",
    "predicate": [ { "metric_name": "query_temp_blocks_to_disk", "operator": ">", "value": 500000 } ],
    "action": "abort"
  }
]
SELECT TRIM(rule) AS rule, TRIM(action) AS action, service_class,
       COUNT(*) AS times, MAX(recordtime) AS last_fired
FROM stl_wlm_rule_action
WHERE recordtime >= DATEADD(day, -7, SYSDATE)
GROUP BY 1, 2, 3
ORDER BY times DESC;

On Serverless there are no WLM queues to configure; instead you set query limits on the workgroup (for example a maximum run time) and control cost with the base and maximum RPU capacity. The SYS_QUERY_HISTORY checks above apply unchanged.

Check 5: Disk space and spills

When a query step doesn't fit in its memory, it spills intermediate results to disk: it gets slower, and on a busy cluster it can fill the disk for everyone. On provisioned clusters, first watch total usage, then find the queries that spill.

-- Total storage used across all nodes (in 1 MB blocks, shown in GB)
SELECT SUM(capacity) / 1024                         AS capacity_gb,
       SUM(used) / 1024                             AS used_gb,
       ROUND(100.0 * SUM(used) / SUM(capacity), 1) AS used_pct
FROM stv_partitions
WHERE part_begin = 0;

-- Queries whose steps spilled to disk
SELECT query,
       COUNT(*)                     AS disk_based_steps,
       MAX(workmem) / 1048576       AS max_workmem_mb
FROM svl_query_summary
WHERE is_diskbased = 't'
GROUP BY query
ORDER BY disk_based_steps DESC
LIMIT 20;

Spills usually come from one of three things: a join on a column that isn't the distribution key (huge redistribution), a SELECT DISTINCT or GROUP BY over very wide rows, or too many queries running at once in a queue with a fixed memory split. Fix the query first; giving the queue more memory hides the problem until the data grows again.

Check 6: Long transactions and locks

Redshift locks whole tables, and an open transaction has two hidden costs: it blocks DDL and conflicting writes on the tables it touched, and it stops VACUUM from reclaiming rows deleted after it began, because that transaction might still need to see them.

SELECT txn_owner, txn_db, xid, pid, txn_start,
       DATEDIFF(minute, txn_start, SYSDATE) AS open_min,
       lock_mode, relation, granted
FROM svv_transactions
WHERE txn_start < DATEADD(minute, -30, SYSDATE)
   OR granted = 'f'                      -- someone is waiting for this lock
ORDER BY txn_start;

When a forgotten session holds the lock everyone else needs, end it with SELECT pg_terminate_backend(<pid>);. Its open transaction rolls back. Then find out which tool left it open; BI tools that start a transaction and keep the connection idle are a frequent cause.

Check 7: Load errors

A COPY with MAXERROR greater than zero succeeds even when some rows are rejected. Without a check, those rows are simply missing from the warehouse.

SELECT start_time, database_name, TRIM(file_name) AS file_name, line_number,
       TRIM(column_name) AS column_name, error_code, TRIM(error_message) AS error_message
FROM sys_load_error_detail
WHERE start_time >= DATEADD(day, -1, SYSDATE)
ORDER BY start_time DESC
LIMIT 50;

Reconcile, don't just count errors

Rejected rows are only one way to lose data; a file that was never delivered rejects nothing. Pair this check with row-count reconciliation against the source, as in the Snowflake track's reconciliation chapter: the same idea works on Redshift.

Check 8: Let Redshift recommend

Redshift analyses your workload and recommends distribution and sort keys. SVV_ALTER_TABLE_RECOMMENDATIONS lists them with the exact ALTER TABLE statement. If auto_eligible is true and the table uses AUTO settings, automatic table optimization applies them in the background; otherwise it is your decision.

SELECT type, database, table_id, ddl, auto_eligible
FROM svv_alter_table_recommendations
ORDER BY table_id;

Check 9: Defragmentation: restoring sort order

Redshift has no indexes to fragment. Its equivalent is sort order: every load appends rows to an unsorted region at the end of each slice, and every update or delete leaves dead rows behind. Both make zone maps less effective (Check 1), so "defragmenting" a Redshift table means re-sorting it, and reclaiming space means removing the dead rows. One command, VACUUM, does both, in several variants.

SELECT "schema", "table",
       size                                AS size_mb,
       tbl_rows,                            -- includes rows marked deleted but not yet vacuumed
       estimated_visible_rows,
       tbl_rows - estimated_visible_rows   AS dead_rows_est,
       unsorted,
       vacuum_sort_benefit
FROM svv_table_info
WHERE unsorted > 10
   OR tbl_rows - estimated_visible_rows > 0.1 * tbl_rows
ORDER BY size DESC;
CommandWhat it doesUse it when
VACUUM table (= FULL)Re-sorts and reclaims dead rows, by default until the table is 95% sortedA table has both problems, typically after a large MERGE
VACUUM SORT ONLYRe-sorts, leaves dead rowsAppend-only tables (hourly COPY) that rarely delete
VACUUM DELETE ONLYReclaims dead rows, doesn't sortSpace is the problem, sort order is fine (Check 10)
VACUUM RECLUSTERSorts only the unsorted portion, without merging it into the sorted regionVery large tables with frequent loads, where a full merge would take hours
VACUUM REINDEXRe-analyses the value distribution of an interleaved sort key, then runs a full vacuumTables with interleaved sort keys only; the slowest variant
 
VACUUM SORT ONLY sales.fact_sale TO 99 PERCENT;   -- stop at 99% sorted instead of the default 95%
VACUUM DELETE ONLY sales.fact_sale TO 100 PERCENT;
ANALYZE sales.fact_sale PREDICATE COLUMNS;

-- In a maintenance window: BOOST gives the vacuum more resources, at the cost of concurrent queries
VACUUM FULL sales.fact_sale BOOST;

Rules that trip people up

Only one VACUUM can run on a cluster at a time, so schedule them one after another rather than in parallel tasks. VACUUM can't run inside a transaction block (no BEGIN … END around it). It needs free disk space to sort. And it can't reclaim rows that a still-open transaction might need to see, which is one more reason to watch long transactions (Check 6). On provisioned clusters, SVV_VACUUM_PROGRESS shows how far a running vacuum has got.

When a deep copy beats vacuum

For a table that is badly unsorted (say, more than 50%) or mostly dead rows, a deep copy is often much faster than vacuum: a bulk insert into an empty table sorts the data as it writes it, in one pass.

CREATE TABLE sales.fact_sale_new (LIKE sales.fact_sale);   -- same columns, distribution, sort key and encoding
INSERT INTO sales.fact_sale_new SELECT * FROM sales.fact_sale;

BEGIN;
ALTER TABLE sales.fact_sale     RENAME TO fact_sale_old;
ALTER TABLE sales.fact_sale_new RENAME TO fact_sale;
COMMIT;

DROP TABLE sales.fact_sale_old;

Three things to plan for: the copy needs free space for a second copy of the table; grants are not copied by LIKE, so re-apply them; and ordinary views are bound to the original table, so after the rename they would point at fact_sale_old. Recreate them, or use late-binding views (WITH NO SCHEMA BINDING), which look the table up by name.

Check 10: Reclaiming space

On RA3 nodes and Serverless, storage is managed storage billed per GB, so reclaimed space is money saved, not only headroom. The space goes to dead rows, uncompressed columns and data nobody queries any more.

  • Dead rows. Automatic vacuum delete reclaims them in the background when the cluster is quiet. For tables that are updated all day, schedule VACUUM DELETE ONLY after the heaviest batch, and use Check 9's dead_rows_est to find them.
  • Clearing a whole table. TRUNCATE sales.stage_orders; frees the space at once, where DELETE FROM only marks every row dead and leaves the vacuum to do the work. Note that TRUNCATE commits the current transaction.
  • Compression. Find columns stored without compression with Check 1 (encoded), get a recommendation with ANALYZE COMPRESSION sales.fact_sale;, and change it in place with ALTER TABLE sales.fact_sale ALTER COLUMN customer_name ENCODE zstd; (or ALTER TABLE … ALTER ENCODE AUTO to let Redshift choose).
  • Cold data. Move history nobody queries daily to S3 and keep it queryable through Redshift Spectrum, then delete it from the table and vacuum.
  • Snapshots. Space from deleted data is still held by manual snapshots taken before the delete. Review manual snapshots, which are kept until someone deletes them.
UNLOAD ('SELECT * FROM sales.fact_sale WHERE sale_date < ''2023-01-01''')
TO 's3://my-archive-bucket/fact_sale/before_2023/'
IAM_ROLE 'arn:aws:iam::123456789012:role/redshift-unload'
FORMAT AS PARQUET;

-- Check the unloaded row count against the table before deleting anything
DELETE FROM sales.fact_sale WHERE sale_date < '2023-01-01';
VACUUM DELETE ONLY sales.fact_sale;
SELECT "schema",
       COUNT(*)                     AS tables,
       SUM(size) / 1024             AS size_gb,
       SUM(tbl_rows - estimated_visible_rows) AS dead_rows_est
FROM svv_table_info
GROUP BY "schema"
ORDER BY size_gb DESC;

Under the hood: why a tiny table can use a lot of space

Redshift allocates storage in 1 MB blocks, per column, per slice. A table with 50 columns distributed across 32 slices needs at least 50 × 32 = 1,600 blocks (about 1.6 GB, plus a few hidden system columns) as soon as every slice holds a row, even if it has only a few hundred rows. Thousands of small staging tables can therefore use a surprising amount of storage. For small dimension tables, DISTSTYLE ALL (or AUTO, which picks ALL for small tables) avoids this.

The platform side: CloudWatch, snapshots and access

Some checks belong outside the database, because they must work even when the database doesn't.

  • CloudWatch alarms. On provisioned clusters, alarm on PercentageDiskSpaceUsed (for example above 80%), HealthStatus and CPUUtilization sustained high. On Serverless, watch the RPU capacity and usage metrics, and set usage limits so a runaway workload can't run up the bill.
  • Snapshots. Check the automated snapshot retention period (1 to 35 days) against your RPO, and enable cross-Region snapshot copy if you need to survive a Regional outage. Take a manual snapshot before risky changes; manual snapshots are kept until you delete them.
  • Access. Enable audit logging (to S3 or CloudWatch Logs), require SSL with the require_ssl parameter, and review superusers like Chapter 1 reviews sysadmin: SELECT usename FROM pg_user WHERE usesuper = true;

Putting it together

System views keep only a limited history (on provisioned clusters, the STL_* logs keep just a few days), so the daily job has two jobs: evaluate the checks and keep what they found. A small Airflow DAG does both: run each check's SELECT through the Redshift Data API, turn rows that cross a threshold into findings, insert them into dba.health_finding, and alert on severity 1.

# Provisioned cluster: --cluster-identifier (with --db-user or --secret-arn)
# Serverless:          --workgroup-name instead of --cluster-identifier
ID=$(aws redshift-data execute-statement \
       --cluster-identifier analytics-prod --database dev --secret-arn "$REDSHIFT_SECRET_ARN" \
       --sql "SELECT \"schema\", \"table\", unsorted, stats_off, skew_rows FROM svv_table_info WHERE unsorted > 20 OR stats_off > 10 OR skew_rows > 4" \
       --query Id --output text)

aws redshift-data describe-statement --id "$ID" --query Status    # wait for FINISHED
aws redshift-data get-statement-result --id "$ID"                  # rows as JSON

The Data API needs no network path to the cluster and no database driver, and with --secret-arn the credentials stay in AWS Secrets Manager. Each BashOperator task in the DAG runs one check this way, and a final task writes the findings and sends the alert.

Exercise: the dashboard that got slower every afternoon

A dashboard query takes 4 seconds at 08:00 and 40 seconds at 15:00, every day. Its plan doesn't change. The fact table it reads is loaded every hour with COPY and has a compound sort key on event_time. Which two checks from this chapter would you look at first, and what would you expect to see?

Answer

Check 1 (SVV_TABLE_INFO): unsorted on the fact table climbing during the day, as each hourly load appends unsorted rows, so zone maps prune fewer blocks and the query scans more as the day goes on. The fix is a VACUUM SORT ONLY after the loads, or a load pattern that appends in sort-key order. Check 3a (SYS_QUERY_HISTORY): compare queue time and execution time by hour. If the afternoon slowdown is mostly queue time, the cause is concurrency (more users in the afternoon), and the fix is WLM priorities or concurrency scaling, not the table.

Key takeaways

  • AWS manages Redshift's hardware and backups; you still own table design, workload and access.
  • Prefer the SYS_* views: they work on both provisioned clusters and Serverless.
  • SVV_TABLE_INFO is the daily table check: skew, unsorted rows, stale statistics, missing encoding.
  • Trend queue time separately from execution time: they have different causes and different fixes.
  • Start query monitoring rules with log, and only switch to abort once you trust them.
  • Long open transactions block vacuum as well as other sessions.
  • Defragmenting Redshift means restoring sort order: pick the right VACUUM variant, run one at a time, and use a deep copy for badly unsorted tables.
  • Reclaim space with VACUUM DELETE, TRUNCATE, compression and archiving to S3: on managed storage, every GB reclaimed is money saved.
  • System views forget quickly: persist findings to your own table every day.
