The Lab

Lab:Ubuntu 24.04 VM on AWS+Docker · docker-compose+SQL Server 2022 on Linux (container)+Airflow 2.7 (containers)This chapter is the infrastructure: the Linux VM in AWS, Docker networking and bind mounts, and SQL Server 2022 running inside a Linux container.

Everything in this tutorial runs on one small Ubuntu Linux virtual machine deployed in AWS, with Docker: SQL Server 2022 for Linux in one container, and an Airflow stack in six more. This chapter shows what runs where, how the folders map into the containers, and how to rebuild the warehouse from nothing.

The folder layout: logic and orchestration apart

The one rule of this design is that no SQL lives in the DAG. Compose Version10 added a single line (Version11 only renamed comments), a new bind mount, so the SQL folder appears inside every Airflow container next to the DAGs:

Lab shortcut

Using sa for the simulator is a lab convenience: it plays the source application. The pipeline itself never uses sa. The DataLoader password is generated on the server and never written into a DAG, a log or this site.

Rebuilding everything from nothing

  1. Course objects, empty. REBUILD=1 COURSE_ONLY=1 bash ~/sbecoltddw/run_sbecoltddw.sh drops and recreates SBEcoLTDDW with the course's schemas, tables, indexed view and columnstore index, plus the DataLoader login with its Resource Governor setup. Every statement is run by sqlcmd inside the SQL Server Linux container. course-build/run_sbecoltddw.sh · ~30 s
  2. Wire up Airflow. bash ~/sbecoltddw/airflow/setup_airflow_sbecoltddw.sh backs up the compose file, installs Version11, copies the SQL folder, plugin and DAGs, recreates the Airflow containers and creates the connection. airflow/setup_airflow_sbecoltddw.sh · ~2 min
  3. Load. ~/sbecoltddw/airflow/sbdw_run.sh sbecoltddw_e2e_pipeline triggers the DAG and waits. The first run deploys the pipeline objects and loads everything. ~1 min per run
echo ">> 3. recreate Airflow containers (docker-compose v1: rm -sf, then up -d)"
SERVICES="airflow-webserver airflow-scheduler airflow-worker airflow-triggerer"
docker-compose rm -sf $SERVICES
docker-compose up -d $SERVICES
echo "waiting for the scheduler..."
for i in $(seq 1 30); do
  if docker exec airflow_airflow-scheduler_1 test -d /opt/airflow/sql/sbecoltddw 2>/dev/null &&
     docker exec airflow_airflow-scheduler_1 airflow version >/dev/null 2>&1; then break; fi
  sleep 5
done
docker ps --format '{{.Names}}  {{.Status}}' | grep airflow_

echo ">> 4. connections (passwords are read from files/connections, never printed)"
set -a; source "$HOME/sbecoltddw/.dataloader.env"; set +a
docker exec -i -e DL_PASSWORD airflow_airflow-scheduler_1 python - <<'PY'
import os
from airflow.hooks.base import BaseHook
from airflow.models import Connection
from airflow.settings import Session

wanted = [
    Connection(conn_id="mssql_sbecoltddw_etl", conn_type="odbc", host="mssql", port=1433,
               schema="SBEcoLTDDW", login="DataLoader", password=os.environ["DL_PASSWORD"],
               description="SBEcoLTDDW pipeline steps (Resource Governor group DataLoads)"),
]
s = Session()
for c in wanted:
    s.query(Connection).filter(Connection.conn_id == c.conn_id).delete()
    s.add(c)
    print(f"connection {c.conn_id}: {c.conn_type}://{c.login}@{c.host}:{c.port}/{c.schema}")
s.commit()
PY

Key takeaways

  • One AWS VM, two container groups: Airflow (6 containers) and SQL Server (1), on one Docker network.
  • The SQL folder is mounted next to the DAGs, which keeps logic and orchestration in separate files.
  • Two connections, one per job: the ETL login for the pipeline, and the source system itself for the simulator.
  • The whole warehouse can be rebuilt with three commands.
