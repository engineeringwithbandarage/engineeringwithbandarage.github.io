The Source System

Lab:Ubuntu 24.04 VM on AWS+Docker · docker-compose+SQL Server 2022 on Linux (container)+Airflow 2.7 (containers)The source, AdventureWorks2022, is restored into the same SQL Server Linux container; every profiling query ran there through sqlcmd.

The warehouse can only be as good as your understanding of the source. Before writing any extract, profile it: how many rows, which keys, which columns record changes, and exactly which rows are in scope. The numbers you find here become the targets the pipeline must reconcile to.

Profile first

These are the profiling queries run against AdventureWorks2022, with the real results. They are read-only and cheap, and they answer the questions every extract design depends on.

-- how many customers, and how many are people rather than stores?
SELECT COUNT(*) AS customers,
       SUM(CASE WHEN PersonID IS NOT NULL AND StoreID IS NULL THEN 1 ELSE 0 END) AS individuals,
       MAX(ModifiedDate) AS max_mod
FROM Sales.Customer;

-- orders: volume, date range, and the change column we'll use as a watermark
SELECT COUNT(*) AS orders, SUM(CAST(OnlineOrderFlag AS int)) AS online_orders,
       MIN(OrderDate) AS min_od, MAX(OrderDate) AS max_od, MAX(ModifiedDate) AS max_mod
FROM Sales.SalesOrderHeader;

-- can a person have more than one home address? (decides the join)
SELECT COUNT(*) AS multi_home FROM (
    SELECT bea.BusinessEntityID
    FROM Person.BusinessEntityAddress AS bea
    JOIN Person.AddressType AS at ON at.AddressTypeID = bea.AddressTypeID AND at.Name = 'Home'
    GROUP BY bea.BusinessEntityID HAVING COUNT(*) > 1) AS x;

-- will the course's char(2)/char(5) columns fit?
SELECT MAX(LEN(a.City)) AS max_city, MAX(LEN(sp.Name)) AS max_state,
       MIN(LEN(a.PostalCode)) AS min_zip, MAX(LEN(a.PostalCode)) AS max_zip
FROM Person.Address AS a
JOIN Person.StateProvince AS sp ON sp.StateProvinceID = a.StateProvinceID
WHERE sp.CountryRegionCode = 'US';

What these numbers decide:

  • No customer has two home addresses, so joining on the Home address type gives exactly one row per customer, and the dimension needs no "pick one" rule.
  • Some US postal codes have 10 characters (ZIP+4, e.g. 98104-1234). The course's Zip char(5) keeps the first five: LEFT(PostalCode, 5).
  • State names are at most 14 characters, so the course's Statename nvarchar(20) fits.
  • Every table has a ModifiedDate. For orders it is the incremental watermark. Customers are small enough to extract in full.
  • A trigger exists, Sales.uSalesOrderHeader (after update). The simulator must expect it, and an OUTPUT clause on that table needs OUTPUT … INTO.

Define the scope precisely

The course's Dimension.Customer has State char(2) and Zip char(5), so it is a US design. The scope is therefore:

Scope

Customers: individuals (StoreID IS NULL) whose Home address is in the US. Orders: online orders (OnlineOrderFlag = 1) of those customers.

us_individuals | us_ind_orders | us_ind_subtotal
7819           | 9567          | 9389789.5108

Those three numbers are the reconciliation targets. After the first pipeline run the warehouse must hold exactly 7,819 current customers and 9,567 orders totalling 9,389,789.5108, and the DQ gate checks this on every run against the live source (rule DQ05, Chapter 10). The first run matched exactly.

Choosing an extract method per table

TableSizeChange markerMethodWhy
Customers7,819 rows from a 5-table join3 different ModifiedDatesFullSmall, and a change can come from any of three tables; the row hash finds the real changes
Orders31k and growingModifiedDate on one tableIncremental (watermark)The table that grows; one reliable change column

Watermarks trust the source

A ModifiedDate watermark only works if every change updates that column. AdventureWorks maintains it in its procedures, and the simulator in Chapter 12 sets it explicitly. Hard deletes are never seen by a watermark at all. When you can't trust the column, use SQL Server Change Tracking or CDC on the source instead.

Key takeaways

  • Profile before you design: cardinalities, lengths and change columns drive every decision.
  • Write the scope as a rule, then measure it in the source; those numbers are your reconciliation targets.
  • Pick full or incremental per table, based on size and how reliable its change marker is.
  • Keep a source-to-target mapping; it doubles as documentation and a test plan.
