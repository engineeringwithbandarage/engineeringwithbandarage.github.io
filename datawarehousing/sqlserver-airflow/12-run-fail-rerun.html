Chapter 12 · Operating It

Running, Failing & Re-running

Lab:Ubuntu 24.04 VM on AWS+Docker · docker-compose+SQL Server 2022 on Linux (container)+Airflow 2.7 (containers)Runs are triggered and cleared with the Airflow CLI through docker exec into the scheduler container on the Linux host.

A pipeline earns trust by how it behaves when things go wrong. This chapter replays the six runs of the rebuilt SBEcoLTDDW lab, plus a genuine bug from the lab's very first build, and shows how each was recovered without reloading anything twice.

Triggering and watching runs

Everything here can be done in the Airflow UI (Trigger DAG w/ config, Clear). For repeatable lab runs, three tiny scripts wrap the Airflow CLI inside the scheduler container:

#!/bin/bash
# Usage: ~/sbecoltddw/airflow/sbdw_run.sh <dag_id> [conf-json] [run_id]
#   e.g. sbdw_run.sh sbecoltddw_e2e_pipeline '{"full_reload": false}' sbdw_run_01
# Task logs: ~/airflow/logs/dag_id=<dag>/run_id=<run_id>/task_id=<task>/attempt=<n>.log
set -euo pipefail
DAG="$1"; CONF="${2:-}"; RUN_ID="${3:-manual_$(date +%Y%m%dT%H%M%S)}"
[ -n "$CONF" ] || CONF='{}'
S=airflow_airflow-scheduler_1
af() { docker exec "$S" airflow "$@" 2>/dev/null; }

af dags unpause "$DAG" >/dev/null
af dags trigger "$DAG" -r "$RUN_ID" -c "$CONF" >/dev/null
echo "triggered $DAG run_id=$RUN_ID conf=$CONF"

start=$(date +%s)
while true; do
  state=$(af dags list-runs -d "$DAG" -o plain | awk -v r="$RUN_ID" '$2==r {print $3}')
  case "$state" in success|failed) break ;; esac
  if [ $(( $(date +%s) - start )) -gt 1500 ]; then echo "timeout waiting for $RUN_ID"; break; fi
  sleep 10
done
echo "run $RUN_ID finished: $state after $(( $(date +%s) - start ))s"
af tasks states-for-dag-run "$DAG" "$RUN_ID" -o plain | awk '{printf "%-48s %-16s %s %s\n", $3, $4, $5, $6}'
#!/bin/bash
# its SQL output to ~/sbecoltddw/captures/<run_id>.txt
# Usage: ~/sbecoltddw/airflow/sbdw_scenarios.sh <step>
#   move    : source change "customer moves + 3 new orders", then pipeline run 03
#   bad     : source change "zero-value order",              then pipeline run 04 (DQ gate fails)
#   fix     : source change "fix the order",                  then pipeline run 05 (passes)
#   reload  : pipeline run 06 with full_reload = true (idempotency check)
set -uo pipefail
cd "$(dirname "$0")"
step="$1"

src() {   # $1 scenario, $2 run_id
  ./sbdw_run.sh sbecoltddw_source_changes "{\"scenario\": \"$1\"}" "$2" | grep -v '^task_id'
  ./sbdw_capture.sh sbecoltddw_source_changes "$2"
}
pipe() {  # $1 run_id, $2 conf
  ./sbdw_run.sh sbecoltddw_e2e_pipeline "${2:-}" "$1" | grep -v -E 'success\s+[0-9]|skipped|^task_id'
  ./sbdw_capture.sh sbecoltddw_e2e_pipeline "$1"
}

case "$step" in
  move)   src move_and_order src_01_move_and_order;   pipe sbdw_run_03_customer_moved ;;
  bad)    src bad_order      src_02_bad_order;        pipe sbdw_run_04_bad_order ;;
  fix)    src fix_bad_order  src_03_fix_bad_order;    pipe sbdw_run_05_order_fixed ;;
  reload) pipe sbdw_run_06_full_reload '{"full_reload": true}' ;;
  *) echo "unknown step $step"; exit 2 ;;
esac

The first build: a real bug, recovered in place

When this lab was first built, its very first run failed, and the failure was not staged. It was fixed the way you would in production: fix the SQL file, then clear the failed task and its downstream tasks inside the same DAG run. Upstream work (deploy, extracts, dimensions, the fact load) was not repeated. (After the fix, the rebuilt SBEcoLTDDW lab's run 01 succeeds on the first try.)

  1. Attempt 1 of post_load.update_statistics failed. Incorrect syntax near the keyword 'statistics': the file used AS statistics as a column alias, and STATISTICS is a reserved word in T-SQL. Everything before it (all the loads) had succeeded; everything after it became upstream_failed and fail_run marked the batch Failed.
  2. Fix the file. The alias became stats_objects, and the file was copied to ~/airflow/sql on the Linux host. Because the bind mount makes it visible to the containers immediately, and SQL is read at task run time, no restart was needed.
  3. Clear and re-run. Clearing from update_statistics with --downstream re-ran only the last 7 tasks. The run ended success and end_run set the batch to Succeeded.
#!/bin/bash
# Usage: ~/sbecoltddw/airflow/sbdw_clear.sh <dag_id> <run_id> <task_regex>
set -euo pipefail
DAG="$1"; RUN_ID="$2"; TASK="$3"
S=airflow_airflow-scheduler_1
af() { docker exec "$S" airflow "$@" 2>/dev/null; }

LD=$(af dags list-runs -d "$DAG" -o plain | awk -v r="$RUN_ID" '$2==r {print $4}')
echo "clearing $TASK (+downstream) in $RUN_ID (logical date $LD)"
af tasks clear "$DAG" -t "$TASK" --downstream --yes -s "$LD" -e "$LD" | tail -3

start=$(date +%s); sleep 5
while true; do
  state=$(af dags list-runs -d "$DAG" -o plain | awk -v r="$RUN_ID" '$2==r {print $3}')
  case "$state" in success|failed) break ;; esac
  if [ $(( $(date +%s) - start )) -gt 1500 ]; then echo "timeout"; break; fi
  sleep 10
done
echo "run $RUN_ID finished: $state after $(( $(date +%s) - start ))s"
af tasks states-for-dag-run "$DAG" "$RUN_ID" -o plain | awk '{printf "%-48s %-16s\n", $3, $4}'

Why clearing was safe

Every task is idempotent. When the statistics task was cleared, the loads that had succeeded were not re-run, and the tasks that ran afterwards would have produced the same result even if they had already run once. The batch's Attempts stayed 1 because start_run wasn't cleared. Clear from start_run if you want the retry counted.

Run 05: fix at the source, run again

The right fix for bad source data is in the source. The simulator's fix_bad_order set the total to 49.99 and moved ModifiedDate forward. Run 05 started from the kept watermark, re-extracted the order, and the MERGE updated the existing fact row (inserted 0, updated 1). The gate passed and the watermark moved to 10:04:37.053.

Don't "fix" a gate failure by editing the warehouse

Updating Fact.Orders by hand would make the gate pass once, then the next full reload would bring the bad value back from the source. Fix the source (or add a documented correction rule to the pipeline), then re-run.

Run 06: the idempotency proof

Triggered with {"full_reload": true}, the extract ignored the watermark and re-read all 31,469 orders. Result: inserted 0, updated 0, unchanged 9571, no new customer versions, and no new dates. Being able to reload everything and change nothing is the best evidence that the incremental logic is right.

About 40 seconds per run, and almost all of it is Airflow scheduling 26 tasks one wave after another (1–2 s between tasks). The SQL itself is a few seconds in total. That overhead is fixed per task, so the same DAG on ten times the data would take only a little longer.

Going to production

  • Schedule it: set schedule="0 2 * * *", keep catchup=False and max_active_runs=1. The watermark design means a skipped night is simply caught up by the next run.
  • Alert on failure: add on_failure_callback (Slack, Teams) or email_on_failure in default_args. fail_run already records the failure in SQL for dashboards.
  • Retries: retries=2, retry_delay=timedelta(minutes=5) on extract tasks absorbs transient network or lock errors. The gate should keep retries=0, because bad data won't fix itself.
  • SLAs and freshness: alert when etl.Watermark.LastValue falls too far behind the source's newest ModifiedDate.

Key takeaways

  • Fix the SQL file, then clear the failed task with its downstream; upstream work is kept.
  • A failed gate leaves the watermark in place, so the next run re-reads the same changes.
  • Fix bad data at the source and re-run; never patch the warehouse by hand.
  • A full reload that changes nothing proves the pipeline is idempotent.
