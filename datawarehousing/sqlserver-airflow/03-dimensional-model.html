Dimensional Modelling

Lab:Ubuntu 24.04 VM on AWS+Docker · docker-compose+SQL Server 2022 on Linux (container)+Airflow 2.7 (containers)The star schema is created by sqlcmd running inside the SQL Server Linux container (docker exec). The T-SQL is the same as on Windows.

Before writing a single load, decide what one row of each table means. This chapter walks through the SBEcoLTDDW star schema: the course's tables, the columns the pipeline adds, and the modelling decisions behind each one.

Start with the grain

The grain is one sentence saying what a single fact row represents. Everything else follows from it.

Grain of Fact.Orders

One row per online sales order of an individual US customer, at the order-header level, with the order's sub-total in OrderTotal.

Because the grain is the header and not the order line, product can't be a dimension of this table; you would need a line-level fact for that. And because OrderTotal is a plain amount, it is fully additive: you can sum it across days, customers and states and the result still means something.

Keys: surrogate, alternate, smart and degenerate

  • Surrogate key CustomerKey (IDENTITY): meaningless, owned by the warehouse. It has to be, because one source customer can have several versions, and each version needs its own key.
  • Alternate (business) key CustomerAlternateKey: the source's CustomerID, used to match incoming rows to existing versions.
  • Smart key DateKey = yyyymmdd (e.g. 20140423). For dates a readable key is the norm: it is stable, sortable and can be computed from the date without a lookup.
  • Degenerate dimension SalesOrderNumber: an identifier with no attributes of its own, so it lives in the fact table. It doubles as the fact's business key for idempotent MERGEs, with a filtered unique index to enforce it.

Foreign keys in a warehouse

The course declares WITH CHECK foreign keys from the fact to both dimensions, and the pipeline keeps them (both are trusted: is_not_trusted = 0). They cost a little at load time and in return guarantee no orphan rows, and the optimizer can use trusted keys to remove joins. Large warehouses sometimes drop them for speed and check orphans in the DQ gate instead. SBEcoLTDDW does both.

What the pipeline adds, and why

The pipeline extends the course tables in place, in an idempotent deploy step that only adds what's missing:

/* deploy 05 - extend the course tables for the pipeline (idempotent)
   Dimension.Customer  + SCD Type 2 columns: ValidFrom, ValidTo, IsCurrent, RowHash, LoadBatchID
   Fact.Orders         + SalesOrderNumber (business key for idempotent MERGE), SourceModifiedDate, LoadBatchID
   Indexes that use the new columns are created with EXEC so this batch compiles before they exist. */
SET NOCOUNT ON;

IF COL_LENGTH(N'Dimension.Customer', N'ValidFrom') IS NULL
    ALTER TABLE Dimension.Customer ADD
        ValidFrom   datetime2(3) NOT NULL CONSTRAINT DF_Customer_ValidFrom DEFAULT ('1900-01-01'),
        ValidTo     datetime2(3) NULL,
        IsCurrent   bit NOT NULL CONSTRAINT DF_Customer_IsCurrent DEFAULT (1),
        RowHash     varbinary(32) NULL,
        LoadBatchID int NULL;

IF COL_LENGTH(N'Fact.Orders', N'SalesOrderNumber') IS NULL
    ALTER TABLE Fact.Orders ADD
        SalesOrderNumber   nvarchar(25) NULL,
        SourceModifiedDate datetime NULL,
        LoadBatchID        int NULL;

IF NOT EXISTS (SELECT 1 FROM sys.indexes WHERE name = N'IX_Customer_AlternateKey')
    EXEC (N'CREATE NONCLUSTERED INDEX IX_Customer_AlternateKey
            ON Dimension.Customer (CustomerAlternateKey, ValidFrom)
            INCLUDE (ValidTo, IsCurrent, RowHash);');

IF NOT EXISTS (SELECT 1 FROM sys.indexes WHERE name = N'UX_Orders_SalesOrderNumber')
    EXEC (N'CREATE UNIQUE NONCLUSTERED INDEX UX_Orders_SalesOrderNumber
            ON Fact.Orders (SalesOrderNumber) WHERE SalesOrderNumber IS NOT NULL;');

Adding columns under an indexed view

dbo.OrdersByDate is created WITH SCHEMABINDING on Fact.Orders. Schema binding blocks changes to the columns the view uses, but adding new columns is allowed. That's why the deploy step can extend the course's fact table without dropping the view.

Key takeaways

  • Write the grain first; it decides which dimensions and measures are possible.
  • Surrogate keys are required as soon as a dimension keeps history.
  • SalesOrderNumber is a degenerate dimension and the fact's idempotency key.
  • The pipeline extends the course model with additive, idempotent DDL.
