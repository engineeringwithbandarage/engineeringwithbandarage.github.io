Loading Facts

Lab:Ubuntu 24.04 VM on AWS+Docker · docker-compose+SQL Server 2022 on Linux (container)+Airflow 2.7 (containers)MERGE, columnstore and indexed views work the same on SQL Server for Linux; the data files live at /var/opt/mssql/data inside the container's Docker volume.

A fact load turns staged source rows into rows of the fact table: it filters to the scope, swaps business keys for surrogate keys, and writes in a way that never duplicates. Do it right and you can re-run any batch, or the whole history, without fear.

The load

/* load_fact_orders - incremental, idempotent load of Fact.Orders from the staged order changes.
   Grain    : one row per sales order (header level)
   Scope    : online orders of customers in Dimension.Customer; other orders are counted and skipped
   Keys     : DateKey = yyyymmdd of OrderDate
              CustomerKey = the customer VERSION valid at OrderDate (SCD2 point-in-time lookup),
              -1 (unknown member) if no version covers the date
   Idempotent: MERGE on the business key SalesOrderNumber - re-running a batch updates, never duplicates. */
SET NOCOUNT ON;
SET XACT_ABORT ON;

DECLARE @BatchID int = (SELECT BatchID FROM audit.BatchRun WHERE DagRunID = N'{{ run_id }}');
DECLARE @staged int = (SELECT COUNT(*) FROM stg.SalesOrderHeader);
DECLARE @actions TABLE (act nvarchar(10));

SELECT h.SalesOrderNumber,
       CONVERT(int, CONVERT(char(8), h.OrderDate, 112)) AS DateKey,
       COALESCE(v.CustomerKey, -1)                      AS CustomerKey,
       h.SubTotal                                       AS OrderTotal,
       h.ModifiedDate
INTO #orders
FROM stg.SalesOrderHeader AS h
OUTER APPLY (
    SELECT TOP (1) d.CustomerKey
    FROM Dimension.Customer AS d
    WHERE d.CustomerAlternateKey = h.CustomerID
      AND h.OrderDate >= d.ValidFrom
      AND (d.ValidTo IS NULL OR h.OrderDate < d.ValidTo)
    ORDER BY d.ValidFrom DESC
) AS v
WHERE h.OnlineOrderFlag = 1
  AND EXISTS (SELECT 1 FROM Dimension.Customer AS c WHERE c.CustomerAlternateKey = h.CustomerID);

DECLARE @in_scope int = @@ROWCOUNT;

MERGE Fact.Orders AS t
USING #orders AS s
   ON t.SalesOrderNumber = s.SalesOrderNumber
WHEN MATCHED AND (t.OrderTotal <> s.OrderTotal OR t.CustomerKey <> s.CustomerKey OR t.DateKey <> s.DateKey) THEN
    UPDATE SET t.OrderTotal = s.OrderTotal, t.CustomerKey = s.CustomerKey, t.DateKey = s.DateKey,
               t.SourceModifiedDate = s.ModifiedDate, t.LoadBatchID = @BatchID
WHEN NOT MATCHED BY TARGET THEN
    INSERT (DateKey, CustomerKey, OrderTotal, SalesOrderNumber, SourceModifiedDate, LoadBatchID)
    VALUES (s.DateKey, s.CustomerKey, s.OrderTotal, s.SalesOrderNumber, s.ModifiedDate, @BatchID)
OUTPUT $action INTO @actions;

DECLARE @ins int = (SELECT COUNT(*) FROM @actions WHERE act = N'INSERT');
DECLARE @upd int = (SELECT COUNT(*) FROM @actions WHERE act = N'UPDATE');
DECLARE @unknown int = (SELECT COUNT(*) FROM #orders WHERE CustomerKey = -1);
DECLARE @note nvarchar(400) = CONCAT(N'staged ', @staged, N', in scope ', @in_scope, N', out of scope ', @staged - @in_scope,
                                     N', unknown customer ', @unknown);
EXEC audit.usp_LogStep @DagRunID = N'{{ run_id }}', @TaskID = N'{{ ti.task_id }}',
     @RowsRead = @staged, @RowsInserted = @ins, @RowsUpdated = @upd, @Note = @note;

PRINT @note;
SELECT @staged AS staged_orders, @in_scope AS in_scope, @ins AS inserted, @upd AS updated,
       @in_scope - @ins - @upd AS unchanged, @unknown AS unknown_customer,
       (SELECT COUNT(*) FROM Fact.Orders) AS fact_rows, (SELECT SUM(OrderTotal) FROM Fact.Orders) AS fact_total;

Point-in-time lookup

The OUTER APPLY … TOP (1) finds the customer version whose half-open interval [ValidFrom, ValidTo) contains the order date. Because consecutive versions share a boundary (the expired row's ValidTo equals the new row's ValidFrom), every instant belongs to exactly one version, and the DQ gate's overlap rule (DQ03) proves it on every run. OUTER APPLY rather than CROSS APPLY keeps the order when nothing matches, so the COALESCE(…, -1) can catch it.

Idempotent by construction

MERGE on the business key SalesOrderNumber decides per row: insert if new, update if something changed, and do nothing otherwise. OUTPUT $action counts what happened. Here is the same task across four real runs:

run                       staged  in_scope  inserted  updated  unchanged  unknown  fact_rows
01 initial load            31465      9567      9567        0          0        0       9567
03 customer moved              3         3         3        0          0        0       9570
05 order fixed                 1         1         0        1          0        0       9571
06 full reload (all rows)  31469      9571         0        0       9571        0       9571

Run 06 re-read the entire source history and changed nothing. That's the property that makes backfills, retries and "just run it again" safe.

MERGE and concurrency

MERGE is not protected against two sessions inserting the same key at the same moment. SBEcoLTDDW avoids that by design: the DAG has max_active_runs=1, so there is only ever one writer, and the unique index UX_Orders_SalesOrderNumber would reject a duplicate anyway. With concurrent writers, add WITH (HOLDLOCK) on the target, or use separate UPDATE and INSERT statements in a serializable transaction.

What about late-arriving customers?

Customers are extracted in full and loaded before facts in the same run, so an order can't arrive before its customer here. In systems where it can (separate feeds, different schedules), the usual pattern is to insert an inferred member: a placeholder dimension row with just the business key, which the next dimension load fills in. The -1 unknown member is the simpler cousin: the fact loads, and the gate makes the gap visible.

Key takeaways

  • Apply scope in the fact load and count what was skipped.
  • Look up the dimension version valid at the event time, not the current one.
  • MERGE on the business key makes every load idempotent; prove it with a full reload.
  • Indexed views are maintained by SQL Server in the same statement; there's nothing to refresh.
