Chapter 5 · Building the Pipeline

Staging & Extraction

Lab:Ubuntu 24.04 VM on AWS+Docker · docker-compose+SQL Server 2022 on Linux (container)+Airflow 2.7 (containers)Extracts are cross-database INSERT … SELECT statements inside the one SQL Server Linux container. Airflow, in its own containers, only sends the SQL.

Extraction copies source rows into the stg schema, and nothing else. No business rules, no joins to warehouse tables. It sounds trivial, but the choices made here (full or incremental, when the watermark moves, what to check) decide whether the pipeline can ever lose or double-count data.

Why stage at all?

  • One read of the source per run. Later steps can re-read stg as often as they like without touching the OLTP system.
  • A frozen snapshot. The dimension and fact loads all see the same data, even if the source changes during the run.
  • A checkpoint. If a later step fails, the staged data shows exactly what the run was working on, and checks can run on it before the warehouse is touched.

SBEcoLTDDW's staging tables hold one run only: each extract starts with TRUNCATE. They are created once by 01_deploy/04_staging_tables.sql, with only the columns the loads need.

Full extract: customers

The customer extract is the five-table join from Chapter 4, copied in full on every run. 7,819 rows take about 1.7 seconds, and a full copy means changes from any of the three source tables are always seen.

/* extract_customers - FULL extract from AdventureWorks2022 into stg.Customer.
   Scope: individual customers (no store) with a US home address - 7,819 rows in the sample.
   Small, slowly changing data is cheapest to extract in full; the SCD2 load works out what changed. */
SET NOCOUNT ON;
SET XACT_ABORT ON;

TRUNCATE TABLE stg.Customer;

INSERT INTO stg.Customer (CustomerID, FirstName, LastName, City, StateCode, StateName, PostalCode, SourceModifiedDate)
SELECT c.CustomerID,
       p.FirstName,
       p.LastName,
       a.City,
       RTRIM(sp.StateProvinceCode),
       sp.Name,
       LEFT(a.PostalCode, 5),
       (SELECT MAX(m) FROM (VALUES (c.ModifiedDate), (p.ModifiedDate), (a.ModifiedDate)) AS x(m))
FROM AdventureWorks2022.Sales.Customer AS c
JOIN AdventureWorks2022.Person.Person AS p                 ON p.BusinessEntityID = c.PersonID
JOIN AdventureWorks2022.Person.BusinessEntityAddress AS bea ON bea.BusinessEntityID = p.BusinessEntityID
JOIN AdventureWorks2022.Person.AddressType AS at           ON at.AddressTypeID = bea.AddressTypeID AND at.Name = N'Home'
JOIN AdventureWorks2022.Person.Address AS a                ON a.AddressID = bea.AddressID
JOIN AdventureWorks2022.Person.StateProvince AS sp         ON sp.StateProvinceID = a.StateProvinceID
WHERE c.StoreID IS NULL
  AND sp.CountryRegionCode = N'US';

DECLARE @rows int = @@ROWCOUNT;
EXEC audit.usp_LogStep @DagRunID = N'{{ run_id }}', @TaskID = N'{{ ti.task_id }}',
     @RowsRead = @rows, @RowsInserted = @rows, @Note = N'full extract: US individual customers';

PRINT CONCAT(N'staged customers: ', @rows);
SELECT COUNT(*) AS staged_customers, MAX(SourceModifiedDate) AS latest_source_change FROM stg.Customer;

Note the {{ run_id }} and {{ ti.task_id }} placeholders: Airflow renders the file with Jinja before sending it to SQL Server, so each step can write its own audit row. Everything else is plain T-SQL that you can paste into SSMS.

Incremental extract: orders and the watermark

Orders grow forever, so only changed rows are copied. The watermark is the highest ModifiedDate already loaded, stored in etl.Watermark. The important design choice is when it moves.

/* extract_sales_orders - INCREMENTAL extract of Sales.SalesOrderHeader using a watermark.
   Only rows with ModifiedDate after etl.Watermark.LastValue are copied. The new high-water mark is
   kept as PendingValue and only committed by publish.advance_watermarks at the very end of a
   successful run - so a failed run never skips changes.
   Trigger with {"full_reload": true} to ignore the watermark and extract everything. */
SET NOCOUNT ON;
SET XACT_ABORT ON;

DECLARE @Source nvarchar(128) = N'AdventureWorks2022.Sales.SalesOrderHeader';
DECLARE @FullReload bit = {{ 1 if params.full_reload else 0 }};
DECLARE @From datetime2(3) =
    CASE WHEN @FullReload = 1 THEN '1900-01-01'
         ELSE (SELECT LastValue FROM etl.Watermark WHERE SourceObject = @Source) END;

TRUNCATE TABLE stg.SalesOrderHeader;

INSERT INTO stg.SalesOrderHeader (SalesOrderID, SalesOrderNumber, OrderDate, CustomerID, OnlineOrderFlag, SubTotal, ModifiedDate)
SELECT h.SalesOrderID, h.SalesOrderNumber, h.OrderDate, h.CustomerID, h.OnlineOrderFlag, h.SubTotal, h.ModifiedDate
FROM AdventureWorks2022.Sales.SalesOrderHeader AS h
WHERE h.ModifiedDate > @From;

DECLARE @rows int = @@ROWCOUNT;

UPDATE etl.Watermark
SET PendingValue = (SELECT MAX(ModifiedDate) FROM stg.SalesOrderHeader), UpdatedAt = SYSDATETIME()
WHERE SourceObject = @Source;

DECLARE @note nvarchar(400) = CONCAT(N'incremental: ModifiedDate > ', CONVERT(nvarchar(23), @From, 121),
                                     CASE WHEN @FullReload = 1 THEN N' (full reload)' ELSE N'' END);
EXEC audit.usp_LogStep @DagRunID = N'{{ run_id }}', @TaskID = N'{{ ti.task_id }}',
     @RowsRead = @rows, @RowsInserted = @rows, @Note = @note;

PRINT CONCAT(N'watermark from ', CONVERT(nvarchar(23), @From, 121), N' -> ', @rows, N' changed orders');
SELECT @From AS watermark_from, PendingValue AS watermark_pending, @rows AS orders_extracted
FROM etl.Watermark WHERE SourceObject = @Source;
/* advance_watermarks - the run passed every gate: commit the pending high-water marks.
   Only now will the next run start after this run's changes. */
SET NOCOUNT ON;

SELECT SourceObject, LastValue AS old_watermark, PendingValue AS new_watermark FROM etl.Watermark;

UPDATE etl.Watermark
SET LastValue = PendingValue, PendingValue = NULL, UpdatedAt = SYSDATETIME()
WHERE PendingValue IS NOT NULL AND PendingValue > LastValue;
DECLARE @moved int = @@ROWCOUNT;

UPDATE etl.Watermark SET PendingValue = NULL WHERE PendingValue IS NOT NULL;   -- nothing new this run

EXEC audit.usp_LogStep @DagRunID = N'{{ run_id }}', @TaskID = N'{{ ti.task_id }}', @RowsUpdated = @moved;

SELECT SourceObject, LastValue AS watermark_now FROM etl.Watermark;

The watermark across real runs

Each line below is the extract task's PRINT message from the Airflow task log:

run 01 initial load    watermark from 1900-01-01 00:00:00.000 -> 31465 changed orders
run 02 no changes      watermark from 2014-07-07 00:00:00.000 -> 0 changed orders
run 03 customer moved  watermark from 2014-07-07 00:00:00.000 -> 3 changed orders
run 04 bad order       watermark from 2026-10-20 10:01:01.350 -> 1 changed orders   (run FAILED at dq_gate)
run 05 order fixed     watermark from 2026-10-20 10:01:01.350 -> 1 changed orders   (same start: nothing lost)
run 06 full reload     watermark from 1900-01-01 00:00:00.000 -> 31469 changed orders

Run 04 failed, so its pending value 10:02:49.947 was never committed. Run 05 started from exactly the same point as run 04 and picked up the corrected order. That is the whole point of committing at the end.

Strictly greater, and why that's safe here

The filter is ModifiedDate > LastValue. If two rows share a timestamp and only one was committed, > would skip the other. Here a run always extracts every row up to the new maximum before committing it, so no row with that timestamp can be half-loaded. If your source commits rows with timestamps in the past (long transactions), subtract a safety overlap (e.g. 5 minutes) and rely on the idempotent MERGE to absorb the re-read rows.

Check staging before touching the warehouse

The stage_checks task runs a handful of cheap rules and THROWs if any fail. Airflow then marks the task failed, and nothing downstream (no dimension, no fact) is touched.

/* check_staging - stop BEFORE touching the warehouse if the staged data is unusable.
   Every rule that fails is listed; THROW makes the Airflow task (and everything after it) fail. */
SET NOCOUNT ON;

DECLARE @checks TABLE (CheckName nvarchar(100), Problems bigint);

INSERT INTO @checks VALUES
 (N'stg.Customer is not empty',          CASE WHEN EXISTS (SELECT 1 FROM stg.Customer) THEN 0 ELSE 1 END),
 (N'stg.Customer has unique CustomerID', (SELECT COUNT(*) FROM (SELECT CustomerID FROM stg.Customer GROUP BY CustomerID HAVING COUNT(*) > 1) AS d)),
 (N'stg.Customer state and zip present', (SELECT COUNT(*) FROM stg.Customer WHERE LEN(StateCode) <> 2 OR LEN(PostalCode) <> 5)),
 (N'stg.SalesOrderHeader unique order',  (SELECT COUNT(*) FROM (SELECT SalesOrderID FROM stg.SalesOrderHeader GROUP BY SalesOrderID HAVING COUNT(*) > 1) AS d)),
 (N'stg.SalesOrderHeader no NULL dates', (SELECT COUNT(*) FROM stg.SalesOrderHeader WHERE OrderDate IS NULL));

SELECT CheckName, Problems, CASE WHEN Problems = 0 THEN N'ok' ELSE N'FAILED' END AS Result FROM @checks;

DECLARE @failed nvarchar(2000) =
    (SELECT STRING_AGG(CheckName, N'; ') FROM @checks WHERE Problems > 0);
DECLARE @n int = (SELECT COUNT(*) FROM @checks);
DECLARE @note nvarchar(400) = COALESCE(N'FAILED: ' + LEFT(@failed, 380), CONCAT(@n, N' checks passed'));

EXEC audit.usp_LogStep @DagRunID = N'{{ run_id }}', @TaskID = N'{{ ti.task_id }}', @Note = @note;

IF @failed IS NOT NULL
    THROW 50001, @failed, 1;
CheckName                          | Problems | Result
-----------------------------------+----------+--------
stg.Customer is not empty          | 0        | ok
stg.Customer has unique CustomerID | 0        | ok
stg.Customer state and zip present | 0        | ok
stg.SalesOrderHeader unique order  | 0        | ok
stg.SalesOrderHeader no NULL dates | 0        | ok

Note there is no "orders not empty" rule: zero changed orders is a perfectly normal incremental run (run 02).

Audit: every step leaves a row

Each load step ends with a call to audit.usp_LogStep. The procedure looks up the batch from the Airflow run_id and records the session's own login and Resource Governor group, so you can see who did the work and under which resource limits.

/* deploy 03 - audit.usp_LogStep: every load step records what it did */
CREATE OR ALTER PROCEDURE audit.usp_LogStep
    @DagRunID     nvarchar(250),
    @TaskID       nvarchar(250),
    @RowsRead     int = NULL,
    @RowsInserted int = NULL,
    @RowsUpdated  int = NULL,
    @RowsDeleted  int = NULL,
    @Note         nvarchar(400) = NULL
AS
BEGIN
    SET NOCOUNT ON;
    INSERT INTO audit.StepLog (BatchID, TaskID, RowsRead, RowsInserted, RowsUpdated, RowsDeleted, Note, LoginName, WorkloadGroupID)
    SELECT (SELECT BatchID FROM audit.BatchRun WHERE DagRunID = @DagRunID),
           @TaskID, @RowsRead, @RowsInserted, @RowsUpdated, @RowsDeleted, @Note,
           ORIGINAL_LOGIN(),
           (SELECT group_id FROM sys.dm_exec_sessions WHERE session_id = @@SPID);
END;
TaskID                       | RowsRead | RowsInserted | LoginName  | WorkloadGroupID | Note
-----------------------------+----------+--------------+------------+-----------------+-------------------------------------------------
extract.extract_sales_orders | 31465    | 31465        | DataLoader | 256             | incremental: ModifiedDate > 1900-01-01 00:00:00.000
extract.extract_customers    | 7819     | 7819         | DataLoader | 256             | full extract: US individual customers

Group 256 is the Resource Governor group DataLoads: every pipeline step runs as the DataLoader login, so all of them are classified there (Chapter 9).

Key takeaways

  • Staging gives one read of the source, a frozen snapshot, and a checkpoint.
  • Extract small tables in full and large, growing tables incrementally.
  • Record the new watermark as pending; commit it only after everything downstream passed.
  • Check staging and log every step: cheap insurance that pays for itself the first time something breaks.
