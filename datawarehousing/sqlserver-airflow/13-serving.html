Serving the Data

Lab:Ubuntu 24.04 VM on AWS+Docker · docker-compose+SQL Server 2022 on Linux (container)+Airflow 2.7 (containers)Consumers connect to SQL Server on Linux through port 1433, which Docker publishes from the container, exactly as to any SQL Server.

The warehouse only matters once someone reads it. Consumers get a small, stable set of views in the rpt schema. This chapter shows those views, the one reporting question every SCD2 warehouse has to answer ("which address do we report by?"), and how to keep consumers away from the moving parts.

The reporting views

/* deploy 07 - rpt.vSalesByMonth: monthly sales, read from the indexed view dbo.OrdersByDate */
CREATE OR ALTER VIEW rpt.vSalesByMonth
AS
SELECT v.Year,
       v.MonthNumber,
       v.MonthName,
       COUNT_BIG(*)      AS Orders,
       SUM(v.OrderTotal) AS Sales
FROM dbo.OrdersByDate AS v WITH (NOEXPAND)
GROUP BY v.Year, v.MonthNumber, v.MonthName;
/* deploy 08 - rpt.vSalesByState: sales by the state the customer lived in WHEN they ordered.
   Because Fact.Orders points at the customer version valid at order time (SCD Type 2),
   a customer who moves keeps their old orders in the old state. */
CREATE OR ALTER VIEW rpt.vSalesByState
AS
SELECT c.State,
       c.Statename,
       d.Year,
       COUNT_BIG(*)      AS Orders,
       SUM(o.OrderTotal) AS Sales
FROM Fact.Orders AS o
JOIN Dimension.Customer AS c ON c.CustomerKey = o.CustomerKey
JOIN Dimension.Date AS d     ON d.DateKey = o.DateKey
GROUP BY c.State, c.Statename, d.Year;
/* deploy 09 - rpt.vCustomerHistory: every SCD Type 2 version of every customer */
CREATE OR ALTER VIEW rpt.vCustomerHistory
AS
SELECT c.CustomerAlternateKey AS CustomerID,
       c.CustomerKey,
       c.FullName,
       c.City,
       c.State,
       c.Zip,
       c.ValidFrom,
       c.ValidTo,
       c.IsCurrent,
       COUNT(c.CustomerKey) OVER (PARTITION BY c.CustomerAlternateKey) AS Versions,
       (SELECT COUNT(*) FROM Fact.Orders AS o WHERE o.CustomerKey = c.CustomerKey) AS OrdersOnThisVersion
FROM Dimension.Customer AS c
WHERE c.CustomerKey <> -1;
/* deploy 10 - rpt.vLoadHistory: one row per pipeline step per run (from the audit tables) */
CREATE OR ALTER VIEW rpt.vLoadHistory
AS
SELECT b.BatchID,
       b.DagRunID,
       b.Status       AS RunStatus,
       b.StartedAt    AS RunStartedAt,
       b.EndedAt      AS RunEndedAt,
       s.TaskID,
       s.RowsRead,
       s.RowsInserted,
       s.RowsUpdated,
       s.RowsDeleted,
       s.LoginName,
       s.WorkloadGroupID,
       s.Note,
       s.LoggedAt
FROM audit.BatchRun AS b
LEFT JOIN audit.StepLog AS s ON s.BatchID = b.BatchID;

As-was or as-is?

With an SCD2 customer, "sales by state" has two honest answers:

  • As-was: by the state the customer lived in when they ordered. Join the fact to the version it points at. This is rpt.vSalesByState.
  • As-is: by the state the customer lives in today. Go from the fact's version to the customer's current version through the alternate key.
SELECT cur.State, COUNT(*) AS orders, SUM(o.OrderTotal) AS sales
FROM Fact.Orders AS o
JOIN Dimension.Customer AS c   ON c.CustomerKey = o.CustomerKey                 -- version at order time
JOIN Dimension.Customer AS cur ON cur.CustomerAlternateKey = c.CustomerAlternateKey
                              AND cur.IsCurrent = 1                             -- today's version
GROUP BY cur.State;

The difference is exactly Trevor Bryant's three pre-move orders (2,374.47 + 3,578.27 + 751.34 = 6,704.08). As-was keeps them in California, where they happened. As-is moves them to Washington, where the customer is now. Neither is wrong: finance usually wants as-was, and customer marketing usually wants as-is. Publish both under clear names instead of letting each analyst write their own join.

Access control

Consumers get SELECT on the rpt schema and nothing else. Ownership chaining lets the views read the underlying tables without granting anything on them:

CREATE ROLE rpt_reader;
GRANT SELECT ON SCHEMA::rpt TO rpt_reader;          -- views only
-- no rights on stg, Fact, Dimension, audit or etl are needed: the views and tables share
-- the owner dbo, so ownership chaining checks permissions on the views only
ALTER ROLE rpt_reader ADD MEMBER [CONTOSO\BI-Analysts];

Found while writing this chapter: who owns the schema?

Ownership chaining only works when the view and the tables have the same owner. A schema created with plain CREATE SCHEMA rpt is owned by whoever ran it, and the pipeline runs as DataLoader. So rpt, stg, audit and etl were owned by DataLoader while Fact and Dimension belonged to dbo, and a reader of rpt would have been refused on the tables. The deploy step now creates schemas AUTHORIZATION dbo and hands any existing ones to dbo. On the lab's first build it logged schema rpt now owned by dbo for all four; a fresh build creates them owned by dbo from the start.

/* deploy 01 - pipeline schemas (idempotent)
   stg    landing copies of source data, emptied at the start of every load
   etl    pipeline control data (watermarks)
   audit  run, step and data-quality logs
   rpt    reporting views for consumers
   All are owned by dbo, like the course's Fact and Dimension schemas. One owner keeps the
   ownership chain unbroken, so readers granted SELECT on rpt need no rights on the tables.
   (A schema created without AUTHORIZATION is owned by whoever ran CREATE SCHEMA - here
   DataLoader - so existing schemas are handed to dbo as well.) */
SET NOCOUNT ON;
IF SCHEMA_ID(N'stg')   IS NULL EXEC (N'CREATE SCHEMA stg AUTHORIZATION dbo');
IF SCHEMA_ID(N'etl')   IS NULL EXEC (N'CREATE SCHEMA etl AUTHORIZATION dbo');
IF SCHEMA_ID(N'audit') IS NULL EXEC (N'CREATE SCHEMA audit AUTHORIZATION dbo');
IF SCHEMA_ID(N'rpt')   IS NULL EXEC (N'CREATE SCHEMA rpt AUTHORIZATION dbo');

DECLARE @s sysname, @sql nvarchar(200);
DECLARE c CURSOR LOCAL FAST_FORWARD FOR
    SELECT name FROM sys.schemas
    WHERE name IN (N'stg', N'etl', N'audit', N'rpt') AND principal_id <> USER_ID(N'dbo');
OPEN c;
FETCH NEXT FROM c INTO @s;
WHILE @@FETCH_STATUS = 0
BEGIN
    SET @sql = N'ALTER AUTHORIZATION ON SCHEMA::' + QUOTENAME(@s) + N' TO dbo';
    EXEC (@sql);
    PRINT CONCAT(N'schema ', @s, N' now owned by dbo');
    FETCH NEXT FROM c INTO @s;
END;
CLOSE c; DEALLOCATE c;

SELECT s.name AS schema_name, USER_NAME(s.principal_id) AS owner
FROM sys.schemas AS s
WHERE s.name IN (N'stg', N'etl', N'audit', N'rpt', N'Fact', N'Dimension')
ORDER BY s.name;

Give readers their own workload group

Extend the Chapter 9 classifier with one more branch, for example IF IS_MEMBER('rpt_reader') = 1 RETURN 'Reports', with a modest REQUEST_MAX_MEMORY_GRANT_PERCENT. Then neither side can starve the other: the ETL has DataLoads, the analysts have Reports.

What consumers should not do

  • Read stg. It holds one run's data and is emptied at the start of the next.
  • Filter facts on Dimension.Customer.IsCurrent = 1. That silently drops every order placed under an older version. Use the as-is join above.
  • Count customers with COUNT(*) on the dimension. 7,821 rows are 7,819 real customers, one extra version and the Unknown member. Count DISTINCT CustomerAlternateKey with CustomerKey <> -1.
  • Read during a failed run without checking. rpt.vLoadHistory shows whether the latest batch Succeeded. A dashboard tile with "data as of the last successful batch" builds trust quickly.

Key takeaways

  • Consumers depend on rpt views; tables stay free to change.
  • SCD2 gives you both as-was and as-is reporting; publish both, clearly named.
  • Grant SELECT on the rpt schema only; ownership chaining does the rest.
  • Show "data as of the last successful batch" from the audit tables.
