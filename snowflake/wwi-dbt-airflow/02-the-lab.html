The Lab

Lab:Ubuntu 24.04 VM on AWS+Docker · docker-compose 1.29+Airflow 2.7.2 + dbt-snowflakeDiagram 1 in Chapter 0 shows this page at full size.

Everything except Snowflake runs on one small Ubuntu virtual machine deployed in AWS. SQL Server and Airflow live in Docker containers; the project's code sits in one folder on the VM that is mounted into Airflow. This chapter sets up that folder, adds dbt's Snowflake adapter to Airflow, and creates the key pair the platform logs in with.

The project folder

The master copy of the code lives on the PC in a project folder and is copied to the VM. On the VM it is one folder, mounted into every Airflow container at /opt/airflow/wwi_snowflake, so the DAG, a terminal session and you all run exactly the same files.

Folder on the VMWhat is in it
~/wwi_snowflake/extract/extract_load.py, reconcile.py and tables.yml (the 31 tables to load)
~/wwi_snowflake/dbt/the dbt project: dbt_project.yml, profiles.yml, models, snapshots, macros, tests
~/wwi_snowflake/landing/the CSV.gz files of each load, kept for 7 days
~/wwi_snowflake/secrets/the private key and the settings file, chmod 700; never copied anywhere
~/wwi_snowflake/snowflake/the one-time account setup script (Chapter 4)
~/airflow/dags/wwi_snowflake_daily.pythe DAG (Chapter 12)

A key pair instead of a password

Airflow and dbt log in to Snowflake as a service user, SVC_AIRFLOW, that has no password at all. It proves who it is with an RSA private key that never leaves the VM; Snowflake only stores the public half. Generate the pair once, on the VM:

mkdir -p ~/wwi_snowflake/secrets && chmod 700 ~/wwi_snowflake/secrets
cd ~/wwi_snowflake/secrets
openssl genrsa 2048 | openssl pkcs8 -topk8 -inform PEM -out rsa_key.p8 -nocrypt   # private key
openssl rsa -in rsa_key.p8 -pubout -out rsa_key.pub                                  # public key
chmod 600 rsa_key.p8
grep -v -- '-----' rsa_key.pub | tr -d '\n'        # this one line goes into the setup script (Chapter 4)

Check the file owner

The Airflow containers run as user ID 1000. The key must be readable by that user, so create it as the VM user that has ID 1000 (check with stat -c %u rsa_key.p8).

Teaching Airflow to speak Snowflake

The lab's Airflow image already contained dbt Core in its own virtual environment, so its libraries can't clash with Airflow's. Adding Snowflake support is one more package in that environment. These are the two lines that change in the Dockerfile:

ARG DBT_SNOWFLAKE_VERSION=1.9.0
RUN ... /home/airflow/dbt_venv/bin/pip install --no-cache-dir "dbt-postgres==${DBT_POSTGRES_VERSION}" "dbt-snowflake==${DBT_SNOWFLAKE_VERSION}"

The Airflow image already ships snowflake-connector-python, pyodbc and Microsoft's ODBC Driver 18, which the extract script uses. The compose file gets one more volume for every Airflow container:

    - /home/devserveruser/wwi_snowflake:/opt/airflow/wwi_snowflake

Then rebuild the image and recreate only the Airflow services, so SQL Server and the other containers in the same compose file keep running:

cd ~/airflow
docker-compose build airflow-worker
docker-compose up -d --no-deps airflow-webserver airflow-scheduler airflow-worker airflow-triggerer
docker exec airflow_airflow-worker_1 dbt --version      # Core 1.12.6 · plugins: snowflake 1.9.0, postgres 1.9.0

docker-compose 1.29 and KeyError: 'ContainerConfig'

With a recent Docker Engine, the old docker-compose 1.29 fails while recreating a container from a new image, and leaves the old container stopped under a name like 18b91c16a8a6_airflow_airflow-webserver_1. Remove those stopped copies (docker rm) and run the same up -d --no-deps again; the containers are then created fresh. Docker Compose v2 (docker compose) doesn't have this bug.

Installing dbt-snowflake also moved dbt Core up to 1.12.6. If other dbt projects share the same image, run them once after the upgrade.

Key takeaways

  • One VM, one project folder mounted into Airflow: the DAG and you run the same files.
  • The service user logs in with a key pair; the private key never leaves the VM.
  • dbt-snowflake goes into dbt's own virtualenv in the Airflow image; rebuild, then recreate only the Airflow services.
