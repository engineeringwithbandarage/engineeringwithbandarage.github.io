Chapter 1 · The Design

The Big Picture

Lab:Ubuntu VM on AWS+SQL Server 2022+Snowflake+dbt Core 1.12 · dbt-snowflake+Airflow 2.7Every number in this tutorial was measured on this lab.

A wholesale company runs its business on a SQL Server database. Its analysts want trusted numbers in Power BI without slowing the operational system down. We copy the data into Snowflake every night, clean and model it with dbt, check it against the source, and hand analysts a small, well-documented data mart. This chapter is the map; the rest of the tutorial walks it.

Why a medallion design

You could write one big query from the source to a report table. It would work until the first time something went wrong, and then nobody could tell where. Splitting the flow into layers, each with a single job, gives you places to stop, test and re-run:

LayerIts one jobIf it breaks
BronzeKeep exactly what arrived from the source, as text, plus when and from which fileReload a table; nothing downstream is lost
SilverGive every column a real type and a clean name, keep the latest version of each row, record historyFix a model and rebuild it from Bronze
GoldModel the business: conformed dimensions and facts with surrogate keysRebuild from Silver; history is safe in the snapshots
Data martServe one subject (sales) in the simplest shape for reportsRebuild in seconds from Gold and Silver

The rules we follow

  1. The source is read, never changed. The extract uses its own read-only login. Chapter 3
  2. Least privilege in Snowflake. One role per job and a service user with a key pair, no password. Chapter 4
  3. Load only what changed. High-water marks on each table's change column keep every night's load small. Chapter 5
  4. Bronze is append-only; Silver decides. A re-run may load a row twice; the staging model keeps the latest. Chapters 5, 7
  5. History is captured once, in Silver. dbt snapshots record every change as SCD Type 2. Chapter 7
  6. Every number is proved. dbt tests check keys and relationships; a reconciliation compares totals with the source. Chapter 11
  7. Orchestration stays boring. Each Airflow task is one shell command you can run by hand. Chapter 12

The life of one invoice line

Follow invoice line 1, a sale recorded on 1 January 2013, through the platform:

  1. Source. It sits in Sales.InvoiceLines, joined to its invoice in Sales.Invoices.
  2. Extract. extract_load.py selects it because its LastEditedWhen is above the table's high-water mark, and writes it to a gzipped CSV file.
  3. Bronze. The file is uploaded to a Snowflake stage and copied into WWI_RAW.BRONZE.SALES__INVOICE_LINES: every column as text, plus the batch number and file name.
  4. Silver. stg_sales__invoice_lines types the columns and keeps one row per line; int_invoice_lines_enriched adds the invoice header and the customer's delivery city.
  5. Gold. fact_sale swaps every business ID for the surrogate key of the dimension version valid on the invoice date.
  6. Mart. MART_SALES.FACT_SALES_LINE serves it with its six dimensions to Power BI.
  7. Proof. The reconciliation sums all 228,265 lines in the source and in Snowflake; the totals must match to the cent.

Key takeaways

  • Five stops: source, Bronze, Silver, Gold, data mart. Each layer has one job.
  • Python moves the data in; dbt shapes it; Airflow runs it; tests and reconciliation prove it.
  • Security and simplicity are design rules, not afterthoughts.
