Gold: Facts

Lab:models/gold/facts+incremental · mergeGold built in 47 s in the scheduled run.

A fact table records business events (a sale, an order line, a stock movement) with the measures you add up and a key for every dimension. Three things make a fact correct: its grain, the right dimension version for each key, and totals that follow the business rules exactly.

Point-in-time lookups

An invoice from March 2014 must point at the customer as they were in March 2014, not as they are today. Every SCD2 join therefore matches on the business ID and on the date falling inside the version's validity window:

left join {{ ref('dim_customer') }} as cu
       on cu.wwi_customer_id = l.customer_id
      and l.invoice_date >= cu.valid_from and l.invoice_date < cu.valid_to
...
coalesce(cu.customer_key, -1)   as customer_key,

The validity windows are half-open (>= start, < end), so every date falls into exactly one version. In the lab every sale found its customer, stock item, city and salesperson: none needed the unknown member.

With these rules, all 228,265 sales total 198,043,439.45 including tax and 172,261,341.20 excluding tax, with 85,729,180.90 profit. Chapter 11 proves those totals equal the source.

Incremental: only merge what is new

{{ config(unique_key='sale_key') }}           -- folder config: materialized='incremental', strategy='merge'

with lines as (
    select * from {{ ref('int_invoice_lines_enriched') }}
    {% if is_incremental() %}
    where _batch_id > (select max(lineage_key) from {{ this }})
    {% endif %}
)

On the first run the filter is skipped and the whole table is built. After that, only rows from a newer load batch are selected and merged on sale_key: new invoice lines are inserted, re-loaded ones are updated in place. The batch number travels from the extract all the way here as lineage_key, so every fact row says which load wrote it.

Combining two sources in one fact

fact_transaction unions customer transactions (97,147) and supplier transactions (2,438). Their source IDs could collide, so its key is hash('customer', id) or hash('supplier', id): unique by construction.

Key takeaways

  • State the grain of every fact, and keep it.
  • SCD2 keys are looked up point-in-time with half-open validity windows.
  • Business rules for totals live in one intermediate model each.
  • Incremental facts merge only newer batches; lineage_key records which load wrote each row.
