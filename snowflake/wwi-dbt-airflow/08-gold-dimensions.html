Gold: Conformed Dimensions

Lab:WWI_ANALYTICS.GOLD+models/gold/dimensionsDiagram 4 in Chapter 0 shows all eight with every column.

A dimension answers "who, what, where, when" for every fact. Gold has eight of them, and they are conformed: every fact that mentions a customer uses the same customer dimension with the same keys. This chapter explains the four design decisions every dimension shares, then the one that is different: the calendar.

Decision 1: a surrogate key that never changes

hash(v.customer_id, v.dbt_valid_from)   as customer_key,
v.customer_id                           as wwi_customer_id,

The key identifies one version of one customer. Snowflake's HASH() returns a 64-bit number, and because it is computed from the business ID and the version's start, rebuilding the table gives every row the same key as before. A row number would change on every rebuild and break every fact that points at it.

Decision 2: versions from the snapshot

with versions as (
    select s.*,
           row_number() over (partition by s.customer_id order by s.dbt_valid_from) as version_number
    from {{ ref('snap_customers') }} as s
)
select
    ...
    iff(v.version_number = 1, '1900-01-01'::timestamp_ntz, v.dbt_valid_from) as valid_from,
    coalesce(v.dbt_valid_to, '9999-12-31'::timestamp_ntz)                    as valid_to,
    v._batch_id                                                              as lineage_key
from versions as v

Decision 3: the first version starts at the beginning of time

The snapshot starts history on the day we first loaded it, and the source row's ValidFrom may be years after the customer's first invoice. Without a rule, a 2013 invoice would find no customer version valid in 2013. So the first version of every customer is valid from 1900-01-01: whatever we knew first is assumed to have been true before. Later versions start when the change happened.

Decision 4: an unknown member

union all
select -1, 0, 'Unknown', 'N/A', 'N/A', 'N/A', 'N/A', 'N/A',
       '1900-01-01'::timestamp_ntz, '9999-12-31'::timestamp_ntz, 0

When a fact can't find its dimension row, for example an order nobody has picked yet, it gets key -1 instead of NULL. Reports then show "Unknown" instead of silently dropping the row in an inner join, and you can count exactly how many lookups failed. In this lab the only unknowns are 23,740 order lines with no picker, which matches the source exactly: their orders have no PickedByPersonID.

The calendar: a fiscal year that starts in November

with days as (
    select dateadd(day, row_number() over (order by seq4()) - 1, '2013-01-01'::date) as d
    from table(generator(rowcount => 1461))                         -- 2013-01-01 to 2016-12-31
)
select
    d                                               as date_key,
    'CY' || year(d) || '-' || to_char(d, 'Mon')     as calendar_month_label,
    mod(month(d) + 1, 12) + 1                       as fiscal_month_number,   -- November = 1
    year(d) + iff(month(d) >= 11, 1, 0)             as fiscal_year,
    weekiso(d)                                      as iso_week_number,
    ...
from days

Use row_number() over (order by seq4()), not seq4() on its own: Snowflake doesn't promise that seq4() has no gaps, and a gap would be a missing day.

Key takeaways

  • Hash the business ID and version start for a stable, numeric surrogate key.
  • SCD2 versions come straight from the snapshots; the first version reaches back to 1900.
  • The unknown member (-1) turns silent row loss into a countable "Unknown".
  • One generated calendar, with the fiscal year starting on 1 November.
