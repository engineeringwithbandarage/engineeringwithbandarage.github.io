Silver: Staging, Snapshots & Intermediate

Lab:WWI_ANALYTICS.SILVER+dbt run --select silver+dbt snapshotSilver ran in 34 s and the snapshots in 44 s in the scheduled run.

Silver turns raw text into data you can trust. Staging models give every column a real type and a readable name and keep only the latest version of each row. Snapshots record every change to the things that change slowly, such as customers and stock items. Intermediate models do the joins that several Gold models need.

Staging: one view per Bronze table

Every staging model has the same shape, which is why they are generated. Here is the one for customers:

with source as (
    select * from {{ source('bronze', 'sales__customers') }}
),

latest as (
    select *
    from source
    qualify row_number() over (partition by CUSTOMERID order by VALIDFROM desc, _LOADED_AT desc, _BATCH_ID desc) = 1
)

select
    CUSTOMERID::number                as customer_id,
    CUSTOMERNAME::varchar             as customer_name,
    CREDITLIMIT::number(18,2)         as credit_limit,
    ACCOUNTOPENEDDATE::date           as account_opened_date,
    ISONCREDITHOLD::boolean           as is_on_credit_hold,
    try_to_geography(DELIVERYLOCATION) as delivery_location,
    VALIDFROM::timestamp_ntz          as valid_from,
    ...
    _BATCH_ID                         as _batch_id,
    _LOADED_AT                        as _loaded_at
from latest
  • QUALIFY keeps exactly one row per key: the newest version, then the most recent load. This is what makes an append-only Bronze safe: loading a row twice changes nothing.
  • Casting turns text into numbers, dates, booleans and geography. If a value can't be cast, the model fails loudly in dbt, which is far better than a wrong number in a report.
  • snake_case names (CustomerID → customer_id) are what every later model uses.

Staging models are views: they cost nothing to store and always show the latest Bronze data. Each is tested for a unique, non-null key; in the scheduled run all 62 Silver tests passed.

Snapshots: history, captured once

A customer can change category, credit limit or delivery city. Reports about last year must still see last year's values. dbt snapshots keep every version of a row, with the time each version was valid:

{% snapshot snap_customers %}
{{ config(unique_key='customer_id', strategy='timestamp', updated_at='valid_from') }}
select * from {{ ref('stg_sales__customers') }}
{% endsnapshot %}

On each run dbt compares the staging view with the snapshot. When a customer's valid_from has moved, it closes the old version (dbt_valid_to is set) and inserts the new one. The source tables are system-versioned, so valid_from is a timestamp SQL Server maintains itself and can be trusted as the "updated at" signal.

After the first run each snapshot holds one version per row, for example 663 rows for 663 customers, all current. History grows from here, one night at a time.

Run order matters

A snapshot reads a staging view, so the view must exist first. That's why the DAG runs dbt run --select silver before dbt snapshot; on an empty database the other order fails.

Intermediate: joins that several models need

Intermediate models are ephemeral: dbt pastes them into the models that use them as a CTE, so they never appear as tables. They keep Gold models short and put each business rule in one place.

select
    il.invoice_line_id, il.invoice_id, i.order_id,
    i.customer_id, i.bill_to_customer_id, i.salesperson_person_id, i.delivery_method_id,
    c.delivery_city_id,
    i.invoice_date,
    i.confirmed_delivery_time::date         as delivery_date,
    il.extended_price,                                         -- including tax
    il.tax_amount,
    il.extended_price - il.tax_amount       as total_excluding_tax,
    il.line_profit,
    greatest(il._batch_id, i._batch_id)     as _batch_id
from {{ ref('stg_sales__invoice_lines') }} as il
join {{ ref('stg_sales__invoices') }}      as i on i.invoice_id = il.invoice_id
join {{ ref('stg_sales__customers') }}     as c on c.customer_id = i.customer_id

The other three are int_order_lines_enriched (order lines with their order and totals), int_stock_movements and int_city_geography (state and country for each city).

Key takeaways

  • Staging views type, rename and keep the latest row per key; that makes an append-only Bronze safe.
  • Snapshots record SCD Type 2 history from the source's own ValidFrom.
  • Run the staging models before the snapshots that read them.
  • Ephemeral intermediate models hold each shared join and business rule once.
