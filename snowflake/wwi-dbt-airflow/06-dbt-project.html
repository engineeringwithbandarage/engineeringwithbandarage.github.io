Chapter 6 · Transforming with dbt

The dbt Project

Lab:dbt Core 1.12.6+dbt-snowflake 1.9.0+~/wwi_snowflake/dbt56 models, 5 snapshots, 123 tests, 31 sources.

dbt turns SELECT statements into tables and views, in the right order, and tests them. The project is organised so that its folders are the medallion layers: where a model lives decides its schema and how it is built, and you can run a whole layer by naming its folder.

Folders are layers

dbt_project.yml          the project: layers, schemas, materializations
profiles.yml             the connection (no secrets)
macros/generate_schema_name.sql
models/
  silver/
    _sources.yml         the 31 Bronze tables (generated)
    staging/             31 stg_* views (generated) + _staging.yml tests
    intermediate/        4 int_* models, ephemeral
  gold/
    dimensions/          8 dim_* tables
    facts/               6 fact_* incremental tables
    _gold.yml            key and relationship tests
  mart_sales/
    dimensions/          6 mart_dim_* tables
    facts/               mart_fact_sales_line
    _mart_sales.yml      key, relationship and totals tests
snapshots/snapshots.sql  5 SCD Type 2 snapshots
tests/mart_sales_totals_match_silver.sql
models:
  wwi_snowflake:
    silver:
      +schema: SILVER
      staging:      {+materialized: view}        # thin, always current
      intermediate: {+materialized: ephemeral}   # inlined into the models that use them
    gold:
      +schema: GOLD
      dimensions:   {+materialized: table}
      facts:        {+materialized: incremental, +incremental_strategy: merge}
    mart_sales:
      +schema: MART_SALES
      +materialized: table

Because each layer is a folder, the Airflow tasks select by folder: dbt run --select silver, --select gold, --select mart_sales. Inside Gold and the mart, dimensions and facts have folders of their own, so you can also run just one kind by hand, for example dbt run --select path:models/gold/dimensions.

A profile with no secrets

wwi_snowflake:
  target: prod
  outputs:
    prod:
      type: snowflake
      account: <your account identifier>
      user: SVC_AIRFLOW
      private_key_path: /opt/airflow/wwi_snowflake/secrets/rsa_key.p8
      role: TRANSFORMER
      warehouse: WH_TRANSFORM
      database: WWI_ANALYTICS
      schema: SILVER
      threads: 4
      query_tag: wwi_dbt

An account identifier and a user name are not secrets, and the key itself is a file only the VM can read, so profiles.yml can sit in git next to dbt_project.yml. The query_tag labels every query dbt runs, which makes them easy to find in Snowsight's query history.

Schema names exactly as written

By default dbt names a custom schema <target schema>_<custom schema>, which would give SILVER_GOLD. One small macro makes dbt use the folder's schema as written:

{% macro generate_schema_name(custom_schema_name, node) -%}
    {%- if custom_schema_name is none -%} {{ target.schema }}
    {%- else -%} {{ custom_schema_name | trim | upper }}
    {%- endif -%}
{%- endmacro %}

Model names are unique across the project

Gold and the mart both have a customer dimension, but dbt requires every model name to be unique. The mart's models are therefore called mart_dim_customer and so on, with an alias that sets the table name in Snowflake:

{{ config(alias='dim_customer') }}      -- table WWI_ANALYTICS.MART_SALES.DIM_CUSTOMER

Key takeaways

  • Folders are layers: they set the schema and materialization, and they are what you select.
  • The profile holds no secrets; the key file stays on the VM.
  • A schema-name macro and model aliases keep Snowflake names clean.
  • Generate what is mechanical; handwrite what is a decision.
