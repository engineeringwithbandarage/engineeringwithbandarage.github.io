Chapter 1 · Foundations

The Big Picture

Lab:SQL Server 2022 warehouse+Power BI semantic model+Airflow+PostgreSQLThis chapter is conceptual. These are the lab components that the later chapters build the AI system on.

Calling a language model takes a few lines of code. Building something people can rely on takes much more: the right data in front of the model, tools that let it look things up instead of guessing, tests that show whether a change made it better or worse, guardrails, and the same operational discipline as any other production pipeline. This chapter maps out those parts and shows where they sit on the data platform you already have.

A model is not a system

A language model predicts text. On its own it doesn't know your data, can't run a query, has no idea whether its last answer was right, and will answer a question it should refuse. Each of those gaps is filled by a part of the system around it. Most of the engineering, and most of this tutorial, is in those parts:

How it differs from the pipelines you already run

If you have built the warehouse in the Data Warehousing track, you already know most of what an AI system needs: sources, contracts, tests, orchestration and monitoring. What changes is that one step in the pipeline is probabilistic. That single difference changes how you test, how things fail and what you version.

Data pipelineAI system
Same input twiceSame outputPossibly different output, unless you design for it
TestingAssertions: row counts, keys, reconciliationEvaluations: scores over a test set, plus assertions where you can
How it failsErrors, failed tasks, rows that don't reconcileFluent, confident, wrong answers that raise no error at all
What you versionCode and schemasCode, prompts, model and its settings, retrieval settings and the index itself
Cost driverCompute and storageTokens per request × requests, which grows with the context you send
Security boundaryLogins and permissionsLogins and permissions, plus any text that reaches the prompt

The dangerous failure is the quiet one

A failed SQL task stops the DAG and pages someone. A model that invents a revenue figure returns HTTP 200 and a well-formatted sentence. That is why this tutorial never lets the model produce a business number from memory: numbers come from tools that query the semantic model, and the model only explains them.

The life of one question

Take a question a sales manager might ask the assistant: "Which territory grew net sales the most this fiscal year compared with last year, and what does our definition of net sales include?" It has a number part and an explanation part, so it exercises the whole system:

  1. Input checks. Is this in scope for the assistant? Does the message try to override the instructions? Is the user allowed to see sales by territory? Chapter 9
  2. Routing. The orchestrator sees two needs: a calculation, which goes to a tool, and a definition, which goes to retrieval. Chapter 7
  3. Tool call. The model asks for net sales by territory for this fiscal year and last year. The tool runs that against the semantic model, so the fiscal calendar, the measure definition and the user's row-level security all apply. Chapter 6
  4. Retrieval. The definition of net sales is found in the data dictionary through the vector index, along with its source. Chapters 4–5
  5. Answer. The model writes a short answer from the tool result and the retrieved definition, and cites both. Chapter 3
  6. Output checks. Every number in the answer must appear in the tool result. The format must match the contract. Chapter 9
  7. Trace and evaluate. The request, context, tool calls, answer, tokens and latency are logged. Similar questions sit in the test set and are scored on every change. Chapters 8, 10

The approach in seven rules

  1. Ground every answer in governed data. The model answers from what the system gives it: tool results and retrieved documents, not its memory of the internet. Chapters 4–6
  2. Numbers come from the semantic layer. The same measures that power the reports power the assistant, with the same security. The model never does business arithmetic on its own. Chapter 6
  3. Start with the simplest design that works. One well-written call before retrieval, retrieval before tools, tools before an agent. Each step adds cost, latency and new ways to fail. Chapter 7
  4. Prompts and settings are code. Prompts, model choice, temperature and retrieval settings live in git, are reviewed, and are deployed with a version. Chapter 3
  5. Evaluate before and after every change. A fixed test set with expected answers is the AI equivalent of the data quality gate. No change ships if the scores drop. Chapter 8
  6. Least privilege for everything the model can touch. Tools are read-only unless they must not be, run as the user, and can only reach what the user could reach. Chapter 9
  7. Trace everything, budget everything. Every request can be replayed from its trace, and every feature has a token and latency budget. Chapters 10–11

When not to use a language model

Part of AI systems engineering is knowing when the answer is not AI. A language model is the right tool for reading and writing language: summarising, classifying, extracting, explaining and turning a question into a query. It is the wrong tool when an exact, repeatable answer already has a known method.

Good fits

  • Answering questions about definitions, processes and documentation
  • Turning a plain-language question into a query on trusted measures
  • Summarising or classifying free text, such as support tickets
  • Extracting fields from documents into a table
  • Drafting the explanation that goes with a number

Poor fits

  • Calculating a total: that is SQL or a measure
  • Forecasting a time series: that is a statistical model (see the Statistics track)
  • Matching keys or deduplicating exact records: that is deterministic logic
  • Any decision that must be identical every time and explainable line by line

Exercise: AI, or not AI?

For each request, decide whether it needs a language model, and if so which parts of the system: (a) "What were net sales last month?" on a dashboard tile; (b) "Summarise this week's customer complaints by theme"; (c) "Why did gross margin fall in the Pacific, and what does gross margin include?"; (d) "Forecast next quarter's unit sales"; (e) "Remove duplicate customer rows that share the same customer key".

Answer

(a) No model: it is a measure on a report. (b) Model, with the ticket text as context and a fixed output format: a good fit. (c) Model with a tool for the margin numbers by territory and period, and retrieval for the definition; the explanation must cite both. (d) No language model: use a statistical forecasting model; a language model can only describe its result. (e) No model: exact keys mean deterministic SQL.

Key takeaways

  • The model is the smallest part of an AI system; retrieval, tools, evaluation, guardrails and operations make it reliable.
  • An AI system is a data pipeline with one probabilistic step, so its worst failures are quiet ones.
  • Numbers come from the semantic layer through tools; the model explains them and cites its sources.
  • Start with the simplest design, version prompts like code and evaluate every change.
