Chapter 3 · Foundations

Getting Data In

Power Query can do almost anything to data, which is exactly why it should do very little. In this approach SQL does the work and Power Query only connects, passes the query, sets types and splits the big fact into partitions. This chapter shows that thin layer on AdventureWorksDW2022, and the traps we found in the source while building it.

The source query is the contract

Each model table reads exactly one SQL query. It returns the columns the semantic model needs, with the right names and types, already joined and filtered, and it is the only place where row-level rules live. Where you own the warehouse, that query is a reporting view (rpt.vw_sales), versioned and tested with the warehouse code. In this lab the warehouse is read-only for us, so the same SQL is kept in the model and sent with Value.NativeQuery. It is written exactly as the view would be, so moving it into the warehouse later is a copy and paste.

SELECT  s.OrderDateKey AS DateKey,
        s.ChannelKey,
        s.CustomerID,
        s.ProductKey,
        s.SalesTerritoryKey,
        s.SalesRepKey,
        s.CurrencyKey,
        s.OrderQuantity AS Units,
        CAST(s.ExtendedAmount   AS decimal(19, 4)) AS GrossSales,
        CAST(s.DiscountAmount   AS decimal(19, 4)) AS Discounts,       /* float in the warehouse */
        CAST(s.TotalProductCost AS decimal(19, 4)) AS ProductCost,
        CAST(1.0 / r.AverageRate AS decimal(19, 6)) AS LocalCurrencyRate /* local units per USD on the order date */
FROM (
        SELECT 1 AS ChannelKey, CustomerKey AS CustomerID, -1 AS SalesRepKey,
               OrderDateKey, ProductKey, SalesTerritoryKey, CurrencyKey,
               OrderQuantity, ExtendedAmount, DiscountAmount, TotalProductCost
        FROM dbo.FactInternetSales
        UNION ALL
        SELECT 2, 100000 + ResellerKey, EmployeeKey,
               OrderDateKey, ProductKey, SalesTerritoryKey, CurrencyKey,
               OrderQuantity, ExtendedAmount, DiscountAmount, TotalProductCost
        FROM dbo.FactResellerSales
     ) AS s
LEFT JOIN dbo.FactCurrencyRate AS r
       ON r.CurrencyKey = s.CurrencyKey
      AND r.DateKey = s.OrderDateKey

Three habits make the contract work:

  • Only what is used. Every column costs memory in the model. The two fact tables have 26 and 27 columns; the query returns 12. SalesOrderNumber isn't one of them: no report needs it, and with 31,455 distinct orders it would be one of the most expensive columns in the model.
  • Types are decided in SQL. Money as a fixed decimal, rates with enough decimal places, flags as bit, keys as integers. Names are decided there too (AS GrossSales), so Power Query has nothing to rename.
  • One rule, one place. The 4-4-5 calendar rule is written once, as the shared expression FiscalCalendarSql (a SQL common table expression named cal). The Date query starts with it, and any other query that ever needs a fiscal week reuses it instead of repeating the rule. Chapter 4 explains it.

Connect with parameters

Never type a server name into each query. The project has two Power Query parameters, ServerName and DatabaseName, and every query uses them. Pointing the model at another server is a parameter change, and in a deployment pipeline it becomes a deployment rule.

let
    Source = Sql.Database(ServerName, DatabaseName),
    Sales  = Value.NativeQuery(Source, "SELECT ... (the query above) ...", null, [EnableFolding = true])
in
    Sales
let
    Source = SalesSource,
    FY2013 = Table.SelectRows(Source, each [DateKey] >= 20120701 and [DateKey] < 20130630)
in
    FY2013

EnableFolding = true is what makes this efficient. Without it, Power Query runs the native query as is and filters the result itself, so each partition would pull all 121,253 rows from SQL Server and keep a quarter of them. With it, Power Query wraps the native query and adds the partition filter as a WHERE clause, so SQL Server returns only that fiscal year. Right-click the last step and choose View Native Query to check. If the option is greyed out, a step broke folding.

Comments in a query that folds

Because Power Query puts your SQL inside its own, the Sales query uses /* … */ comments only. A -- comment runs to the end of the line, and whether that is safe depends on how the wrapper lays out the text. Block comments are safe either way.

The other tables use the same connection with their own query and no further steps, for example the date table: Value.NativeQuery(Source, FiscalCalendarSql & "SELECT … FROM cal").

A finance P&L is refreshed after close or overnight, is queried heavily, and uses complex DAX: currency conversion iterates, period to date reads a slicer selection, a calculation group rewrites every measure. That is the textbook case for import.

Partitions for the big fact

A real sales fact holds years of order lines, and refreshing all of it every night wastes hours. So the fact is split into partitions, each with the same query and a different date filter. A nightly job refreshes only the open year; closed years are refreshed only when finance restates them. AdventureWorksPL has one partition per fiscal year:

PartitionFilter on DateKeyRows
Sales FY2011>= 20100627 and < 201106265,115
Sales FY2012>= 20110626 and < 2012070120,380
Sales FY2013>= 20120701 and < 2013063050,210
Sales FY2014>= 20130630 and < 2014062945,548

Power BI Desktop shows the partitions but can't refresh them one at a time; in the service you do that with Tabular Editor, SQL Server Management Studio or a script against the XMLA endpoint. If you don't need that control, incremental refresh does it for you: define the RangeStart and RangeEnd datetime parameters, filter on them, and set a policy such as "store 4 years, refresh the last 2 periods".

Filtered = Table.SelectRows(SalesSource, each
               [DateKey] >= Int64.From(Date.ToText(Date.From(RangeStart), "yyyyMMdd"))
           and [DateKey] <  Int64.From(Date.ToText(Date.From(RangeEnd),   "yyyyMMdd")))

Use >= on one side and < on the other

If both ends are inclusive, a row exactly on a boundary lands in two partitions and is counted twice. If both are exclusive, it is lost. The four partitions above add up to 121,253 rows, the same as COUNT(*) over both warehouse facts.

Traps we found in the source

Each of these is in AdventureWorksDW2022 today, and each one would have changed numbers on the report page without any error. They are why the source queries look the way they do.

Trap 1: money stored as float

DiscountAmount is a float, while every other amount is money. Summed as float, the discounts and therefore Net Sales pick up binary rounding noise. Fix: cast every amount to decimal(19, 4) in the query. After the cast, Gross Sales − Discounts equals the warehouse's own SalesAmount on all 121,253 lines.

Trap 2: a fiscal year that means something else

DimDate already has FiscalYear and FiscalQuarter columns, so it is tempting to use them. But they label the year by the calendar year it starts in (1 July 2012 is FiscalYear 2012), and they describe calendar months, not finance's 4-4-5 weeks. Our FY2013 runs from 1 July 2012 to 29 June 2013. Fix: derive the calendar you actually need (Chapter 4), and never reuse a warehouse column because its name looks right.

Trap 3: one product, several keys

DimProduct keeps price history: 606 rows for 504 product codes. A measure written as DISTINCTCOUNT ( Sales[ProductKey] ) to count "products sold" overstates the answer whenever a product's price changed during the period. Fix: count Product[Product Code], and say in the measure's description what is being counted.

Review checklist for a table query

  • Reads one SQL query (or view) through the ServerName / DatabaseName parameters.
  • Names and types are set in SQL; Power Query has no rename steps, only a partition filter where needed.
  • The partitioned fact folds (View Native Query is available on the last step).
  • No hard-coded dates or IDs outside partition definitions; mapping rules, like the 100,000 offset on reseller customer keys, are commented.
  • Amounts are cast to decimal, rates have enough decimal places.
  • Partition filters are half-open (>= and <) and their row counts add up to the source.
Exercise: the missing year

After a release, FY2012 is missing from every report, but the warehouse has the data. The fact has one partition per fiscal year. What do you check first?

Answer

The partition list: either the FY2012 partition is missing, or its filter is wrong (an inclusive/exclusive boundary, or a typo in the date range), or it was never refreshed after being created. Compare each partition's row count with COUNT(*) per fiscal year in SQL; for this model they are 5,115, 20,380, 50,210 and 45,548.

Key takeaways

  • One SQL query per table; it decides columns, names, types and row-level rules.
  • Power Query connects through parameters and passes the query; EnableFolding lets partition filters reach SQL Server.
  • Import mode for a P&L model; partitions or incremental refresh for the big fact.
  • Profile the source before you trust it: dates drift, labels lie, floats round and keys repeat.
