The Fiscal Calendar & Time Intelligence

Many finance teams don't close on calendar months. Adventure Works closes on a 4-4-5 calendar: the fiscal year ends on the last Saturday of June, so most years have 52 weeks and some have 53. Power BI's built-in time-intelligence functions assume calendar months and give wrong answers here. This chapter builds the calendar in SQL and last year and period-to-date on its IDs.

Why SAMEPERIODLASTYEAR is wrong here

SAMEPERIODLASTYEAR shifts the selected dates back one calendar year. Fiscal week 1 of FY2013 runs from Sunday 1 July to Saturday 7 July 2012. The same dates in 2011 run from Friday to Thursday and fall in two fiscal weeks (FY2012 weeks 1 and 2). The comparison drifts by a day or two each year and breaks completely around FY2012, which has 53 weeks. Finance compares week 1 with week 1, so the model must too.

The date dimension

The calendar is generated in SQL from DimDate, once, in the shared expression FiscalCalendarSql. The Date query starts from it, so there is exactly one answer to which fiscal week a day belongs to.

WITH days AS (
    SELECT DateKey, FullDateAlternateKey AS [Date], EnglishDayNameOfWeek AS DayName, CalendarYear
    FROM dbo.DimDate
    WHERE FullDateAlternateKey BETWEEN '2010-06-27' AND '2014-06-28'
),
-- A fiscal year ends on the last Saturday of June and is named after that year.
-- DATEDIFF(day, '19000106', d) % 7 = days since the last Saturday (6 Jan 1900 was a Saturday).
years AS (
    SELECT days.*,
           CASE WHEN days.[Date] > e.YearEnd THEN days.CalendarYear + 1 ELSE days.CalendarYear END AS FiscalYear
    FROM days
    CROSS APPLY (SELECT DATEADD(day, -(DATEDIFF(day, '19000106', DATEFROMPARTS(days.CalendarYear, 6, 30)) % 7),
                                DATEFROMPARTS(days.CalendarYear, 6, 30)) AS YearEnd) AS e
),
weeks AS (
    SELECT years.*, DATEDIFF(day, s.YearStart, years.[Date]) / 7 + 1 AS FiscalWeek
    FROM years
    CROSS APPLY (SELECT DATEADD(day, 1 - (DATEDIFF(day, '19000106', DATEFROMPARTS(years.FiscalYear - 1, 6, 30)) % 7),
                                DATEFROMPARTS(years.FiscalYear - 1, 6, 30)) AS YearStart) AS s
),
-- 4-4-5: each quarter is 13 weeks split 4, 4 and 5; week 53 belongs to period 12.
cal AS (
    SELECT weeks.*, q.FiscalQuarter,
           (q.FiscalQuarter - 1) * 3
               + CASE WHEN q.WeekOfQuarter <= 4 THEN 1 WHEN q.WeekOfQuarter <= 8 THEN 2 ELSE 3 END AS FiscalPeriod
    FROM weeks
    CROSS APPLY (SELECT CASE WHEN weeks.FiscalWeek = 53 THEN 4  ELSE (weeks.FiscalWeek - 1) / 13 + 1 END AS FiscalQuarter,
                        CASE WHEN weeks.FiscalWeek = 53 THEN 13 ELSE (weeks.FiscalWeek - 1) % 13 + 1 END AS WeekOfQuarter) AS q
)

Before any measure was written, the calendar was checked in SQL. Every year starts on a Sunday, periods are 4, 4 and 5 weeks, and FY2012's period 12 has 6 weeks because it holds week 53:

All the visible labels live on Date itself, with the hierarchy Fiscal Year › Quarter › Period › Fiscal Week, so every fiscal slicer filters the one table that Sales relates to. The trick is the shape of the IDs: because FiscalWeekID = year × 100 + week, the same week last year is usually FiscalWeekID − 100. Integer arithmetic replaces date arithmetic.

Last year: the pattern you often inherit

Older models frequently compute last year like this. The model keeps a copy as the hidden measure _Net Sales LY (FILTER version) so you can compare it with the rewrite:

CALCULATE (
    SUMX ( VALUES ( 'Date'[FiscalWeekID] ), [03 - Net Sales] ),
    FILTER (
        ALL ( 'Date' ),
        COUNTROWS (
            FILTER ( 'Date', 'Date'[FiscalWeekID] = EARLIER ( 'Date'[FiscalWeekID] ) + 100 )
        )
    )
)

Read it from the inside out:

  1. Outer FILTER over ALL('Date'). Walk every day in the calendar (1,463 of them), ignoring the user's selection.
  2. Inner FILTER over 'Date'. For that day, look in the currently selected dates for a day whose week ID equals this day's week ID + 100. EARLIER reaches back to the outer row.
  3. COUNTROWS. If any selected day is exactly one fiscal year later, keep this day. The result is last year's days for the weeks on screen.
  4. CALCULATE + SUMX over weeks. Evaluate Net Sales in that new date filter, week by week, and add up.

Clear every date column, not just one

The report's fiscal-year slicer filters 'Date'[Fiscal Year], while the measure works on FiscalWeekID. Replacing the filter on one column leaves the slicer's filter in place, so last year's days would still be filtered to FY2013 and the measure would return blank. ALL ( 'Date' ) and REMOVEFILTERS ( 'Date' ) clear every column of the table at once. Keeping all fiscal columns on Date is what makes that one line enough.

Last year: a clearer rewrite

03 - Net Sales LY =
VAR lyWeeks =
    VALUES ( 'Date'[LYFiscalWeekID] )      -- weeks to compare with, for the weeks on screen
RETURN
    CALCULATE (
        [03 - Net Sales],
        REMOVEFILTERS ( 'Date' ),
        TREATAS ( lyWeeks, 'Date'[FiscalWeekID] )
    )

VALUES collects the comparison weeks from the current selection. REMOVEFILTERS clears every date filter, and TREATAS applies the comparison weeks as a filter on FiscalWeekID. It says what it does, it has no row-by-row walk over the calendar, and the week-53 rule lives in data instead of in + 100.

Is it also faster? It is often written that it must be, so we measured both on this model with a cleared cache (Chapter 9 shows how). They returned identical totals, and the same time: about 70 ms for a 397-cell week × region grid, and about 290 ms for a 1,718-cell week × product grid. The engine optimised the FILTER version well at this size. Choose the TREATAS version for clarity, and measure on your own model before claiming a speed-up: with larger calendars and more LY measures per visual, the difference can appear.

Why a stored LYFiscalWeekID instead of − 100

Subtracting 100 works for 52 weeks a year, but FY2012 has a week 53, and 201253 − 100 = 201153 doesn't exist. Finance decides what week 53 compares with. In this model the rule is "nothing": LYFiscalWeekID is blank for week 53, so FY2013's last-year total is FY2012's weeks 1–52, $30,688,807, not the full $32,120,916. The $1,432,109 difference is week 53. Storing the rule in the calendar query puts it in one place, where it can be read and tested.

One LY definition for every measure

With the pattern above you still need 05 - Gross Profit LY, 02 - Discounts LY and so on: one copy per P&L line, each identical except for the measure name. A calculation group defines the time logic once and applies it to any measure. In the project it is the table Time Comparison:

table 'Time Comparison'

	calculationGroup
		precedence: 10

		calculationItem Actual = SELECTEDMEASURE ()

		calculationItem LY =
				CALCULATE (
				    SELECTEDMEASURE (),
				    REMOVEFILTERS ( 'Date' ),
				    TREATAS ( VALUES ( 'Date'[LYFiscalWeekID] ), 'Date'[FiscalWeekID] )
				)

		calculationItem 'vs LY' =
				SELECTEDMEASURE ()
				    - CALCULATE ( SELECTEDMEASURE (), 'Time Comparison'[Comparison] = "LY" )

		calculationItem 'vs LY %' =
				DIVIDE (
				    SELECTEDMEASURE ()
				        - CALCULATE ( SELECTEDMEASURE (), 'Time Comparison'[Comparison] = "LY" ),
				    CALCULATE ( SELECTEDMEASURE (), 'Time Comparison'[Comparison] = "LY" )
				)

			formatStringDefinition = "0.0%"

The P&L matrix on the report page uses it: Comparison on the columns, the five P&L line measures as rows, and every line gets Actual, LY, vs LY and vs LY % without a separate LY measure for lines 01, 02 or 04. formatStringDefinition makes "vs LY %" show as a percentage whatever measure it is applied to. A calculation group requires discourage implicit measures on the model, which this approach wants anyway (Chapter 2).

The trade-off is that authors must learn that the calculation group is applied to whatever measure is in the visual, including ratios, where "vs LY" of a percentage is a difference in percentage points. For a model that already has hundreds of LY measures, converting them is a project of its own: plan it, and check the numbers against the old measures before deleting anything.

Period to date with a selector

Finance reviews the same page as week, period, quarter or year to date. Rather than four copies of every measure, a disconnected table holds the choice and one measure applies it.

Period To Date =
DATATABLE (
    "Period", STRING, "Sort", INTEGER,
    { { "Week", 1 }, { "Period", 2 }, { "Quarter", 3 }, { "Year", 4 } }
)
03 - Net Sales PTD =
VAR pick    = SELECTEDVALUE ( 'Period To Date'[Period], "Week" )
VAR lastDay = MAX ( 'Date'[Date] )               -- the end of whatever is selected
VAR wk      = MAX ( 'Date'[FiscalWeekID] )
VAR per     = MAX ( 'Date'[FiscalPeriodID] )
VAR qtr     = MAX ( 'Date'[FiscalQuarterID] )
VAR yr      = MAX ( 'Date'[FiscalYear] )
RETURN
    SWITCH (
        pick,
        "Week",    CALCULATE ( [03 - Net Sales], REMOVEFILTERS ( 'Date' ), 'Date'[FiscalWeekID] = wk ),
        "Period",  CALCULATE ( [03 - Net Sales], REMOVEFILTERS ( 'Date' ), 'Date'[FiscalPeriodID] = per, 'Date'[Date] <= lastDay ),
        "Quarter", CALCULATE ( [03 - Net Sales], REMOVEFILTERS ( 'Date' ), 'Date'[FiscalQuarterID] = qtr, 'Date'[Date] <= lastDay ),
        "Year",    CALCULATE ( [03 - Net Sales], REMOVEFILTERS ( 'Date' ), 'Date'[FiscalYear] = yr, 'Date'[Date] <= lastDay )
    )

It works because the fiscal IDs increase with time: the MAX of each ID within the selection is the period the selection ends in. The user picks a week in a slicer and "Year" in the selector, and sees year to date up to the end of that week.

Not every measure needs this

Apply the selector to a small set of clearly named PTD measures, not to every measure. A selector that silently changes the meaning of every number in the model confuses users of other reports and Excel. Keep PTD measures in their own display folder.

Exercise: week 53

With the original EARLIER(...) + 100 pattern and no LYFiscalWeekID, what does Net Sales LY show for week 53 of FY2012? And what does LY show for the full year FY2013?

Answer

Week 53 of FY2012 shows blank, because week 201153 doesn't exist. FY2013 LY shows FY2012's weeks 1–52 ($30,688,807): week 201253 is never anyone's "+ 100", so it is silently dropped. That happens to be the same answer as this model's rule, but by accident. If finance decides week 53 should compare with week 52, only the stored mapping can say so.

Exercise: LY for a single day

A user filters to one day, 2012-07-04. What does the TREATAS version of Net Sales LY return?

Answer

The whole of FY2012's week 1, because the comparison is defined per week, not per day. If day-level comparisons matter, add an LYDateKey column (the same weekday in last year's same week) and use it the same way.

Key takeaways

  • On a fiscal calendar, compare fiscal weeks, not dates: avoid the built-in time-intelligence functions.
  • Generate the calendar once, in SQL, and check it before writing any measure.
  • Shape IDs as year × 100 + week so "last year" is integer arithmetic, and store the LY mapping for 53-week years.
  • Keep every fiscal column on Date, so one REMOVEFILTERS ( 'Date' ) clears every date filter.
  • A calculation group replaces one LY copy per measure; a disconnected selector plus SWITCH gives period to date.
