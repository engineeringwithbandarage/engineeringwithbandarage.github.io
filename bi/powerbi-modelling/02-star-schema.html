A Star Schema for Power BI

Power BI's engine is built for star schemas: one fact table per business process, surrounded by dimensions it can filter through. Most performance problems and wrong totals in Power BI trace back to a model that is not a star. This chapter designs the AdventureWorksPL model and explains each decision.

Start with the grain

Grain of Sales

One row per order line, internet or reseller: one product, on one order, for one customer, on one day, in one sales territory. Amounts are stored in US dollars, with the order's exchange rate alongside.

Everything follows from that sentence. Because the grain is the order line, any dimension that has one value per line (customer, product, date, territory, sales rep, channel, currency) can relate directly to the fact. Because amounts are additive at that grain, SUM gives the right answer at every level.

AdventureWorksDW2022 keeps internet and reseller orders in two fact tables. They share almost every column and answer the same question, so the model unions them into one Sales fact with a ChannelKey: 121,253 rows. Two facts would mean two copies of every measure.

Relationship rules

RuleWhy
Every relationship is many-to-one, fact → dimensionThe engine is optimised for it, and totals are unambiguous.
Single-direction cross-filtering onlyBi-directional filters create ambiguous paths and slow queries. If a dimension slicer must react to a fact ("only customers with sales"), use a visual-level filter or a measure, not a both-ways relationship.
Integer surrogate keysSmall, fast to join and compress well. Smart date keys (20120701) are integers too.
Hide every key and every fact columnUsers must not sum CustomerID, or sum GrossSales without the currency logic. Facts expose measures only. The model also sets discourage implicit measures, so a column dragged into a visual is not summed automatically.
No many-to-many relationshipsThey make totals hard to predict. If two tables really are many-to-many, put a bridge or a dimension at the shared grain between them.

In the project these are plain text. A relationship with no other properties is many-to-one and single-direction, because those are the defaults:

relationship Sales_Date
	fromColumn: Sales.DateKey
	toColumn: Date.DateKey

relationship Sales_Customer
	fromColumn: Sales.CustomerID
	toColumn: Customer.CustomerID

relationship Sales_SalesTerritory
	fromColumn: Sales.SalesTerritoryKey
	toColumn: 'Sales Territory'.SalesTerritoryKey

Designing dimensions

  • Flatten in SQL. Product, subcategory and category are three warehouse tables, but the model gets one Product table. Snowflaked dimensions in Power BI mean more relationships and slower filters.
  • One dimension for one business concept. AdventureWorks keeps individual customers in DimCustomer and resellers in DimReseller. The Customer query unions them and offsets reseller keys by 100,000 so both fit one integer key; Customer Type says "Individual" or the reseller's business type.
  • Labels must be unique. 171 of the 19,185 customers share their name with another customer. A visual groups by the label, so two customers with the same name would merge into one row. The query appends the customer code only where a name repeats.
  • Build hierarchies users actually drill: Customer Type › Customer, Category › Subcategory › Product, Group › Country › Region, and Fiscal Year › Quarter › Period on Date.
  • Sort labels by a number. "P01 Jul" … "P12 Jun" must sort by FiscalPeriodID, and "FY2013" by FiscalYear. Set Sort by column in the model.
  • Unknown members. Internet orders have no sales rep. Rather than a blank key, the query uses -1, and the Sales Rep table has a row "Internet (no rep)". The fact never has a blank foreign key, so totals always reconcile.
  • Watch width. DimCustomer has 29 columns, including addresses, phone numbers and education and occupation in three languages. The model takes seven. Every column costs memory and clutters the field list.

The fiscal calendar lives in Date

Finance reports by fiscal week, period, quarter and year, but there is no separate period table. Each of those is a column of Date, one row per day, so Sales needs only one relationship to the calendar and every fiscal slicer filters through it. Chapter 4 builds the columns from DimDate.

Disconnected tables

Four tables have no relationships at all, on purpose:

  • _Measures holds every measure, so users find them in one place instead of scattered across fact tables. It has one hidden column, and the leading underscore sorts it to the top of the field list.
  • Period To Date is a list of choices (Week, Period, Quarter, Year) for a slicer. A measure reads the selection with SELECTEDVALUE (Chapter 4).
  • Time Comparison is a calculation group: its items Actual, LY, vs LY and vs LY % are applied to whatever measure is in the visual (Chapter 4).
  • User Access maps a user's e-mail to the sales territories they may see. The row-level security role reads it (Chapter 6).

No calculated columns

Power BI lets you add columns with DAX. In this approach we don't: every column comes from the source query. Calculated columns are computed after the data is loaded, so they compress worse; they hide logic from SQL users; and they can't be tested with SQL. If a report needs Customer Type, the query returns that column. The model has none.

Exercise: "only show customers that bought"

A report designer asks you to make the Customer → Sales relationship bi-directional so that the Customer slicer only lists customers with sales in the selected period. What do you suggest instead?

Answer

Keep the relationship single-direction and add a visual-level filter on the slicer: [03 - Net Sales] is not blank. The slicer then shows only customers with sales in the current context, and no other visual or measure is affected by a second filter path.

Key takeaways

  • Write the grain of every fact as one sentence before modelling.
  • Many-to-one, single direction, integer keys, keys hidden. No exceptions without a written reason.
  • The fiscal calendar is columns of Date, not a separate period table.
  • Measures live in a disconnected measure table; fact columns stay hidden.
  • Columns come from SQL, not from DAX calculated columns.
