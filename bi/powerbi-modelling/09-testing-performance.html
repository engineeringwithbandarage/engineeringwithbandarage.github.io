Chapter 9 · Engineering

Testing & Performance

A P&L model is only useful if finance trusts it, and trust comes from numbers that match the warehouse every time. This chapter proves each P&L line against SQL, tests the patterns from Chapter 6, measures performance instead of guessing, and lists what to check before a release. Every result shown was produced on AdventureWorksPL.

Check that every measure compiles

Before testing numbers, ask the engine whether every DAX expression is valid. Open the project in Desktop (or deploy it) and query the model's metadata from DAX Studio or any XMLA client. State 1 means ready; anything else comes with an error message:

SELECT [Name], [State], [ErrorMessage] FROM $SYSTEM.TMSCHEMA_MEASURES WHERE [State] <> 1
SELECT [Name], [State], [ErrorMessage] FROM $SYSTEM.TMSCHEMA_CALCULATION_ITEMS WHERE [State] <> 1

Both return no rows for AdventureWorksPL. Do this in the release pipeline as well: a measure that refers to a renamed column fails silently in a report (the visual shows an error) but loudly here.

Reconcile every line with SQL

The source query is the contract (Chapter 3), so the model must return exactly what SQL on the warehouse returns, at the grain finance checks: fiscal period × sales territory. Run the same question both ways. Both files are in bi/code/tests.

EVALUATE
SUMMARIZECOLUMNS (
    'Date'[FiscalPeriodID],
    'Sales Territory'[SalesTerritoryKey],
    "GrossSales",  [01 - Gross Sales],
    "Discounts",   [02 - Discounts],
    "NetSales",    [03 - Net Sales],
    "ProductCost", [04 - Product Cost],
    "GrossProfit", [05 - Gross Profit]
)
ORDER BY 'Date'[FiscalPeriodID], 'Sales Territory'[SalesTerritoryKey]
SELECT c.FiscalYear * 100 + c.FiscalPeriod                                      AS FiscalPeriodID,
       s.SalesTerritoryKey,
       SUM(s.ExtendedAmount)                                                     AS GrossSales,
       SUM(CAST(s.DiscountAmount AS decimal(19, 4)))                            AS Discounts,
       SUM(s.ExtendedAmount - CAST(s.DiscountAmount AS decimal(19, 4)))         AS NetSales,
       SUM(s.TotalProductCost)                                                   AS ProductCost,
       SUM(s.ExtendedAmount - CAST(s.DiscountAmount AS decimal(19, 4)) - s.TotalProductCost) AS GrossProfit
FROM (SELECT OrderDateKey, SalesTerritoryKey, ExtendedAmount, DiscountAmount, TotalProductCost FROM dbo.FactInternetSales
      UNION ALL
      SELECT OrderDateKey, SalesTerritoryKey, ExtendedAmount, DiscountAmount, TotalProductCost FROM dbo.FactResellerSales) AS s
JOIN cal AS c ON c.DateKey = s.OrderDateKey
GROUP BY c.FiscalYear * 100 + c.FiscalPeriod, s.SalesTerritoryKey
ORDER BY 1, 2;

Export both results and compare them row by row. For AdventureWorksPL both return 366 rows (territory × period combinations with sales), and the largest difference on any of the five lines is 0.00. Note that the SQL side deliberately does not reuse the model's measures or its source query: it starts from the warehouse tables, so a bug in the source query would show up as a difference. Any difference points to one of three places: the source query, a partition (missing period, double-counted boundary, leftover filter), or a measure.

Automate it. The DAX query can be run from a script through the XMLA endpoint (in Microsoft Fabric, Semantic Link's evaluate_dax does it from a notebook), so the comparison runs after every deployment and every refresh.

Find out why a page is slow

  1. Performance Analyzer in Power BI Desktop: record while the page refreshes. It shows each visual's time, split into DAX query, visual display and other. Copy the slowest visual's query.
  2. DAX Studio, Server Timings: paste the query and run it with a cleared cache. The total splits into formula engine (single-threaded DAX logic) and storage engine (fast, parallel scans). Many storage-engine queries or a large formula-engine share points to the measure, not the data.
  3. VertiPaq Analyzer (in DAX Studio, View Metrics): model size per table and column, with cardinality. Wide dimensions and high-cardinality columns show up immediately.

Always time with a cold cache, or the second run measures the cache. We compared the two last-year measures from Chapter 4 this way, five runs each, clearing the cache before every run:

Measure before and after

Run each change with a cold cache, before and after, and compare the result values as well as the timings. A faster measure that returns a different number isn't an optimisation.

Go-live checklist

Model

  • Every fact has a written grain; all relationships are many-to-one and single-direction.
  • Fact columns and keys hidden; measures only in _Measures; implicit measures discouraged.
  • Every visible measure has a format string and a description.
  • The definition loads without errors, every measure's state is ready, and Best Practice Analyzer passes.

Data

  • Every table reads one SQL query or view through the connection parameters.
  • Partitions cover every period exactly once; their row counts add up to the warehouse.
  • Amounts are decimals; the source quirks found in profiling are handled in SQL and commented.

Numbers

  • Reconciliation passes for lines 01–05 by territory × period, and the pattern tests pass or have written, expected differences.
  • Last year checked for a 53-week year if the data covers one.
  • Finance has signed off one closed period against its own sales report.

Security and operations

  • Roles tested with "View as" and with a real test account; every fact reachable from the secured dimension.
  • Generated measure documentation is up to date (Chapter 8).
  • Refresh schedule, partition refresh job and failure alerts are in place.
Exercise: a difference of exactly one day

Reconciliation shows that one period in the model is higher than SQL by exactly one day's sales. All other periods match. What is the likely cause?

Answer

That day is loaded by two partitions: its own and a neighbouring one whose filter reaches one day too far, typically an inclusive end (<=) set to the next partition's first day. The reconciliation groups by the fiscal period of each row's date, so the duplicate shows up in the period that owns the day, which tells you exactly which boundary to check. The fix is half-open ranges everywhere: >= the start and < the next start.

Key takeaways

  • Check that every measure compiles, then reconcile every P&L line with SQL on the warehouse tables, by territory × fiscal period, and automate it.
  • Each pattern (currency, LY, security) gets its own test; explained differences are written into the test.
  • Performance Analyzer finds the slow visual, DAX Studio explains it, VertiPaq Analyzer shows where memory goes.
  • Measure with a cold cache before and after every optimisation, and compare values, not only timings.
