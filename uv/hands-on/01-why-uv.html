Why uv

Running someone else's Python code should be easy, yet it usually starts with questions. Which Python version? Which packages, at which versions? Do I install them globally or in a virtual environment? uv answers all of those with one tool. This chapter explains the problem, what uv replaces, and the mental model you'll use in every later chapter.

The problem: five jobs, five tools

To run a Python project reliably, something has to do five separate jobs:

  1. Get the right Python. The project needs Python 3.12, but the machine has 3.10, or none at all.
  2. Isolate the project. Each project needs its own set of packages, so upgrading pandas for one project doesn't break another. That is what a virtual environment is for: a folder with its own site-packages.
  3. Install the dependencies. Download packages from PyPI (the Python Package Index) and put them in that environment.
  4. Make it reproducible. "pandas" today means version 2.3; in six months it means something newer. To get the same result on every machine, you need a record of the exact version of every package, including the dependencies of your dependencies. That record is a lockfile.
  5. Run tools and ship code. Linters and formatters need installing too, and libraries need building and uploading to PyPI.

Traditionally each job had its own tool, each with its own commands, configuration and quirks. uv does all five.

Why uv is so fast

uv's speed is the first thing people notice: installing a large data-science stack takes seconds instead of minutes. That isn't one trick but several design decisions working together.

  • Rust, not Python. uv is a compiled program. It doesn't need Python to start, and it doesn't pay Python's start-up and interpretation cost.
  • Parallel everything. Downloads, unpacking and installation run concurrently instead of one package at a time.
  • One global cache. Each package version is downloaded and unpacked once per machine. The tenth project that needs numpy gets it from the cache, without the network.
  • Links instead of copies. Installing from the cache usually means creating hard links (or copy-on-write clones) into the environment, which is almost free. Chapter 12 shows how.
  • A modern resolver. Working out compatible versions uses the PubGrub algorithm, which handles conflicts well and explains them clearly when there's no solution.

Under the hood

Speed changes behaviour. Because installing is nearly instant once the cache is warm, uv can afford to check and repair the environment every time you run your code. That is why uv run silently re-syncs your project before running it, something that would be painfully slow with pip. Keep this in mind: much of what feels like "magic" in later chapters is just uv doing the safe thing because it's cheap.

The mental model: three places

Everything uv does in a project comes down to keeping three things in agreement. Learn this picture now; every later chapter refers back to it.

pyproject.toml: what you want
A standard Python file (not uv-specific) with your project's name, required Python version and dependencies, written as ranges such as httpx>=0.27. You edit it by hand or with uv add.
uv.lock: what was resolved
The exact version of every package, direct and indirect, with download hashes. It covers every operating system and Python version your project supports, so the same file works on Windows, macOS and Linux. uv writes it; you commit it and never edit it by hand.
.venv: what is installed
The virtual environment, a folder holding a Python interpreter link and the installed packages. It's disposable: delete it and the next uv run or uv sync rebuilds it in seconds from the lockfile.

Where uv fits, and where it doesn't

  • It manages Python packages, not system libraries. If a package needs a C library such as GDAL or CUDA from the operating system, you still install that with your OS package manager, Docker or conda.
  • It uses standard formats. pyproject.toml, wheels, PyPI and virtual environments are the same standards pip uses. A uv project is a normal Python project; colleagues can still use pip if they must.
  • It is open source (MIT or Apache 2.0) and developed by Astral, the company behind the Ruff linter.

Key takeaways

  • Running Python reliably needs five jobs: get Python, isolate, install, lock, and run or ship tools. uv does all five.
  • uv is fast because it is compiled, parallel and cache-first, and installs by linking from the cache rather than copying.
  • The mental model: pyproject.toml (what you want) → uv.lock (what was resolved) → .venv (what is installed). uv run keeps all three in step.
  • Commit pyproject.toml and uv.lock; never commit .venv.
