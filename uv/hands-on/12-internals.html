Chapter 12 · Advanced

Internals, Configuration and Troubleshooting

You can use uv for years without knowing how it works inside. But when an install is mysteriously slow, a resolution fails, or a corporate proxy blocks downloads, knowing the internals turns a guessing game into a two-minute fix. This chapter looks under the hood and ends with a troubleshooting guide.

~40 min Commands: uv cache · uv -v · uv tree Config: uv.toml · [tool.uv] · UV_* variables

The cache and link modes

Every package uv installs passes through its global cache. A wheel is downloaded once, checked against its hash, and unpacked into the cache. Installing into an environment then means placing those unpacked files into site-packages, and how that happens is the link mode.

Link modeHow it worksDefault on
cloneCopy-on-write clone: instant, no extra space until a file is modifiedmacOS (APFS)
hardlinkA second name for the same file on disk: instant, no extra spaceLinux, Windows
copyA real copy: slower, uses space, always worksFallback
symlinkSymbolic link to the cache: fragile (cleaning the cache breaks environments)Never by default

Links only work within one filesystem. If your cache is on C: and your project on D:, or the cache is a Docker cache mount, uv falls back to copying and prints a warning. Either move the cache to the same drive (UV_CACHE_DIR) or set UV_LINK_MODE=copy to say "I know".

$ uv cache dir                   # where it is
$ du -sh "$(uv cache dir)"       # how big it is
$ uv cache prune                 # remove unused entries (safe)
$ uv cache prune --ci            # also drop downloaded wheels (before saving a CI cache)
$ uv cache clean                 # remove everything
$ uv cache clean numpy           # remove one package

Under the hood: hard links and "modifying" packages

With hard links, the file in your .venv and the file in the cache are the same file. If you edit an installed package's source for a quick debug, you're editing the cache, and every environment linked to it sees the change. Don't patch installed packages in place; use an editable source (Chapter 6) or uv sync --reinstall-package <name> afterwards to restore a clean copy.

How the resolver works

Resolving means choosing one version per package so every requirement is satisfied. In the worst case this is a hard search problem. uv uses PubGrub, an algorithm originally designed for Dart's package manager:

  1. Pick the next undecided package, starting with those with the fewest choices, and try its newest allowed version.
  2. Read that version's requirements (from the lock, the cache or the index's metadata, without downloading the whole package when the index supports it).
  3. When two requirements contradict each other, work out the root cause, record it as a new rule ("no version of A ≥ 2 can be used with B < 3") and jump back to the decision that caused it, instead of retrying blindly.
  4. Repeat until every package has a version, or until the rules prove no solution exists.

That learned rule is why uv's error messages explain why resolution failed:

× No solution found when resolving dependencies:
╰─▶ Because only pandas<2.0 is available and forecast depends on pandas>=2.2,
    we can conclude that forecast's requirements are unsatisfiable.
    And because your workspace requires forecast, we can conclude that your
    workspace's requirements are unsatisfiable.

Forking

For a universal lock (Chapter 7), uv sometimes needs different answers for different platforms, for example when a package requires numpy<2 on Python 3.11 only. The resolver then forks: it splits into one branch per set of markers, solves each branch, and merges the results into a single lockfile. You can see the forks in uv.lock as resolution-markers.

Configuration: where uv reads settings

Most options can be set on the command line, in an environment variable, or in a configuration file. When the same setting appears in several places, the most specific one wins:

python-preference = "only-managed"
link-mode = "copy"
native-tls = true                 # use the OS certificate store (corporate proxies)

[[index]]
name = "company"
url = "https://pypi.company.example/simple"
[tool.uv]
python-preference = "only-managed"
required-version = ">=0.9"        # refuse to run with an older uv

Use --no-config to ignore all configuration files, which is handy to check whether a setting is causing a problem.

Troubleshooting guide

First step for any problem: run the command again with -v (or -vv) to see what uv is doing, and check uv --version.

SymptomLikely causeFix
No solution found when resolving dependenciesTwo requirements contradict, often for a Python version in requires-python you don't useRead the explanation; raise requires-python, relax a bound, or limit environments
Failed to hardlink files; falling back to full copyCache and project on different filesystemsSet UV_CACHE_DIR on the same drive, or UV_LINK_MODE=copy
invalid peer certificate: UnknownIssuerCorporate proxy re-signs HTTPS traffic--native-tls / UV_NATIVE_TLS=1, or SSL_CERT_FILE
Failed to build <package>No wheel for your platform; building from source needs a compiler or system libraryUse a Python version that has wheels, install build tools, or pin an older version with wheels
The lockfile needs to be updated, but --locked was providedpyproject.toml changed without committing uv.lockRun uv lock locally and commit it
Wrong Python version in .venvA .python-version or UV_PYTHON you forgot aboutuv python find, then uv sync --python 3.x or update the pin
Package works with pip, not with uv, private indexuv takes each package from the first index onlyMark the index explicit and map the package in [tool.uv.sources]
A package you installed by hand disappeareduv sync / uv run are exactAdd it with uv add (or to a group) instead of uv pip install
Strange errors after a uv or Python upgradeStale environment or cache entryDelete .venv and run uv sync; if needed, uv cache clean <package>

Key takeaways

  • Packages are downloaded and unpacked into the cache once, then hard-linked or cloned into environments; keep the cache on the same filesystem as your projects.
  • The PubGrub resolver learns from conflicts, which is why uv can explain failed resolutions; universal locks fork the resolution per platform where needed.
  • Settings come from options, then UV_* variables, then project, user and system config files.
  • For any problem: -v, check the version, and use the troubleshooting table above.
