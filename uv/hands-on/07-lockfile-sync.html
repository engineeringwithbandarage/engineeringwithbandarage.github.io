The Lockfile and Sync

The lockfile is what makes "it works on my machine" true on every machine. This chapter opens uv.lock, explains how one file can serve Windows, macOS and Linux at once, and shows how to control exactly when uv is allowed to change it, which matters a lot in CI and production.

~35 min Commands: uv lock · uv sync · uv export Lab: fuelprice

Two steps: resolve, then install

Locking (resolving) answers "which exact versions satisfy every requirement?". It's a puzzle: httpx needs anyio, which needs idna, and every package has its own version ranges. The answer is written to uv.lock.

Syncing makes .venv match the lockfile exactly: installs what's missing, changes what's different and removes what isn't in the lock.

$ uv lock          # pyproject.toml → uv.lock
Resolved 14 packages in 210ms

$ uv sync          # uv.lock → .venv
Resolved 14 packages in 2ms
Audited 13 packages in 0.4ms

You rarely type either one: uv add, uv remove and uv run call them for you. But knowing them separately is the key to controlling uv in CI.

What's inside uv.lock

The lockfile is human-readable TOML. Here is a shortened extract:

version = 1
requires-python = ">=3.12"

[[package]]
name = "fuelprice"
version = "0.1.0"
source = { editable = "." }
dependencies = [
    { name = "httpx" },
    { name = "rich" },
]

[package.dev-dependencies]
dev = [{ name = "pytest" }]

[package.metadata]
requires-dist = [
    { name = "httpx", specifier = ">=0.28.1" },
    { name = "rich", specifier = ">=14.0.0" },
]

[[package]]
name = "httpx"
version = "0.28.1"
source = { registry = "https://pypi.org/simple" }
dependencies = [
    { name = "anyio" },
    { name = "certifi" },
    { name = "httpcore" },
    { name = "idna" },
]
sdist = { url = "https://files.pythonhosted.org/…/httpx-0.28.1.tar.gz", hash = "sha256:…", size = 141406 }
wheels = [
    { url = "https://files.pythonhosted.org/…/httpx-0.28.1-py3-none-any.whl", hash = "sha256:…", size = 73517 },
]

[[package]]
name = "colorama"
version = "0.4.6"
…
  • One entry per package, with one exact version, where it came from (source) and what it depends on.
  • Hashes for every file. When installing, uv checks each download against its SHA-256 hash, so a tampered or corrupted file is rejected.
  • All wheels, not just yours. A package like numpy lists wheels for every platform and Python version, so the same lock installs on any machine.
  • Your own requirements (package.metadata), so uv can tell instantly whether pyproject.toml changed since the lock was made.

Universal resolution: one lock for every platform

pip-tools and pip freeze record what was installed on your machine. Lock on a Mac, install on Windows, and packages such as colorama (needed by some tools only on Windows) are missing. uv resolves for every platform and every Python version in requires-python at once. Where the answer differs, the lock records both answers with conditions, called markers:

[[package]]
name = "click"
version = "8.2.1"
dependencies = [
    { name = "colorama", marker = "sys_platform == 'win32'" },
]

If a project only ever runs on some platforms, say so, and uv skips resolving for the others. That's faster, and it avoids failures from packages that don't exist on platforms you don't use:

[tool.uv]
environments = [
    "sys_platform == 'linux'",
    "sys_platform == 'win32'",
]

When does the lock change?

uv's rule is "change as little as possible". It keeps every locked version that still satisfies pyproject.toml. Adding a package resolves only what's needed for it; nothing else moves. The lock changes when:

  • you edit pyproject.toml by hand, or use uv add / uv remove;
  • you ask for upgrades with uv lock --upgrade or --upgrade-package;
  • a locked version disappears from the index (rare: a "yanked" release).

--locked and --frozen: control in CI

On your laptop, it's convenient that uv run and uv sync fix an outdated lock quietly. In CI and production you want the opposite: fail loudly if someone changed pyproject.toml but forgot to commit the updated lock. Two options give you that control:

$ uv sync --locked
error: The lockfile at `uv.lock` needs to be updated, but `--locked` was provided.
To update the lockfile, run `uv lock`.

$ uv lock --check              # only check, install nothing (good for pre-commit hooks)

Exact sync

By default uv sync is exact: it removes any package in .venv that isn't in the lock. If you uv pip installed something by hand, the next sync takes it away. That keeps environments honest. If you really need extras for a while, use uv sync --inexact, or better, add them to a dependency group.

$ uv sync --no-dev                    # production set
$ uv sync --no-install-project         # dependencies only (Docker layer caching, Chapter 11)
$ uv sync --reinstall-package numpy    # force one package to be reinstalled
$ uv sync --python 3.13                # rebuild .venv on another version

Resolution strategies

By default uv picks the newest versions that satisfy every requirement. For libraries, it's worth testing the other end too: do your lower bounds really work?

$ uv sync --resolution lowest-direct    # lowest allowed versions of your direct deps
$ uv run pytest

If tests fail, a lower bound in pyproject.toml is too low; raise it. Run this in CI as a separate job, not on your main lock.

To make resolution reproducible against a date (useful in research and for auditing), use exclude-newer:

[tool.uv]
exclude-newer = "2026-10-31T00:00:00Z"     # ignore anything published later

Exporting for other tools

Some platforms only understand requirements.txt. Export the lock, with hashes:

$ uv export --format requirements-txt --no-dev -o requirements.txt
$ head -4 requirements.txt
# This file was autogenerated by uv via the following command:
#    uv export --format requirements-txt --no-dev -o requirements.txt
anyio==4.x \
    --hash=sha256:…

$ uv export --format pylock.toml -o pylock.toml     # the new standard lock format (PEP 751)

Keep uv.lock as the source of truth and regenerate exports from it, never the other way round.

Merge conflicts in uv.lock

Two branches that both add dependencies will conflict in uv.lock. Don't try to merge it by hand: resolve the conflict in pyproject.toml, take either version of uv.lock, and regenerate it.

$ git checkout --theirs uv.lock
$ uv lock
$ git add uv.lock pyproject.toml

Key takeaways

  • uv lock resolves pyproject.toml into exact versions with hashes; uv sync makes .venv match exactly.
  • The lock is universal: one file covers every platform and Python version in requires-python, using markers where answers differ.
  • uv changes the lock as little as possible and upgrades only when asked.
  • Use --locked in CI to fail on a stale lock, and --frozen to install without checking.
  • uv export produces requirements.txt or pylock.toml for tools that need them.
