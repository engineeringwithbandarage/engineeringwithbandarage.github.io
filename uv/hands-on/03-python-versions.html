Managing Python Versions

Different projects need different Python versions: an old service still runs on 3.10, a new one wants 3.13. uv installs as many versions as you like side by side, picks the right one per project, and never touches the Python that came with your operating system.

~20 min Commands: uv python list · install · find · pin · uninstall

See what you have

uv python list shows interpreters uv has found on your machine and the versions it could download.

$ uv python list
cpython-3.14.0-linux-x86_64-gnu      <download available>
cpython-3.13.5-linux-x86_64-gnu      /home/sameera/.local/share/uv/python/cpython-3.13.5-…/bin/python3.13
cpython-3.12.3-linux-x86_64-gnu      /usr/bin/python3.12
cpython-3.11.13-linux-x86_64-gnu     <download available>
pypy-3.11.13-linux-x86_64-gnu        <download available>
…

There are two kinds of interpreter in that list:

  • Managed Pythons live in uv's own folder (uv python dir). uv downloaded them, and it can install or remove them freely.
  • System Pythons were installed some other way: by your OS, python.org, Homebrew, the Microsoft Store or pyenv. uv will use them, but never modifies them.
$ uv python list --only-installed       # only what is on disk
$ uv python list 3.12                   # only versions matching 3.12
$ uv python list --all-versions         # every patch release, not just the latest

Install Python versions

$ uv python install 3.12
Installed Python 3.12.11 in 2.1s
 + cpython-3.12.11-linux-x86_64-gnu

$ uv python install 3.11 3.13         # several at once
$ uv python install                   # the version in .python-version, or the latest
$ uv python install pypy@3.11         # an alternative implementation
$ uv python install 3.13t             # free-threaded build (no GIL)

Managed Pythons come from the python-build-standalone project: pre-built, relocatable interpreters that unpack in seconds, with no compiler needed. That's why installing takes seconds rather than the minutes pyenv needs to compile from source.

You rarely need to install explicitly

If a command needs a Python version that isn't on your machine, uv downloads it automatically. uv python install is useful to prepare a machine in advance (for example in a Docker image) or to get a newer patch release.

Recent uv versions also put version-named commands such as python3.12 into the same folder as uv (~/.local/bin), so you can start a managed interpreter directly.

Find out which Python uv would use

$ uv python find
/home/sameera/.local/share/uv/python/cpython-3.13.5-…/bin/python3.13

$ uv python find 3.12
/usr/bin/python3.12

$ uv run python --version             # what a command really runs with
Python 3.13.5

Pin a version for a folder

A .python-version file tells uv (and pyenv, and other tools) which version to use in a folder and every folder below it. Create one with uv python pin:

$ mkdir fuelprice && cd fuelprice
$ uv python pin 3.12
Pinned `.python-version` to `3.12`

$ cat .python-version
3.12

$ uv run python --version
Python 3.12.11

Commit .python-version to git so everyone on the team gets the same minor version. uv init (Chapter 5) creates it for you.

Choose a version for one command

Almost every uv command accepts --python (short form -p). It wins over everything else, which makes it ideal for trying your code on another version:

$ uv run --python 3.11 python --version
Python 3.11.13

$ uv run -p 3.13 python -c "import sys; print(sys.version_info[:2])"
(3, 13)

Version requests can be written in several ways:

RequestMeans
3, 3.12, 3.12.4Any matching CPython, from least to most specific
>=3.11,<3.13A version range
3.13tThe free-threaded build of 3.13
pypy@3.11, cpython@3.12A specific implementation
/usr/bin/python3An exact interpreter path

How uv chooses an interpreter

When a command needs Python, uv works through a fixed order of preferences. Once you know it, you'll never be surprised by "why is this running on 3.11?".

You can change the right-hand side with the python-preference setting (or --python-preference):

ValueBehaviourGood for
managed (default)Prefer managed Pythons, fall back to system onesMost people
only-managedNever use a system PythonFully reproducible machines
systemPrefer system Pythons, fall back to managed onesLocked-down machines with an approved Python
only-systemNever use or download managed PythonsDistribution packaging, strict corporate rules

Upgrade and remove

$ uv python install 3.12 --reinstall    # get the latest 3.12.x patch release
$ uv python uninstall 3.11              # remove a managed version

Environments point at an interpreter

A virtual environment links to the exact interpreter that created it. If you uninstall that Python, environments built on it stop working. The fix is quick: delete the .venv folder and run uv sync, and uv rebuilds it with an available version.

Try it yourself

Exercise

  1. Install Python 3.11 and 3.13 with one command.
  2. In an empty folder, pin 3.11 and confirm uv run python --version prints 3.11.
  3. Without changing the pin, run the same command on 3.13 using --python.
  4. Run uv python find from the folder and from its parent. Why are the answers different?

Key takeaways

  • uv python install downloads pre-built interpreters in seconds and keeps many versions side by side.
  • .python-version pins a version for a folder tree; commit it. --python overrides it for one command.
  • uv first decides the version (option → .python-version → requires-python), then the interpreter (managed → system → download).
  • uv never modifies system Pythons; it only adds and removes its own.
