The pip Interface and Migration

Not every codebase can switch to uv projects overnight. uv has a second, lower-level interface that behaves like pip, venv and pip-tools, only much faster. It's the easiest way to bring uv into an existing workflow, and a stepping stone to a full migration.

~30 min Commands: uv venv · uv pip install · compile · sync · freeze Replaces: venv, pip, pip-tools

Two interfaces, one engine

Virtual environments with uv venv

$ uv venv
Using CPython 3.12.11
Creating virtual environment at: .venv
Activate with: source .venv/bin/activate

$ uv venv --python 3.11            # a specific Python
$ uv venv build-env                # a different folder name
$ uv venv --seed                   # also install pip into it, for tools that expect pip

An environment made by uv venv doesn't contain pip, because uv doesn't need it. Add --seed only if another tool insists on calling pip inside it.

Installing packages with uv pip

The commands mirror pip. uv installs into, in order: the activated environment, else a .venv in the current or a parent folder. It refuses to touch a system Python unless you pass --system.

$ uv pip install pandas "sqlalchemy>=2"
$ uv pip install -r requirements.txt
$ uv pip install -e .                       # your project, editable
$ uv pip install "fuelprice[plot] @ ./fuelprice"
$ uv pip uninstall pandas
$ uv pip list
$ uv pip show httpx
$ uv pip freeze > installed.txt
$ uv pip tree
$ uv pip check                              # find broken or conflicting installs

Differences from pip worth knowing

  • No environment, no install. uv won't install into a system Python by accident. Use --system deliberately (for example in a Docker image without a virtual environment).
  • Indexes. With several indexes, uv uses the first one that has a package, not the best version across all of them (Chapter 6).
  • No pip.conf. uv reads its own settings (uv.toml, UV_* variables), not pip's configuration files.
  • Pre-releases are only chosen when you ask for one or when nothing else fits.

The pip-tools workflow: compile and sync

Before uv projects existed, the best practice was pip-tools: write loose requirements in requirements.in, compile them into a fully pinned requirements.txt, then sync environments to it. uv does the same, faster:

pandas>=2.2
sqlalchemy>=2
httpx
$ uv pip compile requirements.in -o requirements.txt
Resolved 14 packages in 160ms

$ uv pip compile requirements.in -o requirements.txt --universal    # one file for all platforms
$ uv pip compile requirements.in -o requirements.txt --generate-hashes
$ uv pip compile requirements.in -o requirements.txt --upgrade-package pandas

$ uv pip sync requirements.txt     # make the environment match exactly

uv pip sync removes anything not in the file, just as uv sync does for projects. uv pip install -r only adds.

Migrating to a uv project

The pip interface is a good first step, but a uv project gives you the lockfile, dependency groups, Python pinning and uv run. Here's how to move common setups.

From requirements.txt

$ cd legacy-app
$ uv init --bare                         # only pyproject.toml, keep existing files
$ uv add -r requirements.in              # loose requirements become dependencies
$ uv add --dev -r requirements-dev.in    # dev requirements go into the dev group
$ uv lock

If you only have a fully pinned requirements.txt, you can still import it, but you'd lock every indirect package as a direct dependency. A cleaner way: add only the packages your code imports, then reuse the old pins as constraints so the first lock gives the same versions as before:

$ uv add pandas sqlalchemy httpx -c requirements.txt

From Poetry

Poetry projects already have a pyproject.toml, but with Poetry-specific sections ([tool.poetry.dependencies], caret versions like ^2.2). The community tool migrate-to-uv rewrites them into standard sections and keeps your locked versions:

$ uvx migrate-to-uv          # converts pyproject.toml and creates uv.lock
$ git diff pyproject.toml    # review the changes
$ uv sync
$ uv run pytest

From conda

If your conda environment only holds Python packages from PyPI, list them in a pyproject.toml and switch completely. If it holds non-Python libraries (CUDA, GDAL, MKL), keep conda for those and consider using uv for the Python packages on top, or a Docker image that provides the system libraries.

Try it yourself

Exercise

  1. Write a requirements.in with pandas and httpx, compile it with --universal, and look at the markers in the output.
  2. Create an environment with uv venv and uv pip sync it to the file.
  3. Migrate the same folder to a uv project with uv init --bare and uv add -r requirements.in. Compare uv.lock with your compiled requirements.txt.

Key takeaways

  • uv venv and uv pip are drop-in, much faster replacements for venv, pip and pip-tools. You manage the files.
  • uv pip compile pins a requirements.in; --universal makes the result work on every platform. uv pip sync applies it exactly.
  • uv won't install into a system Python unless you pass --system.
  • Migrate with uv init --bare + uv add -r for requirements files, and uvx migrate-to-uv for Poetry.
