Chapter 10 · Advanced

Workspaces, Building and Publishing

fuelprice is growing. The price-loading code is now wanted by a web API and a nightly forecast job too. Copying it around would be a mistake; publishing it to PyPI just to share it inside one repository is overkill. uv workspaces keep several packages in one repository with one lockfile. When a package is ready for the world, uv build and uv publish ship it.

~40 min Commands: uv init (in a workspace) · uv run --package · uv version · uv build · uv publish Lab: fuelprice monorepo

Part 1: Workspaces

A workspace is a root project plus members, each with its own pyproject.toml. They share one uv.lock and one .venv, so every member is guaranteed to use the same version of every third-party package.

Step 1: Create the workspace

$ uv init fuelprice --bare          # root: only pyproject.toml
$ cd fuelprice
$ uv init --lib packages/pricecore
$ uv init --package packages/priceapi
$ uv init --package packages/forecast

Running uv init inside an existing project adds the new folder to the workspace automatically. uv lists each member by path; replace the list with a glob so future members are picked up too. The root pyproject.toml then contains:

[project]
name = "fuelprice"
version = "0.1.0"
requires-python = ">=3.12"
dependencies = []

[tool.uv.workspace]
members = ["packages/*"]

Step 2: Connect the members

Make priceapi depend on pricecore. Because pricecore is a workspace member, uv records it as a workspace source instead of looking for it on PyPI:

$ uv add --package pricecore pandas
$ uv add --package priceapi pricecore fastapi uvicorn
$ uv add --package forecast pricecore statsmodels
[project]
name = "priceapi"
version = "0.1.0"
requires-python = ">=3.12"
dependencies = ["pricecore", "fastapi>=0.116", "uvicorn>=0.35"]

[tool.uv.sources]
pricecore = { workspace = true }

[project.scripts]
priceapi = "priceapi:main"

Step 3: Work in the workspace

$ uv lock                                 # one lock for everything
$ uv sync --all-packages                  # install every member
$ uv run --package priceapi priceapi      # run a member's command
$ uv run --package forecast pytest        # test one member
$ cd packages/forecast && uv run pytest   # same: uv picks the member from the folder

A change to pricecore is visible to priceapi and forecast immediately, because members are installed editable.

When not to use a workspace

One lockfile means one version of each package for every member. If forecast needs pandas 1.x and priceapi needs pandas 2.x, they can't share a workspace. Make them separate projects that use pricecore through a path source (Chapter 6) instead.

Part 2: Building packages

To share pricecore outside the repository, build it into distribution files:

  • a wheel (.whl): a ready-to-install zip; installing it is just unpacking;
  • a source distribution (.tar.gz, "sdist"): the source code plus the instructions to build a wheel from it.

The build backend named in [build-system] does the actual building. uv's own backend, uv_build, is fast and needs no configuration for pure-Python packages in the standard src/ layout; uv init --package and --lib use it by default. Use another backend when you need its features:

BackendChoose it when
uv_buildPure Python, standard layout: the default
hatchlingYou need build hooks, generated files or unusual layouts
setuptoolsExisting projects, C extensions with setup.py
maturin / scikit-build-coreExtensions written in Rust / C++ with CMake
 
$ uv build --package pricecore
Building source distribution...
Building wheel from source distribution...
Successfully built dist/pricecore-0.1.0.tar.gz
Successfully built dist/pricecore-0.1.0-py3-none-any.whl

$ uv build --all-packages            # every member
$ uv build --wheel                   # wheel only

Test the wheel, not the folder

Editable installs hide packaging mistakes, such as a data file missing from the wheel. Before publishing, install the built wheel into a clean environment and import it: uv run --isolated --no-project --with dist/pricecore-0.1.0-py3-none-any.whl python -c "import pricecore".

Part 3: Versioning

$ uv version --package pricecore
pricecore 0.1.0

$ uv version --package pricecore --bump minor
pricecore 0.1.0 => 0.2.0

$ uv version --package pricecore --bump patch --dry-run   # preview only
$ uv version --package pricecore 1.0.0                    # set it exactly

uv version edits version in pyproject.toml and updates the lockfile. Tag the commit (git tag pricecore-v0.2.0) so you can find the source of every release.

Part 4: Publishing

Always try a release on TestPyPI first. Define it as an index in the root pyproject.toml:

[[tool.uv.index]]
name = "testpypi"
url = "https://test.pypi.org/simple/"
publish-url = "https://test.pypi.org/legacy/"
explicit = true
$ uv publish --index testpypi --token "$TEST_PYPI_TOKEN" dist/pricecore-0.2.0*
$ uv run --isolated --no-project --index testpypi --with pricecore python -c "import pricecore"

$ uv publish --token "$PYPI_TOKEN" dist/pricecore-0.2.0*      # the real thing

Better than any token is trusted publishing: you register your GitHub repository and workflow on PyPI once, and GitHub Actions proves its identity to PyPI at publish time. No secret is stored anywhere. In a workflow with permissions: id-token: write, a plain uv publish uses it automatically. Chapter 11 shows the full workflow.

Key takeaways

  • A workspace is several packages in one repository with one uv.lock and one .venv; members depend on each other through { workspace = true } sources.
  • Use --package to target a member, and --all-packages to sync or build all of them.
  • Workspaces force one version of each third-party package; projects that need different versions should be separate.
  • uv version --bump, uv build and uv publish cover the release cycle; test on TestPyPI and prefer trusted publishing over tokens.
