Reference architecture · modern ELT stack

dbt + Airflow + Snowflake

Data is loaded raw into Snowflake, transformed inside Snowflake by dbt, and the whole run is scheduled and monitored by Airflow. Each tool does one job: Snowflake stores and computes, dbt defines the transformations, and Airflow decides when things run.

How a daily run flows

  1. Extract and load. Fivetran or Airbyte copy database and SaaS data into Snowflake RAW schemas. Files land in S3 and Snowpipe loads them, and Kafka events arrive through Snowpipe Streaming. Nothing is transformed yet.
  2. Land in RAW. Data arrives as-is, with JSON kept in VARIANT columns. dbt declares these tables as sources with freshness rules.
  3. Airflow starts the transformation. The DAG waits for loads to finish (sensor or connector API), runs dbt source freshness, then dbt build. With Cosmos, each model becomes its own Airflow task with its own retry.
  4. dbt transforms inside Snowflake. dbt compiles models to SQL and runs them on TRANSFORM_WH, building staging → intermediate → marts in DAG order. Tests run right after each model, and a failed test stops everything downstream of it.
  5. Serve. BI tools query the marts through BI_WH (multi-cluster for the morning rush). Snowpark notebooks, reverse ETL and data shares read the same tables.
  6. Monitor. Airflow alerts on failures. dbt artifacts (run_results.json) record timings and test results, and Snowflake ACCOUNT_USAGE plus resource monitors track cost.

Airflow DAG and dbt project

DAG with Cosmos

from cosmos import DbtTaskGroup, ProjectConfig, ProfileConfig
from cosmos.profiles import SnowflakePrivateKeyPemProfileMapping

profile = ProfileConfig(
    profile_name="analytics", target_name="prod",
    profile_mapping=SnowflakePrivateKeyPemProfileMapping(
        conn_id="snowflake_transformer"),
)

with DAG("daily_elt", schedule="0 5 * * *",
         start_date=datetime(2026, 1, 1), catchup=False,
         default_args={"retries": 2}) as dag:

    wait_load = FivetranSensor(task_id="wait_fivetran", ...)
    freshness = BashOperator(task_id="freshness",
        bash_command="dbt source freshness")
    transform = DbtTaskGroup(group_id="dbt",
        project_config=ProjectConfig("/opt/airflow/dbt/analytics"),
        profile_config=profile)

    wait_load >> freshness >> transform

Change flow from laptop to production

Develop in DBT_DEV_<USER>→ Open a pull request→ CI clones prod, runs dbt build -s state:modified+ --defer→ Review and merge→ New dbt image deployed to Airflow→ Next scheduled run builds prod

Explaining it in an interview

The two-minute answer

“We use an ELT pattern. Fivetran and Snowpipe land raw data in Snowflake, and dbt transforms it in layers: staging cleans each source, intermediate holds the business logic, and marts publish tested facts and dimensions. Airflow orchestrates the run. It waits for the loads, checks source freshness, then runs dbt through Cosmos so each model is its own task with retries and alerts.

Snowflake gives us a separate warehouse for loading, transforming and BI, so the workloads never compete. Every change goes through a pull request, and CI builds only the modified models against a zero-copy clone of prod.”

  • Why ELT and not ETL? Snowflake compute is elastic, so transforming inside it is simpler and keeps the raw data available for replay.
  • Why Airflow if dbt has its own DAG? dbt only orders SQL models. Airflow coordinates the whole pipeline: loads, dbt, ML jobs, reverse ETL, alerts and backfills.
  • Why Cosmos over a single BashOperator? You get per-model visibility and retries, so a failure reruns one model instead of the whole project.
  • Alternatives worth naming: dbt Cloud's scheduler instead of Airflow; Snowflake tasks or dynamic tables for simple in-warehouse pipelines; Dagster for asset-based orchestration.
